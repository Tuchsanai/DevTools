#ในฐานะฉันต้องการ … เพื่อ …มาจากประโยคไหน
US-1อาจารย์/เจ้าหน้าที่แจ้งซ่อมโดยระบุห้องและอาการ · เพื่อให้เรื่องไม่หายไปกับแชท"อาจารย์ทักในไลน์กลุ่มตอนสามทุ่ม … ผมก็ลืมจด"
US-2หัวหน้าสำนักงานมอบหมายงานให้ช่างเป็นรายคน · เพื่อตอบได้ว่าเรื่องอยู่ที่ใคร"อยากเห็นหน้าจอเดียวที่บอกว่าตอนนี้มีงานอะไรอยู่ในมือใครบ้าง"
US-3ช่างซ่อมบำรุงเห็นเฉพาะงานของตัวเอง · เพื่อไม่ต้องเดินมาถามทุกเช้า"ผมอยากรู้ว่างานไหนเป็นของผม"
US-4ช่างซ่อมบำรุงปิดงานพร้อมบันทึกอะไหล่ที่ใช้ · เพื่อไม่ต้องกลับมาแจ้งพัสดุทีหลัง"ถ้ามันบันทึกตอนปิดงานได้เลยว่างานนี้ใช้อะไหล่อะไรไปบ้าง"

US-5…US-7 — รายงาน · ยืม-คืน · อะไหล่

#ในฐานะฉันต้องการ … เพื่อ …มาจากประโยคไหน
US-5หัวหน้าสำนักงานเห็นจำนวนงานตามสถานะและงานที่ค้างนาน · เพื่อรายงานโดยไม่ต้องนั่งนับ"ต้องนั่งนับเอง ใช้เวลาครึ่งวัน"
US-6เจ้าหน้าที่พัสดุให้ระบบปฏิเสธการยืมของที่มีคนยืมอยู่ · เพื่อไม่ให้จ่ายของซ้ำ"คนมายืมโปรเจกเตอร์ตัวเดิมวันเดียวกันสองคน"
US-7เจ้าหน้าที่พัสดุเห็นยอดอะไหล่คงเหลือและคำเตือนเมื่อใกล้หมด · เพื่อสั่งซื้อทัน"อะไหล่หมดโดยไม่รู้ตัว … ถ้ามีตัวเลขบอกว่าเหลือเท่าไหร่"
ทุกแถวมีคอลัมน์ขวาสุดเสมอ — กันไม่ให้ทีมพัฒนาใส่ฟีเจอร์ที่ลูกค้าไม่เคยขอ · เต็มที่ docs/01_requirements.md

REQ-01…REQ-06 — งานซ่อมและการเบิกอะไหล่

ทุกข้อตัดสิน "ผ่าน" หรือ "ไม่ผ่าน" ได้
REQข้อกำหนดเกณฑ์ผ่านจาก
REQ-01สร้างใบแจ้งซ่อมได้ ระบุครุภัณฑ์ อาการ ความเร่งด่วนPOST /api/tickets คืน 201 และใบใหม่มีสถานะ NEWUS-1
REQ-02ใบเดินตามลำดับ NEW → ASSIGNED → IN_PROGRESS → DONE เท่านั้นสั่ง NEW → DONE ตรง ๆ ต้องได้ 409 และสถานะไม่เปลี่ยนUS-2
REQ-03มอบหมายงานต้องระบุชื่อช่างเปลี่ยนเป็น ASSIGNED โดยไม่ส่งชื่อช่าง ต้องได้ 400US-2
REQ-04กรองใบแจ้งซ่อมตามช่างผู้รับผิดชอบได้GET /api/tickets?assignee=TECH-01 คืนเฉพาะงานของคนนั้นUS-3
REQ-05ปิดงานพร้อมบันทึกอะไหล่ที่ใช้ได้ (ไม่ใช้อะไหล่ก็ปิดได้)ปิดงานพร้อมอะไหล่ 2 รายการ → ยอดคงเหลือทั้งสองลดลงตามจำนวนUS-4
REQ-06เบิกอะไหล่เกินยอดคงเหลือไม่ได้เบิกเกินยอด ต้องได้ 409 และยอดคงเหลือไม่เปลี่ยนUS-4, US-7

สิ่งที่ ไม่ ทำในเวอร์ชันนี้

ของที่ไม่ได้เขียนว่า "ไม่ทำ" มักกลายเป็นสิ่งที่ลูกค้าคิดว่าจะได้

ลูกค้าพูดเองว่ายังไม่ต้องการ

  • ระบบล็อกอินและการแบ่งสิทธิ์
  • แจ้งเตือนเข้าไลน์
  • แอปมือถือ

ทีมพัฒนาขอตัดออกเอง

  • รายงานส่งออก Excel
  • ระบบอนุมัติหลายชั้น
  • การจองล่วงหน้าเป็นช่วงวันที่
ระบบนี้เป็น เคสสอน ไม่ใช่ผลิตภัณฑ์ — ลูกค้า หน่วยงาน และบุคคลทั้งหมดเป็นสมมติ · รหัสผ่านทั้งหมด (เช่น labpass) เป็นค่าสำหรับแล็บที่เขียนไว้ในไฟล์ตรง ๆ
named volume พิสูจน์ว่าข้อมูลรอดการสร้างกล่องใหม่ แต่ ไม่ใช่ระบบสำรองข้อมูล · compose.yaml ของชุดนี้เป็นแบบ เครื่องเดียว — งานหลายเครื่องต้องใช้ orchestrator
การเขียนขอบเขตให้ชัดคือส่วนหนึ่งของการเก็บ requirements — ไม่ใช่การปฏิเสธลูกค้า
