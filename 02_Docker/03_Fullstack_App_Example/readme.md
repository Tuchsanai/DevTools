**ชุดนี้คือ "ตัวอย่างสรุป" ไม่ใช่บทเรียนใหม่** — ไม่มีคำสั่ง Docker ตัวไหนในชุดนี้ที่ไม่เคยสอนมาก่อน
ทุกเทคนิคมาจาก [`01_Docker_Basics_Run_Port_Volume_Build`](../01_Docker_Basics_Run_Port_Volume_Build/readme.md)
และ [`02_Dockerfile_Build_Run_Compose_Guide`](../02_Dockerfile_Build_Run_Compose_Guide/readme.md)
สิ่งที่เพิ่มเข้ามาคือ **โจทย์ธุรกิจจริงหนึ่งโจทย์** ที่บังคับให้เราต้องเลือกใช้เทคนิคเหล่านั้นให้ถูกตัว

> **คำถามเดียวของทั้งชุด :** *ข้อจำกัดของลูกค้าข้อไหน บังคับให้ต้องใช้เทคนิค Docker ตัวไหน*
> ซึ่งเป็นคนละเรื่องกับการท่องคำสั่ง เพราะข้อจำกัดของลูกค้ารายถัดไปจะไม่เหมือนเดิม

ระบบที่สร้างชื่อ **CampusOps** — งานแจ้งซ่อม · ยืม-คืนครุภัณฑ์ · คลังอะไหล่ ของสำนักงานคณะสมมติแห่งหนึ่ง
ประกอบด้วย **สามกล่อง** : หน้าเว็บ (`web`) · บริการเบื้องหลัง (`api`) · ฐานข้อมูล (`db`)

ทุกคำสั่งและทุกบล็อก `✅ สิ่งที่ต้องเห็น` ใน README ของแต่ละแล็บ **มาจากการรันจริง**

## ผลลัพธ์การเรียนรู้

เมื่อจบชุดนี้ ผู้เรียนควรทำให้เห็นได้ว่า :

- แปลงคำบ่นของลูกค้าเป็น REQ/NFR ที่ทดสอบได้ แล้วชี้ได้ว่า NFR ข้อนั้นตกไปเป็นหน้าที่ของเทคนิค Docker ตัวไหน
- ยกฐานข้อมูลพร้อม schema + seed ขึ้นด้วย `docker run` และอธิบายได้ว่าข้อมูลหายตอนไหน · รอดตอนไหน
- build image ของ backend และ frontend จาก Dockerfile จริง โดยเรียงบรรทัดให้ layer cache ทำงาน
- ใช้ multi-stage ตัด toolchain ออกจาก image ที่ส่งมอบ (1.09GB → 298MB จาก source ชุดเดียวกัน)
- แยกได้ว่าค่าไหนต้องมาตอน **build** (`ARG`) ค่าไหนอ่านตอน **run** (`ENV`) และทำไมสลับกันไม่ได้
- ต่อสามกล่องด้วย user-defined network ให้เรียกกันด้วย **ชื่อ** และพิสูจน์ได้ว่า `db` ไม่มีประตูออกนอกเครื่อง
- ยุบทุก flag ที่พิมพ์มา 4 แล็บลงใน `compose.yaml` ไฟล์เดียว แล้วส่งมอบผ่าน Docker Hub โดยเครื่องปลายทางไม่ต้องมีซอร์สโค้ด

## เตรียมเครื่องเรียน

ทุกแล็บรันในเครื่องเรียนแบบ **Docker-in-Docker** โดย **แต่ละแล็บมี container และพอร์ตของตัวเอง**
จึงเปิดค้างพร้อมกันได้โดยไม่ชนกัน (คำสั่งเต็มอยู่ในหัวข้อ "เตรียมเครื่องเรียน" ของแต่ละแล็บ) :

| LAB | container | SSH | พอร์ตอื่น (เครื่องเรา → กล่องเรียน) |
|---|---|---:|---|
| 1 | `devtools-fs-lab1` | 2251 | — (คุยกับฐานข้อมูลผ่าน `docker exec`) |
| 2 | `devtools-fs-lab2` | 2252 | `8252:8088` (API + หน้า `/docs`) |
| 3 | `devtools-fs-lab3` | 2253 | `8253:3000` (หน้าเว็บ) |
| 4 | `devtools-fs-lab4` | 2254 | `8254:3000` (หน้าเว็บ) |
| 5 | `devtools-fs-lab5` | 2255 | `8255:3000` (หน้าเว็บ) |

ตัวอย่างของ LAB 1 (แล็บอื่นเปลี่ยนชื่อและพอร์ตตามตาราง) :

```bash
docker rm -f devtools-fs-lab1 2>/dev/null
docker run -dit --name devtools-fs-lab1 --privileged -p 2251:22 tuchsanai/devtools:2569_1
ssh root@localhost -p 2251        # password : passwd
```

> `--privileged` ใช้เฉพาะ **disposable classroom container** นี้เพื่อรัน Docker ซ้อนข้างใน
> ไม่ใช่ค่าที่ควรใช้กับ production workload

จากนั้นใช้ VS Code **Remote-SSH** ต่อไปที่ `root@localhost:<พอร์ต SSH ของแล็บ>` แล้วทำแล็บทั้งหมดข้างใน
และ clone โค้ดแล็บครั้งเดียวใช้ได้ทุกแล็บ :

```bash
mkdir -p ~/labwork && cd ~/labwork
git clone --depth 1 https://github.com/Tuchsanai/DevTools.git
cd DevTools/02_Docker/03_Fullstack_App_Example
```

> LAB 1 การทดลองที่ 1 แสดงลำดับเปิด repository, เข้าโฟลเดอร์ชุดสอน และคัดลอก URL แบบ HTTPS จาก GitHub ก่อนใช้คำสั่ง `git clone`
> `docker cp <โฟลเดอร์นี้> <ชื่อกล่องเรียน>:/root/labwork/` แล้วข้ามขั้น clone ไป

## ขอบเขตของสิ่งที่แล็บพิสูจน์

- **ระบบนี้เป็นเคสสอน ไม่ใช่ผลิตภัณฑ์** — ลูกค้า หน่วยงาน และบุคคลทั้งหมดเป็นสมมติ · ชื่อคนใช้ตำแหน่งงานแทนชื่อจริง
- **ไม่มีระบบล็อกอินและไม่มีการแบ่งสิทธิ์** เพราะลูกค้าพูดเองว่ายังไม่ต้องการ (`docs/00_story.md`) — ใครเปิดหน้าเว็บได้ก็กดได้ทุกปุ่ม
- LAB 5 ใช้ **Docker Hub จริง** โดยตั้ง repository เป็น Public ใช้ Access Token อายุสั้นสำหรับ push/pull และ revoke หลังจบแล็บ
- รหัสผ่านทั้งหมด (`labpass` ฯลฯ) เป็น **ค่าสำหรับแล็บ** ที่เขียนไว้ในไฟล์ตรง ๆ · งานจริงต้องใช้ secret ที่ไม่เข้า git
- `compose.yaml` ของชุดนี้เป็นแบบ **เครื่องเดียว** — งานหลายเครื่องต้องใช้ orchestrator เช่น Kubernetes
- **named volume พิสูจน์แค่ว่า "ข้อมูลไม่ผูกชะตากับ container" ไม่ได้พิสูจน์ว่า "ข้อมูลไม่ผูกชะตากับเครื่อง"** —
  สามชั้นนี้คนละเรื่องกัน อย่าสับสน :

  | ชั้น | คำถาม | ชุดนี้ทำไหม |
  |---|---|---|
  | ข้อมูลรอดการสร้างกล่องใหม่ | ลบ container แล้วสร้างใหม่ ข้อมูลยังอยู่ไหม | ✅ พิสูจน์แล้ว — **LAB 1** การทดลองที่ 7–8 · **LAB 5** `down` เทียบ `down -v` |
  | สำรองข้อมูล (backup) | เผลอ `docker volume rm` หรือลบข้อมูลผิด กู้กลับได้ไหม | ❌ ไม่ได้ทำ — volume คือข้อมูล**ชุดเดียว** ไม่ใช่สำเนาสำรอง ของจริงต้อง `pg_dump` ไปเก็บที่อื่น |
  | ระบบไม่ล่ม (High Availability) | ดิสก์พังหรือเครื่องดับ ระบบยังให้บริการต่อได้ไหม | ❌ ไม่ได้ทำ — ทั้งระบบอยู่**เครื่องเดียว** `db` มีตัวเดียว ไม่มี replica ไม่มี failover |

  *disk failure* = ดิสก์ลูกที่เก็บ volume พัง volume หายตามเพราะมีสำเนาเดียว · *node failure* = เครื่องดับทั้งเครื่อง
  `web` `api` `db` ดับพร้อมกัน ไม่มีเครื่องสำรองรับช่วง — เรื่องนี้เป็นงานของ orchestrator (Kubernetes) และระบบ backup จริง
- `healthcheck` + `depends_on` ช่วยเรื่อง**ลำดับการเริ่ม** แต่โค้ดแอปยังต้อง retry เอง เพราะ service ล้มหลังเริ่มแล้วได้
- แล็บยิง REQ-01…REQ-12 ครบทุกข้อด้วย `curl` จริง (`api/smoke.sh` ที่ **LAB 2** การทดลองที่ 11)
  และเห็นผลบนหน้าเว็บจริงอีกชั้น (REQ-08 · REQ-09 · REQ-12 ที่ **LAB 3** การทดลองที่ 8)
  แต่ชุดนี้ยัง**ไม่ใช่**แล็บสอน automated testing — ไม่มี unit test / CI ให้ดู

## เก็บกวาดหลังเลิกเรียน

แต่ละแล็บมีขั้นตอนเก็บกวาดของตัวเองอยู่ท้าย README (ลบทรัพยากรในกล่องเรียน แล้วลบกล่องเรียนของแล็บนั้น)
ถ้าต้องการล้างทุกแล็บพร้อมกันจาก **เครื่องของผู้เรียน** :

```bash
docker rm -f devtools-fs-lab1 devtools-fs-lab2 devtools-fs-lab3 devtools-fs-lab4 devtools-fs-lab5 2>/dev/null
docker ps -a --filter "name=devtools-fs-lab"
```

> ลบกล่องเรียนทิ้ง = ของทุกอย่างที่สร้างข้างในกล่อง (image · volume · network) หายตามไปด้วยทั้งหมด
