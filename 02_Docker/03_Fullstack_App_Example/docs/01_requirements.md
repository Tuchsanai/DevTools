## 2. ข้อกำหนดที่ทดสอบได้ (Acceptance Criteria)

**ทุกข้อต้องตัดสินได้ว่า "ผ่าน" หรือ "ไม่ผ่าน" โดยไม่ต้องตีความ**

| REQ | ข้อกำหนด | เกณฑ์ผ่าน (ทดสอบอย่างไร) | จาก |
|---|---|---|---|
| **REQ-01** | สร้างใบแจ้งซ่อมได้ โดยต้องระบุครุภัณฑ์ อาการ และความเร่งด่วน | `POST /api/tickets` คืน `201` และใบใหม่มีสถานะ `NEW` | US-1 |
| **REQ-02** | ใบแจ้งซ่อมเดินตามลำดับ `NEW → ASSIGNED → IN_PROGRESS → DONE` เท่านั้น | สั่ง `NEW → DONE` ตรง ๆ ต้องได้ `409` และสถานะไม่เปลี่ยน | US-2 |
| **REQ-03** | มอบหมายงานต้องระบุชื่อช่าง | เปลี่ยนเป็น `ASSIGNED` โดยไม่ส่งชื่อช่าง ต้องได้ `400` | US-2 |
| **REQ-04** | กรองใบแจ้งซ่อมตามช่างผู้รับผิดชอบได้ | `GET /api/tickets?assignee=TECH-01` คืนเฉพาะงานของคนนั้น | US-3 |
| **REQ-05** | ปิดงานพร้อมบันทึกอะไหล่ที่ใช้ได้ (ไม่ใช้อะไหล่ก็ปิดได้) | ปิดงานพร้อมอะไหล่ 2 รายการ → ยอดคงเหลือของทั้งสองลดลงตามจำนวน | US-4 |
| **REQ-06** | เบิกอะไหล่เกินยอดคงเหลือไม่ได้ | เบิกเกินยอด ต้องได้ `409` และยอดคงเหลือ**ไม่เปลี่ยน** | US-4, US-7 |
| **REQ-07** | ทุกการเคลื่อนไหวของอะไหล่ถูกบันทึกไว้ย้อนดูได้ | `GET /api/parts/{id}/moves` แสดงรายการเบิก/รับเข้าเรียงตามเวลา | US-4 |
| **REQ-08** | หน้าสรุปแสดงจำนวนใบแจ้งซ่อมแยกตามสถานะ | `GET /api/dashboard` คืนจำนวนครบทั้ง 4 สถานะ ตรงกับที่นับจากฐานข้อมูล | US-5 |
| **REQ-09** | หน้าสรุปชี้งานที่ค้างเกินกำหนด | ใบที่เปิดเกิน `sla_days` ของความเร่งด่วนนั้น ปรากฏในรายการ `overdue` | US-5 |
| **REQ-10** | ยืมครุภัณฑ์ที่ยังไม่ถูกคืน ไม่ได้ | ยืมชิ้นที่มีสัญญายืมค้างอยู่ ต้องได้ `409` | US-6 |
| **REQ-11** | ครุภัณฑ์ที่มีใบแจ้งซ่อมค้างอยู่ ยืมไม่ได้ | ยืมชิ้นที่มีใบซ่อมสถานะยังไม่ `DONE` ต้องได้ `409` | US-6 |
| **REQ-12** | อะไหล่ที่เหลือต่ำกว่าจุดสั่งซื้อถูกทำเครื่องหมายเตือน | อะไหล่ที่ `qty_on_hand < reorder_point` ปรากฏในรายการเตือนของหน้าสรุป | US-7 |

### ข้อกำหนดที่ไม่ใช่ฟังก์ชัน (มาจากข้อจำกัดของลูกค้า)

| REQ | ข้อกำหนด | เกณฑ์ผ่าน |
|---|---|---|
| **NFR-1** | ติดตั้งบนเครื่องใหม่ได้ด้วยคำสั่งเดียว | `docker compose up -d` แล้วระบบพร้อมใช้งาน โดยไม่ต้องติดตั้ง Python/Node/Postgres บนเครื่อง |
| **NFR-2** | ข้อมูลไม่หายเมื่อ restart หรือสร้าง container ใหม่ | ลบ container ทั้งหมดแล้วสร้างใหม่ ข้อมูลเดิมยังอยู่ครบ |
| **NFR-3** | ฐานข้อมูลเข้าถึงจากภายนอกเครื่องไม่ได้ | ไม่มีการ publish พอร์ตของฐานข้อมูลออกจากเครื่อง |

## 3. ขอบเขต — สิ่งที่ **ไม่** ทำในเวอร์ชันนี้

ลูกค้าพูดเองว่ายังไม่ต้องการ : ระบบล็อกอิน · แจ้งเตือนเข้าไลน์ · แอปมือถือ
เพิ่มเติมจากทีมพัฒนา : รายงานส่งออก Excel · ระบบอนุมัติหลายชั้น · การจองล่วงหน้าเป็นช่วงวันที่

> ✍️ **การเขียนขอบเขตให้ชัดคือส่วนหนึ่งของการเก็บ requirements** — ของที่ไม่ได้เขียนว่า "ไม่ทำ"
> มักกลายเป็นสิ่งที่ลูกค้าคิดว่าจะได้

## 4. ระบบที่จะสร้าง

จาก REQ ทั้งหมดข้างบน สรุปได้เป็น 3 ส่วนงาน และ 5 ตาราง

| ส่วนงาน | REQ ที่รับผิดชอบ | ตาราง |
|---|---|---|
| แจ้งซ่อม | REQ-01 … REQ-04, REQ-08, REQ-09 | `assets`, `tickets` |
| ยืม-คืนครุภัณฑ์ | REQ-10, REQ-11 | `loans` |
| คลังอะไหล่ | REQ-05 … REQ-07, REQ-12 | `parts`, `stock_moves` |

**สิ่งที่ต้อง deploy** : หน้าเว็บ (`web`) · บริการเบื้องหลัง (`api`) · ฐานข้อมูล (`db`) — สามกล่อง

## 5. แล้ว Docker ที่เรียนมาเข้ามาตรงไหน

**นี่คือแกนของทั้งชุดแล็บ** — เราไม่ได้เรียนเครื่องมือใหม่ แต่เอาของเดิมมาทำให้ระบบนี้ขึ้นจริง

| แล็บ | โจทย์จากลูกค้าที่ทำให้เป็นจริง | เครื่องมือที่**เคยเรียนแล้ว** |
|---|---|---|
| **LAB 1** | NFR-2 ข้อมูลห้ามหาย · ยกฐานข้อมูลขึ้นตาม 5 ตาราง | `docker run` · `logs` · `exec` · `-v` volume · `-e` env |
| **LAB 2** | REQ-01…REQ-12 ทำงานได้ · สร้าง image ของ `api` | Dockerfile · build context · layer cache · `.dockerignore` · `EXPOSE` vs `-p` |
| **LAB 3** | หัวหน้าสำนักงานเปิดหน้าเว็บแล้วเห็นงานทั้งหมด · สร้าง image ของ `web` | multi-stage · `ARG` vs `ENV` · `CMD` exec form |
| **LAB 4** | NFR-3 ฐานข้อมูลห้ามเข้าถึงจากภายนอก · ให้ 3 กล่องคุยกัน | user-defined network · เรียกกันด้วย**ชื่อ** · ไม่ publish พอร์ต db |
| **LAB 5** | NFR-1 ติดตั้งด้วยคำสั่งเดียว · ส่งมอบให้ลูกค้า | `compose.yaml` · `healthcheck` · named volume · `tag` · `push` |

> 🎯 จบชุดนี้ผู้เรียนจะตอบได้ว่า **"ข้อจำกัดทางธุรกิจข้อไหน ทำให้ต้องเลือกเทคนิค Docker ตัวไหน"**
> ซึ่งเป็นคนละเรื่องกับการท่องคำสั่ง
