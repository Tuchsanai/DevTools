บท 008 PersistentVolume และ PVC — ทฤษฎีละเอียด: ปัญหาข้อมูลหาย (emptyDir ผูกอายุ Pod), ประเภท volume (emptyDir, hostPath, configMap/secret แบบแนวคิด, persistentVolumeClaim, ephemeral), PV vs PVC vs StorageClass (แยกบทบาทผู้ดูแลคลัสเตอร์/นักพัฒนา), static provisioning (PV hostPath/local + PVC + การ bind, storageClassName: "" , claimRef), dynamic provisioning (StorageClass, provisioner, default class), accessModes (RWO/ROX/RWX/RWOP) และความจริงของ local-path, capacity/requests, volumeMode, binding และสถานะ Pending/Bound/Released/Available/Failed, volumeBindingMode WaitForFirstConsumer vs Immediate, reclaimPolicy Delete vs Retain (และ Recycle เลิกใช้), finalizers kubernetes.io/pvc-protection / pv-protection, การขยาย PVC (allowVolumeExpansion), subPath, readOnly, fsGroup/สิทธิ์ไฟล์ (postgres uid 70), ข้อมูลผูก node กับ local storage (node ล่ม → Pod ย้ายไม่ได้ ต่อจากบท 003), ResourceQuota ของ storage (ต่อบท 004), snapshot/backup ปูทาง, CSI แนวคิด, ตารางสรุป. LAB 9–11 ข้อจากง่ายไปยาก. LAB สุดท้าย: "ร้านน้องส้มจำได้แล้ว" — แก้ db ของบท 007 ให้ใช้ PVC (Deployment db replicas 1 + strategy Recreate + PVC จาก StorageClass standard), ลบ Pod db / rollout restart db / ลบ Deployment db แล้ว apply ใหม่ → ออเดอร์ยังอยู่, ลบ PVC → ข้อมูลหายจริง (reclaimPolicy Delete), ทดลอง Retain, ทดลองว่า scale db เป็น 2 แล้วปัญหาอะไร (RWO/Multi-Attach หรือสองตัวเขียนโฟลเดอร์เดียว — ยืนยันผลจริง) → ปูทาง StatefulSet; ใช้แอปจากบท 007 (คัดลอกมาไว้ในบท) อาจทำ 1.4 ใหม่ถ้าจำเป็นแต่ไม่บังคับ
บท 009 StatefulSet — ทฤษฎีละเอียด: ทำไม Deployment ไม่พอสำหรับฐานข้อมูล/ระบบ stateful, StatefulSet คุณสมบัติ (ชื่อคงที่ <sts>-0..N, ลำดับสร้าง/ลบ OrderedReady vs Parallel, headless Service + DNS ต่อ Pod <pod>.<svc>.<ns>.svc.cluster.local, serviceName, volumeClaimTemplates → PVC ต่อ Pod data-<sts>-N, PVC ไม่ถูกลบตอน scale down/ลบ sts — persistentVolumeClaimRetentionPolicy whenDeleted/whenScaled), updateStrategy RollingUpdate (ลำดับย้อนกลับ, partition สำหรับ canary) vs OnDelete, minReadySeconds, podManagementPolicy, ตอนนี้ replicas หลายตัวไม่ได้แปลว่าข้อมูล replicate อัตโนมัติ (แอปต้องจัดการเอง เช่น postgres streaming replication / operator ปูทาง), StatefulSet กับ node ล่ม (Pod ไม่ถูกสร้างที่ node อื่นทันที — at-most-one semantics, force delete อันตราย), เทียบ Deployment vs StatefulSet vs DaemonSet (แนวคิด), แนวปฏิบัติ. LAB 9–11 ข้อ. LAB สุดท้าย: "ร้านน้องส้มแบบโปรดักชัน: db เป็น StatefulSet" — postgres StatefulSet (som-db-0) + headless Service + volumeClaimTemplates, web Deployment ต่อ DB ผ่านชื่อคงที่ (som-db-0.som-db หรือ Service ปกติ), ลบ som-db-0 → กลับมาชื่อเดิม PVC เดิม ข้อมูลเดิม, rolling update db (เช่นเปลี่ยน resources/annotation หรือ minor tag ที่มีจริง) ข้อมูลอยู่, ลบ StatefulSet แล้ว apply ใหม่ PVC เดิมกลับมาผูก ออเดอร์ยังอยู่, scale เป็น 3 เห็น PVC แยกต่อ Pod และอธิบายว่าไม่ได้ replicate (ถ้าทำ read replica ด้วย streaming replication ได้ง่ายและเสถียรให้เป็น LAB เสริมพร้อมยืนยันจริง ไม่บังคับ), ปิดบทปูทาง ConfigMap/Secret (รหัสผ่านใน YAML), Ingress, HPA
- เรื่องเล่าน้องส้มต่อเนื่อง: บท 008 ปิดด้วยปัญหาที่บท 009 แก้ อุปมาเดิม (container=ตู้สินค้า, Pod=กล่องใส teal มีป้าย IP, Node=เรือ, Control Plane=หอบังคับการ, Namespace=โซนทาสี, ReplicaSet=หุ่นยนต์หัวหน้ากะ, Deployment=หุ่นยนต์ผู้จัดการ, Service=ประภาคาร/เคาน์เตอร์, EndpointSlice=รายชื่อบูธ) เพิ่มอุปมาใหม่ที่สอดคล้อง เช่น PV=ตู้เซฟ/ห้องเก็บของบนเรือ, PVC=ใบเบิกตู้เซฟ, StorageClass=บริษัทรับทำตู้เซฟอัตโนมัติ, bind=กุญแจคู่, reclaimPolicy=ทิ้ง/เก็บตู้เมื่อคืนใบเบิก, StatefulSet=หัวหน้ากะที่ตั้งชื่อบูธตามลำดับเลขและแต่ละบูธมีตู้เซฟประจำตัว, headless Service=สมุดรายชื่อที่บอกเลขบูธตรง ๆ
