สิ่งที่ต้องตรวจสอบและตัดสินใจก่อนวางแผน (บันทึกใน plan.md พร้อมแหล่งอ้างอิง WebSearch/WebFetch จากแหล่งทางการ helm.sh, github helm/helm, artifacthub):
1) Helm 4 (v4.x) ต่างจาก Helm 3 อย่างไรที่กระทบการสอน: server-side apply เป็นค่าเริ่มต้นหรือไม่, ระบบ plugin, chart API v2/v3, คำสั่ง/flag ที่เปลี่ยน (เช่น --atomic → ?, --wait, helm upgrade --install, helm show, helm get, helm history, helm rollback, helm test, helm template, helm lint, helm package, helm push/pull OCI, helm dependency) ทดลองจริงด้วย helm v4.3.0 ใน image ว่าคำสั่งที่จะสอนใช้ได้จริงและ output เป็นอย่างไร
2) chart ภายนอกที่ใช้ใน LAB: Traefik (repo https://traefik.github.io/charts หรือ OCI) และ metrics-server (https://kubernetes-sigs.github.io/metrics-server/) — เลือกเวอร์ชัน chart ที่ pin แล้วให้ได้ app v3.7.13 / v0.9.0 ตรงกับบทก่อน (ถ้าไม่มี ให้ใช้เวอร์ชันใกล้สุดและบันทึก), ทดสอบติดตั้งด้วย values ที่ทำให้ได้ผลเหมือน static manifest บท 012/013 (NodePort 30080/30081/30082, flags ทั้ง 3, IngressClass traefik default, --kubelet-insecure-tls) และเทียบ helm get manifest กับ static manifest เดิม; ทางย้ายจาก static manifest ไป Helm (ต้องลบของเดิมก่อน หรือ adopt ด้วย label/annotation meta.helm.sh/release-name — ทดสอบจริงว่า Helm 4 adopt ได้หรือ error อะไร); ห้ามใช้ Bitnami chart/image (ตรวจสถานะ Bitnami 2025 แล้วอธิบายสั้น ๆ ในทฤษฎีว่าทำไมต้องระวังแหล่ง chart/image)
3) chart ของร้านเอง: helm create แล้วปรับเป็นร้าน som-shop (web Deployment + Service + Ingress + HPA + ConfigMap + Secret + db StatefulSet + Service headless) values.yaml เปิด/ปิดได้ (hpa.enabled, ingress.enabled, db.enabled ฯลฯ), _helpers.tpl, NOTES.txt, values.schema.json (ตรวจว่ายังรองรับ), helm test (Pod เช็ก /api/health), hook (pre-install/pre-upgrade สำหรับ seed หรือ post-install job — ทดสอบ), lookup/required/default/toYaml/nindent/include/range/if, values ต่อ environment (values-dev.yaml / values-prod.yaml หรือ --set), upgrade เปลี่ยน image 1.7 → 1.8 (ถ้าจะทำรุ่น 1.8 ให้เป็นการเปลี่ยนเล็กน้อยเช่นป้ายเวอร์ชัน/ธีม และ build เป็น tag ใหม่) แล้ว rollback, revision history, ข้อควรระวัง secret ใน values/release secret (Helm เก็บ release ใน Secret type helm.sh/release.v1 — base64+gzip ถอดได้ สาธิต), PVC ของ StatefulSet ไม่ถูกลบเมื่อ uninstall (ต่อบท 009), helm uninstall --keep-history
4) OCI: helm package + helm push ไป registry:2 ในคลัสเตอร์หรือใน container ทดลอง แล้ว helm install oci://… (ต่อบท 011 imagePullSecrets) — ทดสอบว่าทำได้ง่ายพอสำหรับ LAB (ถ้ายุ่งเกินให้เป็น LAB เสริม)
- ทฤษฎีละเอียด: ปัญหาไฟล์ YAML เยอะ/ค่าซ้ำ/หลาย environment, Helm คืออะไร (package manager), chart/release/revision/repository/values, Helm 3→4 ไม่มี Tiller (ประวัติ v2), โครงสร้าง chart (Chart.yaml apiVersion v2, values.yaml, templates/, _helpers.tpl, NOTES.txt, charts/, crds/, values.schema.json), Go template + Sprig ขั้นพื้นฐาน (., .Values, .Release, .Chart, include, toYaml, nindent, quote, default, required, if/range/with), ลำดับความสำคัญของ values (default < -f file < --set), การ render (helm template, --dry-run=server, --debug), lifecycle install/upgrade/rollback/uninstall, revision เก็บใน Secret, hooks และ helm test, dependencies (Chart.yaml dependencies, helm dependency update), repository แบบ HTTP vs OCI, Artifact Hub, ความปลอดภัย (ตรวจแหล่ง chart, pin เวอร์ชัน, อ่าน values ก่อนติดตั้ง, ไม่ใส่ secret จริงใน values ที่ commit), เทียบ Helm vs Kustomize vs static manifest, ปูทาง GitOps (Argo CD/Flux อ่าน Helm chart), ตารางคำสั่งที่ใช้บ่อย
- LAB 10–12 ข้อจากง่ายไปยาก ทุกข้อทดสอบจริง เช่น ตรวจ helm version + repo add/search/show → ติดตั้ง chart ง่าย ๆ (เช่น podinfo หรือ chart ที่ดึงได้และเสถียร) → values/--set/-f + helm get values/manifest → upgrade/history/rollback → helm template/lint/--dry-run debug error ของ template → helm create chart แรก → template functions (if/range/include/toYaml) → values ต่อ environment → hook + helm test → แทน static manifest ด้วย chart Traefik + metrics-server (เทียบผล, ทางย้าย) → package + OCI registry (ถ้าเหมาะ) → LAB สุดท้าย
- LAB สุดท้าย (แนะนำ ปรับได้): "ร้านน้องส้มพร้อมส่ง: ติดตั้งทั้งร้านด้วยคำสั่งเดียว" — chart som-shop (โฟลเดอร์ 02_LAB/charts/som-shop) ติดตั้ง dev และ prod คนละ namespace/release ด้วย values ต่างกัน (เช่น dev: replicas 1 ไม่มี HPA ชื่อร้านมีคำว่า dev; prod: HPA min 2 max 6, ingress shop.localhost TLS) → upgrade prod เป็นรุ่นใหม่ระหว่างยิง curl วน err=0 → rollback → helm uninstall dev (PVC ค้าง อธิบาย) → ปิดบทปูทาง GitOps (Argo CD/Flux), Kustomize, operator; ระบุผลที่ต้องเห็นและจุดที่ต้องยืนยัน (Helm 4 server-side apply conflict กับของที่ kubectl apply ไว้, เวลา install ทั้งร้าน, rollback เปลี่ยน revision เลขอะไร)
- เรื่องเล่าน้องส้มต่อเนื่อง: อุปมาเดิม (container=ตู้สินค้า, Pod=กล่องใส teal/บูธ, Node=เรือ, Control Plane=หอบังคับการ, Namespace=โซนทาสี, Deployment=หุ่นยนต์ผู้จัดการ, Service=ประภาคาร/เคาน์เตอร์, PV/PVC=ตู้เซฟ, StatefulSet=บูธเลขประจำ, ConfigMap=กระดานประกาศ, Secret=ซองปิดผนึก, Ingress=ประตูหน้าท่าเรือ + Traefik=หุ่นยนต์ต้อนรับเสื้อกั๊ก teal, metrics-server=เจ้าหน้าที่จดมิเตอร์, HPA=หุ่นยนต์ผู้ช่วยผู้จัดการดูมิเตอร์) เพิ่มอุปมาใหม่ เช่น chart=ชุดแฟรนไชส์ร้านสำเร็จรูป (กล่องพร้อมคู่มือ), values.yaml=ใบสั่งปรับแต่งร้าน (สี ชื่อ จำนวนบูธ), templates=แม่พิมพ์ป้าย/บูธที่เว้นช่องให้เติม, release=ร้านสาขาที่เปิดจริงจากชุดแฟรนไชส์, revision=สมุดบันทึกการปรับปรุงร้าน, repository/Artifact Hub=แคตตาล็อกแฟรนไชส์, helm (คำสั่ง)=หุ่นยนต์ผู้รับเหมาติดตั้งร้าน, hook=ขั้นตอนพิเศษก่อน/หลังเปิดร้าน, helm test=ผู้ตรวจรับร้าน, OCI registry=โกดังเก็บชุดแฟรนไชส์
