สิ่งที่ต้องตรวจสอบและตัดสินใจก่อนวางแผน (บันทึกเหตุผลใน plan.md):
1) สถานะ ingress-nginx ณ ปัจจุบัน (ต.ค. 2026): มีประกาศ retirement/สิ้นสุดการดูแลราวมีนาคม 2026 — ตรวจด้วย WebSearch/WebFetch จากแหล่งทางการ (kubernetes.io blog, github kubernetes/ingress-nginx) แล้วเลือก controller สำหรับ LAB ที่ยังดูแลอยู่และติดตั้งง่ายบน kind ด้วย manifest/คำสั่งที่ pin เวอร์ชัน (เช่น Traefik, HAProxy Ingress, NGINX Gateway/F5 NGINX Ingress Controller, Contour, หรือ ingress-nginx เวอร์ชันสุดท้ายถ้ายังเหมาะแก่การสอนพร้อมคำเตือน) — สอนทรัพยากร Ingress (networking.k8s.io/v1) ที่เป็นมาตรฐาน และ IngressClass; ถ้า controller ใดต้องใช้ annotation เฉพาะ ให้แยกให้ชัดว่าส่วนไหนเป็นมาตรฐาน ส่วนไหนเฉพาะ controller
2) วิธีที่นักศึกษาเข้าถึงด้วยชื่อโฮสต์จาก browser บนเครื่องตัวเองโดยไม่ต้องแก้ไฟล์ hosts: ทดสอบว่า *.localhost (เช่น http://shop.localhost:30080) ถูก resolve เป็น 127.0.0.1 ใน Chromium (Playwright บนเครื่องนี้ทดสอบเทียบได้กับ gateway โดยใช้ --host-resolver-rules หรือทดสอบตรรกะ Host header ด้วย curl -H 'Host: shop.localhost' และ curl --resolve) และวิธีสำรอง (curl -H Host, แก้ hosts) ให้ระบุผลจริง
3) image ของ controller ดึงได้จาก registry จริง (หรือต้อง kind load) เวลาติดตั้งจริง
- ทฤษฎีละเอียด: ทำไมต้องมี Ingress (NodePort หลายพอร์ต/LoadBalancer หลายตัว), L4 vs L7, Ingress resource vs Ingress controller, IngressClass + default class, rules: host/path/pathType (Prefix, Exact, ImplementationSpecific — พฤติกรรมจริงเช่น /api vs /api/ vs /apix), defaultBackend, หลาย host หลาย path (fan-out, name-based virtual hosting), backend service port name/number, TLS ที่ Ingress (spec.tls + Secret kubernetes.io/tls ต่อจากบท 011, SNI, redirect HTTP→HTTPS ตามที่ controller ทำ), annotation เฉพาะ controller (rewrite, rate limit ฯลฯ เท่าที่ controller ที่เลือกรองรับ แบบสั้น), ingress กับ Service ClusterIP (ไม่ต้องเป็น NodePort แล้ว), การ debug (describe ingress, events, log ของ controller, 404 จาก default backend, 503 เมื่อ endpoints ว่าง), ความสัมพันธ์กับ readiness/rolling update (ไม่มี downtime ผ่าน Ingress), canary/weight (ถ้า controller รองรับง่าย — ทฤษฎีหรือ LAB เสริม), ข้อจำกัดของ Ingress และ Gateway API (HTTPRoute, Gateway, GatewayClass) แบบปูทาง, ingress-nginx retirement, แนวปฏิบัติ, ตารางเปรียบเทียบ NodePort/LoadBalancer/Ingress/Gateway
- LAB 9–11 ข้อจากง่ายไปยาก ทุกข้อทดสอบจริง เช่น ติดตั้ง controller + IngressClass → Ingress แรก (host เดียว) → path-based fan-out (เมนู/api/admin เป็น Service คนละตัว) → host-based (shop.localhost / admin.localhost / ฯลฯ) → pathType ต่างกัน → defaultBackend/404/503 debug → TLS ด้วย Secret (cert self-signed หลายชื่อหรือ wildcard) → redirect HTTPS → annotation เฉพาะ controller (เช่น rewrite หรือ basic auth จาก Secret ถ้าทำได้ — ต่อบท 011) → rolling update ผ่าน Ingress ระหว่าง curl วนแล้ว err=0 → LAB สุดท้าย
- LAB สุดท้าย (แนะนำ ปรับได้): "ร้านน้องส้มมีหน้าร้านเดียวด้วยชื่อโดเมน" — ใช้ร้านจากบท 011 (คัดลอกแอป/manifest มาไว้ในบทนี้ som-shop-v8) เปลี่ยน Service web เป็น ClusterIP, เพิ่ม Ingress: shop.localhost → ร้าน (web), shop.localhost/admin หรือ admin.localhost → หน้าแอดมิน/เมนูง่าย ๆ (เช่น nginx ConfigMap จากบท 010 หรือ endpoint ของแอป) ที่ป้องกันด้วย basic auth (ถ้า controller รองรับ), TLS ที่ Ingress ด้วย Secret som-tls (ย้ายจาก nginx sidecar/HTTPS NodePort ของบท 011 มาไว้ที่ Ingress), HTTP → HTTPS redirect, rolling update ร้านผ่าน Ingress ไม่มี error, ปิดบทปูทาง HPA (ร้านคนเยอะ), Helm (ติดตั้ง controller/ร้านเป็นแพ็กเกจ), Gateway API
- เรื่องเล่าน้องส้มต่อเนื่อง: อุปมาเดิม (container=ตู้สินค้า, Pod=กล่องใส teal มีป้าย IP, Node=เรือ, Control Plane=หอบังคับการ, Namespace=โซนทาสี, ReplicaSet/Deployment=หุ่นยนต์หัวหน้ากะ/ผู้จัดการ, Service=ประภาคาร/เคาน์เตอร์, PV/PVC=ตู้เซฟ/ใบเบิก, StatefulSet=บูธเลขประจำ, ConfigMap=กระดานประกาศ, Secret=ซองปิดผนึก/ตู้กุญแจ) เพิ่มอุปมาใหม่ เช่น Ingress=ประตูหน้าท่าเรือ/โถงต้อนรับหลักที่มีป้ายบอกทาง (กฎ host/path), Ingress controller=พนักงานต้อนรับที่อ่านป้ายแล้วพาลูกค้าไปเคาน์เตอร์ (ไม่มีพนักงาน ป้ายก็ไม่ทำงาน), IngressClass=ชุดยูนิฟอร์มบอกว่าพนักงานบริษัทไหนรับผิดชอบป้ายนี้, TLS=ประตูกระจกนิรภัยมีตราประทับ, defaultBackend=โต๊ะของหาย/ประตูผิด (404), Gateway API=อาคารผู้โดยสารรุ่นใหม่
