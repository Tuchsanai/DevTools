# แผนปรับปรุง LAB: Jenkins สั่ง Build → Push → Pull → Deploy

## แนวคิดหลัก

ผู้เรียนเริ่มงานจาก **Jenkins Pipeline** แล้ว Jenkins ส่งคำสั่งผ่าน **SSH ไปยัง devtools** ซึ่งมี Docker และซอร์สโค้ดร้านอาหารแมวอยู่แล้ว

**Jenkins เป็นผู้สั่งงาน ส่วน devtools เป็นผู้ประมวลผลคำสั่ง Docker** โดยไม่ให้ผู้เรียนเริ่มจากการ build ด้วยมือบน devtools

## 1. เริ่มด้วย System Architecture

- แสดงผู้เรียน, Jenkins container, devtools, Docker daemon, Docker Hub และ container ร้านอาหารแมว
- แยกลูกศรการส่งคำสั่ง SSH ออกจากเส้นทาง push/pull image
- ระบุว่าซอร์สโค้ดอยู่ที่ไหน และ container ร้านทำงานบน Docker daemon ตัวใด
- ตรวจโครงสร้างจริงก่อนวาด เพื่ออธิบายความสัมพันธ์ของ container ได้ถูกต้อง

## 2. ให้ผู้เรียนเข้าใจสภาพแวดล้อม Jenkins

- เข้าหน้าเว็บ Jenkins
- ตรวจจากภายใน Jenkins container ว่าไม่มี Docker CLI แต่มี SSH client
- อธิบายเหตุผลที่ Jenkins ต้องส่งคำสั่งไปยัง devtools
- ยืนยันว่า devtools มี Docker และไฟล์ร้านพร้อมใช้งาน

## 3. อธิบายเครือข่ายและตั้งค่า Credentials

- อธิบายว่า Jenkins ติดต่อ devtools ผ่านชื่อเครื่องและพอร์ตใด
- เตรียม SSH key สำหรับ Jenkins เข้า devtools
- เก็บ private key ใน Jenkins Credentials และ public key ใน `authorized_keys` ฝั่ง devtools
- เก็บ Docker Hub credential แยกจาก SSH credential
- ทดสอบการเชื่อมต่อจาก Jenkins ก่อนเริ่ม build

> แนวทางนี้ต้องตั้งค่า SSH credential เพื่อให้ Pipeline เชื่อมต่อได้โดยไม่ต้องป้อนรหัสผ่านระหว่างทำงาน

## 4. แนะนำซอร์สโค้ดร้านและ Dockerfile

- อธิบายโครงสร้างไฟล์ร้านอาหารแมว
- ระบุ build context และตำแหน่ง Dockerfile บน devtools
- อธิบายขั้นติดตั้ง dependencies, build เว็บไซต์, เริ่มแอป และตรวจสุขภาพ
- ย้ายการ build ด้วยมือบน devtools ออกจากเส้นทางหลัก ให้การ build ครั้งแรกเริ่มจาก Jenkins

## 5. อธิบาย Jenkinsfile ก่อนรัน

แยกอธิบายทีละส่วน ได้แก่ parameters, environment, credentials และ stages พร้อมระบุให้ชัดว่า:

- โค้ดส่วนใดทำงานบน Jenkins
- คำสั่งใดเปิด SSH ไปยัง devtools
- คำสั่ง Docker ใดทำงานบน devtools
- ตัวแปรถูกแทนค่าฝั่งใด และ credential ถูกใช้อย่างไร

จากนั้นจึงให้ Jenkinsfile ฉบับสมบูรณ์ที่ผู้เรียนใช้รันได้

## 6. จัดการทดลองตามลำดับ Pipeline

| ขั้นตอน | Jenkins สั่งให้ devtools ทำอะไร | ผลที่ต้องตรวจ |
|---|---|---|
| Connect | ตรวจเครื่องปลายทางและ Docker | SSH สำเร็จและเป็นเครื่องที่ถูกต้อง |
| Build | สร้าง image จากซอร์สโค้ดร้าน | Build สำเร็จและมี tag ที่กำหนด |
| Test | รัน container ทดสอบ | สถานะเป็น `healthy` |
| Push | ส่ง image ขึ้น Docker Hub | Push สำเร็จและมี digest |
| Pull | ดึง image จาก Docker Hub ลง devtools | มีหลักฐานการ pull และ digest ตรงกัน |
| Deploy | รัน container ร้านจาก image ที่ pull | เปิดเว็บไซต์ได้และแสดงเวอร์ชันถูกต้อง |

**ทุกขั้นเริ่มจาก Pipeline บน Jenkins** รวมถึงการสั่ง pull และ deploy บน devtools

## 7. เขียนแต่ละการทดลองให้ตามได้ง่าย

ใช้รูปแบบเดียวกันตลอดบทเรียน:

1. **เป้าหมาย:** ต้องการเรียนรู้อะไร
2. **ขั้นตอน:** ทำที่หน้าจอหรือเครื่องใด
3. **คำอธิบาย:** คำสั่งหรือโค้ดทำงานอย่างไร
4. **ผลที่ควรเห็น:** ตรวจจากจุดใด
5. **ข้อสรุป:** ผลนั้นพิสูจน์อะไร

ใช้ Computer Use ทดลองและจับภาพ Jenkins, Console Output, Docker Hub และหน้าร้านประกอบขั้นตอน

## 8. ทดลองใหม่และเก็บหลักฐานให้สอดคล้องกัน

- ตรวจสถานะระบบเดิมก่อนเริ่ม
- ทดลองตั้งแต่ Jenkins สั่ง build จนเปิดร้านได้
- เก็บภาพและผลจริงชุดใหม่ โดยให้เวอร์ชัน หมายเลข build และ digest สัมพันธ์กัน
- วางเรื่อง cache, ออกเวอร์ชันใหม่ และ rollback ไว้หลังเส้นทางหลัก

## 9. ปิดบทเรียนด้วย Checklist

- [ ] Devtools pull image กลับมาได้
- [ ] Container ร้านมีสถานะ `healthy`
- [ ] เว็บไซต์แสดงเวอร์ชันและ build ที่ถูกต้อง
- [ ] Jenkins ยังคงไม่มี Docker CLI
- [ ] ผู้เรียนอธิบายได้ว่าใครสั่งงาน และคำสั่งประมว

2. **Env**: `set -a && source /root/workspace/DGX_2024/.env && set +a`
3. **Workdir**: ทำงานทั้งหมดบน remote ที่ `/root/workspace/` เท่านั้น
4. **Web/Browser**: รันบน remote เสมอ
   - ตรวจ Playwright + Chromium ถ้ายังไม่มีให้ติดตั้ง โดยใช้ `uv` ก่อนถ้ามี (`command -v uv`):

     - ไม่มี uv: `pip install playwright && playwright install --with-deps chromium`
   - หา path Chromium ของ Playwright:
     `CHROME=$(find ~/.cache/ms-playwright -type f -name chrome | head -1)`

5. **Display WEB บน host ผ่าน SSH tunnel (1:1 ความละเอียดจริง, ภาพคมชัด)**:
   - remote (kill process เก่าก่อนถ้ามี: `pkill Xvfb; pkill x11vnc; pkill websockify`):
```bash
     Xvfb :99 -screen 0 1920x1080x24 -dpi 96 &
     x11vnc -display :99 -nopw -forever -shared -noxdamage -rfbport 5900 &
     websockify --web /usr/share/novnc 6080 localhost:5900 &
     DISPLAY=:99 $CHROME --no-sandbox --window-size=1920,1080 --start-maximized \
       --force-device-scale-factor=1 https://www.google.com/travel/flights &
```
   - host: `ssh -N -L 6080:localhost:6080 -p 22022 root@127.0.0.1`
   - host: ใช้ computer use เปิด
     `http://localhost:6080/vnc.html?autoconnect=true&resize=off&quality=9&compression=0`
     - `resize=off` = แสดงตามความละเอียดจริงของ remote ไม่ scale/ไม่ resize (ห้ามใช้ `resize=remote`)
     - `quality=9` = JPEG คุณภาพสูงสุด, `compression=0` = ไม่บีบอัด (localhost tunnel ไม่มีปัญหา bandwidth)
   - host: ต้องไม่มีการ scale ซ้ำ
