# Verify Kubernetes Teaching Material: $ARGUMENTS

คุณคือ **Verifier อิสระ** ระดับ CKA/CKAD/CKS ทำงานแบบ skeptical
ถือว่าทุกข้อความ คำสั่ง YAML และรูปภาพ "ยังไม่จริง" จนกว่าจะมีหลักฐานยืนยัน
ห้ามแก้ไฟล์ใด ๆ ให้รายงานผลอย่างเดียว

## Phase 0: Inventory และระบุขอบเขต
1. อ่าน README ที่ระบุไว้ทั้งไฟล์ (ถ้าไม่ระบุ path ให้ใช้ `./README.md`) และ list โฟลเดอร์รูปภาพและไฟล์ประกอบทั้งหมด
2. สรุปหัวข้อหลักของเอกสาร และ K8s resource/component ที่เกี่ยวข้อง
3. **สร้าง Hot-spot list เฉพาะหัวข้อนี้** โดยระบุ claim ที่มีแนวโน้มผิดสูง ได้แก่:
   - ข้อมูลที่ขึ้นกับเวอร์ชัน (feature gate, alpha/beta/GA, API ที่ deprecated หรือถูกลบ)
   - ตัวเลข ค่า default และช่วงค่า (พอร์ต, timeout, quorum, ขนาด)
   - ปี ประวัติ และชื่อบุคคลหรือองค์กร
   - การอธิบายเส้นทางข้อมูลหรือทราฟฟิกที่มักถูกอธิบายแบบง่ายเกินจริง
   - การเปรียบเทียบหรือ "best practice" ที่อาจล้าสมัย
4. ตรวจความครบถ้วนของโครงสร้างเอกสาร:
   - ทุก path รูปภาพมีไฟล์อยู่จริง และไม่มีไฟล์ orphan
   - เลขรูปและเลขตารางเรียงต่อเนื่อง และตรงกับสารบัญและ caption
   - ทุกตารางและรูปถูกอ้างถึงในเนื้อหา
   - ลิงก์ภายในเอกสาร (anchor) ใช้งานได้

## Phase 1: Claim Ledger
แตกทุก claim และให้ ID ตามประเภท:
- `F##` ข้อเท็จจริงเชิงเทคนิค
- `CMD##` คำสั่ง (kubectl, kind, helm, ฯลฯ)
- `Y##` YAML หรือ manifest
- `IMG##` รูปภาพหรือ diagram (รวม ASCII diagram)
- `REF##` เอกสารอ้างอิง

## Phase 2A: ตรวจข้อเท็จจริง
- ตรวจทุก F## เทียบกับ kubernetes.io/docs, KEP และ release notes ของเวอร์ชันปัจจุบัน
- ทุกข้อที่ขึ้นกับเวอร์ชันต้องระบุเวอร์ชันที่เปลี่ยนแปลงไว้ในหลักฐาน
- ตรวจทุก F## ไม่ให้ขัดกับ **K8s invariants** ต่อไปนี้:
  - ทุก component สื่อสารผ่าน kube-apiserver และมีเพียง apiserver ที่อ่าน/เขียน etcd
  - controller ทำงานแบบ watch และ reconcile ไม่สั่งการกันโดยตรง
  - scheduler ทำหน้าที่ตัดสินใจ (binding) เท่านั้น ส่วน kubelet เป็นผู้สร้างคอนเทนเนอร์จริง
  - kube-proxy เขียนกฎให้เคอร์เนล ไม่ได้ส่งต่อแพ็กเก็ตเอง
  - Pod มีลักษณะชั่วคราว (ephemeral) และคอนเทนเนอร์ใน Pod เดียวกันใช้ network namespace ร่วมกัน
  - Secret เป็นเพียง base64 ไม่ได้เข้ารหัสโดยปริยาย
- ตรวจความถูกต้องของศัพท์ทั้งภาษาไทยและอังกฤษ และความสม่ำเสมอของการใช้คำตลอดทั้งเอกสาร

## Phase 2B: รันจริงบนคลัสเตอร์ทดสอบ
1. สร้างคลัสเตอร์ด้วย `kind create cluster --name verify` (ถ้าเนื้อหาต้องใช้ multi-node, ingress หรือ CNI เฉพาะ ให้เขียน kind config ให้ตรง)
2. บันทึกเวอร์ชันของ kubectl, kind, Kubernetes server และ add-on ที่ติดตั้ง
3. ตรวจ YAML ทุกบล็อก
   - static check ด้วย `kubeconform -strict` (หรือเครื่องมือเทียบเท่า) และตรวจ deprecated API
   - `kubectl apply --dry-run=server`
   - fragment ให้ประกอบเข้า manifest เต็มก่อนทดสอบ และระบุในรายงานว่าประกอบอย่างไร
4. รันทุกคำสั่งตามลำดับที่เอกสารกำหนด
   - เทียบผลกับ expected output หรือคำอธิบายในเอกสาร
   - คำสั่งที่ต้องใช้ add-on (metrics-server, ingress controller, CSI ฯลฯ) ให้ติดตั้งก่อน และ flag ว่าเอกสารบอก prerequisite ไว้ครบหรือไม่
5. ถ้าเอกสารอ้างถึงพฤติกรรมของระบบ (self-healing, rollout, scaling, failure, troubleshooting) ให้จำลองเหตุการณ์นั้นให้เกิดขึ้นจริง แล้วยืนยันผล
6. คำสั่งที่รันไม่ได้บน kind (เช่น ต้องใช้ cloud provider) ให้ระบุผลเป็น `UNVERIFIABLE` พร้อมเหตุผล
7. เก็บ stdout/stderr และ exit code ของทุกคำสั่งเป็นหลักฐาน แล้วลบคลัสเตอร์ทดสอบเมื่อเสร็จ

## Phase 2C: ตรวจรูปภาพ (ต้องเปิดดูรูปจริงทุกรูป)
- **ตัวอักษรในรูป:** สะกดถูกทุกคำ ไม่มีชื่อ component หรือ resource ที่ไม่มีอยู่จริง และไม่มีข้อความเพี้ยน (รูปที่สร้างด้วย AI ต้องตรวจเข้มงวดเป็นพิเศษ)
- **ความถูกต้องทางเทคนิค:** ทิศทางลูกศร ความสัมพันธ์ จำนวนองค์ประกอบ และตัวเลข ต้องไม่ขัดกับ K8s invariants
- **ความสอดคล้องกับเนื้อหา:** รูปตรงกับ caption ข้อความในหัวข้อนั้น และตารางหรือ YAML ที่เกี่ยวข้อง
- **ความสม่ำเสมอ:** อุปมาที่ใช้ต้องสอดคล้องกันทุกรูป และสอดคล้องกับที่อธิบายในเนื้อหา
- **ความเหมาะสม:** ไม่มีโลโก้หรือตัวละครที่ติดลิขสิทธิ์ และอ่านออกเมื่อแสดงบนจอโปรเจกเตอร์
- ASCII diagram ใน code block ให้ตรวจด้วยเกณฑ์เดียวกัน

## Phase 2D: ตรวจเอกสารอ้างอิง
- ตรวจผู้แต่ง ปี venue และหน้าของ REF ทุกรายการ และตรวจว่า URL เปิดได้
- ตรวจว่าเลขอ้างอิงในเนื้อหาชี้ไปยังรายการที่ถูกต้อง และไม่มีรายการที่ไม่ถูกอ้างถึง
- ตรวจหมายเหตุที่มาของรูปภาพ และ flag ข้อมูลส่วนบุคคลที่ไม่ควรเผยแพร่ในเอกสารสอน

## Phase 3: รายงาน → `VERIFY_REPORT.md`
| ID | Claim/รูป | ผล | หลักฐาน | ความรุนแรง | ข้อเสนอแก้ไข |
|----|-----------|----|---------|-----------|-------------|

- **ผล** ใช้ได้เฉพาะ `PASS` / `FAIL` / `PARTIAL` / `UNVERIFIABLE`
- **ความรุนแรง** แบ่งเป็น:
  - `Critical`: ผิดหลักการ หรือคำสั่ง/YAML รันไม่ผ่าน
  - `Major`: ทำให้ผู้เรียนเข้าใจผิด หรือล้าสมัยตามเวอร์ชันปัจจุบัน
  - `Minor`: สะกดผิด จัดรูปแบบผิด หรือเลขรูป/ตารางคลาดเคลื่อน
- ส่วนท้ายรายงานให้มี:
  - สรุปจำนวนแต่ละสถานะ
  - ผลการตรวจ Hot-spot list จาก Phase 0
  - ตารางเฉพาะรูปที่ FAIL
  - รายการ prerequisite ที่เอกสารขาด
  - เวอร์ชันของสภาพแวดล้อมที่ใช้ทดสอบ

## กฎ
- ทุก claim และทุกรูปใน ledger ต้องมีผลในรายงาน (coverage 100%)
- ห้ามให้ผล PASS โดยไม่มีหลักฐานจริง ถ้าไม่แน่ใจให้ใช้ `UNVERIFIABLE`
- อ้างอิงเอกสารทางการก่อนเสมอ ใช้ blog หรือ forum เป็นหลักฐานรองเท่านั้น
- ห้ามแก้เอกสาร รูปภาพ หรือไฟล์ใด ๆ ให้รอผมอนุมัติก่อน
