📸 ทฤษฎี ① — Commit = Snapshot ของทั้งโปรเจกต์

อ้างอิงสไลด์ 02_GIT.pdf หน้า 12–15 และ 37

มองโปรเจกต์เป็นเส้นเวลา: Initial Project → Add Code → More Code → … จุดที่เราบอก Git ให้จดจำไว้แต่ละจุด เรียกว่า commit

📸
Initial Project
commit #1
→
📸
Add Code
commit #2
→
📸
More Code
commit #3
  • commit ไม่ใช่การเซฟทีละไฟล์ — หนึ่ง commit เก็บการเปลี่ยนแปลงได้ทั้ง working directory เช่นแก้ program.py, index.html, style.css พร้อมกันก็รวมอยู่ใน commit เดียวได้ (สไลด์หน้า 15)
  • ทุก commit มี 3 อย่างเสมอ (สไลด์หน้า 37): hash เลขประจำตัว เช่น 678e366… · message คำอธิบายว่าทำอะไร · parent ตัวชี้กลับไป commit ก่อนหน้า
  • parent ทำให้ commit ต่อกันเป็นสายโซ่ประวัติ — นี่แหละคือรางของเครื่องย้อนเวลา เราจึงถอยกลับไป commit เก่าได้เสมอ (สไลด์หน้า 14)

🗺️ ทฤษฎี ② — สามพื้นที่ของ Git

อ้างอิงสไลด์ 02_GIT.pdf หน้า 17–31

ก่อนไฟล์จะกลายเป็น snapshot ถาวร มันเดินทางผ่าน 3 พื้นที่:

🖥️
Working Directory
โต๊ะทำงาน — ไฟล์จริงที่เราแก้
→git add
🧺
Staging Area
ตะกร้าเตรียมถ่ายรูป — เลือกเฉพาะไฟล์
→git commit
🗄️
Repository (.git/)
อัลบั้มถาวร — เก็บทุก snapshot
  • Working Directory — โฟลเดอร์จริงที่เราสร้าง/แก้ไฟล์ (สไลด์หน้า 18–20)
  • Staging Area — พื้นที่พักสำหรับ "เลือกเฉพาะไฟล์" ที่จะบันทึกใน commit ถัดไป ด้วย git add (สไลด์หน้า 21–23) — ประโยชน์จริง: แก้ 3 ไฟล์ แต่จะ commit แค่ 2 ไฟล์ก็ทำได้ ซึ่งเราจะได้ลองเองใน STEP 2
  • Repository — ฐานข้อมูลในโฟลเดอร์ .git/ ที่เก็บ snapshot ถาวรทุก commit ด้วย git commit (สไลด์หน้า 24–31)

สถานะของไฟล์ที่ git status รายงาน

ข้อความใน git statusสถานะความหมาย
Untracked filesuntrackedไฟล์ใหม่ที่ Git ยังไม่รู้จัก ยังไม่จับตาดู
Changes to be committedstagedเข้า Staging Area แล้ว รอถ่ายรูปใน commit ถัดไป
Changes not staged for commitmodifiedไฟล์ที่เคย commit ถูกแก้ แต่ยังไม่ได้ git add
nothing to commit, working tree cleancleanทุกอย่างถูกบันทึกครบแล้ว — สถานะที่อยากเห็นตอนจบวัน

STEP 1 — สร้าง repo แรก + commit แรก

สร้างโฟลเดอร์งาน แล้วประกาศให้ Git เริ่มจับตาดูด้วย git init:

mkdir git-lab
cd git-lab
git init
Expected Output
hint: Using 'master' as the name for the initial branch. This default branch name
hint: is subject to change. To configure the initial branch name to use in all
hint: of your new repositories, which will suppress this warning, call:
hint:
hint: 	git config --global init.defaultBranch <name>
hint:
hint: Names commonly chosen instead of 'master' are 'main', 'trunk' and
hint: 'development'. The just-created branch can be renamed via this command:
hint:
hint: 	git branch -m <name>
Initialized empty Git repository in /workspace/git-lab/.git/

🌿 master vs main — hint ยาว ๆ นี้บอกอะไรเรา?

อ้างอิงสไลด์ 02_GIT.pdf หน้า 43

  • branch เริ่มต้นของ Git ใช้ชื่อ master มาแต่เดิม แต่ GitHub เปลี่ยนธรรมเนียมชื่อ default branch เป็น main อย่างเป็นทางการแล้ว — repo ที่สร้างบนเว็บ GitHub ทุกวันนี้จึงชื่อ main
  • LAB นี้ทำงานในเครื่องตัวเองล้วน ๆ ชื่อ branch จึงยังไม่มีผลอะไร — ใช้ master ต่อได้เลย
  • แต่ LAB 01 เราจะ push ขึ้น GitHub — ถ้าปล่อย local เป็น master ส่วน GitHub เป็น main จะกลายเป็นคนละ branch คุยกันไม่เจอ → LAB 01 จะแก้ด้วย git branch -M main ตามที่ GitHub แนะนำ
💡 ถ้าเครื่องคุณเคยตั้ง git config --global init.defaultBranch main ไว้จาก LAB Configure (Week 1) — git init จะไม่แสดง hint นี้ และ branch จะชื่อ main ตั้งแต่แรก ซึ่งถูกต้องเช่นกัน (ทุกบรรทัดที่เหลือของ LAB จะเห็น On branch main แทน On branch master)

สร้างไฟล์ 3 ไฟล์ แล้วถาม "เข็มทิศ" ว่าเห็นอะไรบ้าง:

echo "Content for file 1" > file1.txt
echo "Content for file 2" > file2.txt
echo "Content for file 3" > file3.txt
git status
Expected Output
On branch master

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	file1.txt
	file2.txt
	file3.txt

nothing added to commit but untracked files present (use "git add" to track)

ทั้งสามไฟล์เป็น untracked (สีแดง) — Git เห็นว่ามีไฟล์ใหม่ แต่ยังไม่จับตาดูจนกว่าเราจะสั่ง git add:

git add file1.txt file2.txt file3.txt
git status
Expected Output
On branch master

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   file1.txt
	new file:   file2.txt
	new file:   file3.txt
💡 ทางลัดที่ใช้บ่อยในงานจริง: git add . = stage ทุกไฟล์ที่เปลี่ยนในโฟลเดอร์รวดเดียว (สไลด์หน้า 28) — ใน LAB นี้ตั้งใจ add ทีละไฟล์เพื่อให้เห็นชัดว่า Staging Area "เลือกได้" พอคล่องแล้วค่อยใช้ทางลัด

สามไฟล์ย้ายเข้า Staging Area แล้ว (สีเขียว · Changes to be committed) — ได้เวลากดชัตเตอร์ถ่าย snapshot แรก:

git commit -m "Initial commit with three files"
Expected Output
[master (root-commit) 678e366] Initial commit with three files
 3 files changed, 3 insertions(+)
 create mode 100644 file1.txt
 create mode 100644 file2.txt
 create mode 100644 file3.txt
📌 678e366 คือ commit hash — ของแต่ละคนจะไม่เหมือนกัน (Git คำนวณจากเนื้อหา + ชื่อผู้เขียน + เวลา) ส่วน root-commit = commit แรกสุดของ repo ที่ยังไม่มี parent

ตรวจสอบผลด้วยเข็มทิศ + สมุดประวัติ:

git status
git log
Expected Output
On branch master
nothing to commit, working tree clean

commit 678e3667ca4fd037059c249d2f2d1bfda0e2a13e
Author: somchai-dev <somchai.dev@example.com>
Date:   Tue Jul 14 04:27:03 2026 +0700

    Initial commit with three files
📌 hash / Author / Date ในเครื่องคุณจะเป็นของคุณเอง ไม่ตรงกับตัวอย่าง — สิ่งที่ต้องเหมือนคือโครงสร้างของ output

STEP 2 — แก้ 2 ไฟล์ แล้ว "เลือก" stage เฉพาะที่ต้องการ

เพิ่มเนื้อหาต่อท้ายไฟล์ (>> = append) เฉพาะ file1 กับ file2 — จงใจไม่แตะ file3:

echo "Additional content for file 1" >> file1.txt
echo "Additional content for file 2" >> file2.txt
git status
Expected Output
On branch master
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   file1.txt
	modified:   file2.txt

no changes added to commit (use "git add" and/or "git commit -a")

คราวนี้สถานะไม่ใช่ untracked แล้ว แต่เป็น modified — Git รู้จักไฟล์อยู่แล้ว และตรวจพบว่ามันต่างไปจาก snapshot ล่าสุด · สังเกตว่า file3.txt ไม่ถูกพูดถึงเลยเพราะเราไม่ได้แก้

stage เฉพาะสองไฟล์ที่แก้ แล้ว commit — นี่คือพลังของ Staging Area ที่เล่าไว้ในทฤษฎี ②:

git add file1.txt file2.txt
git commit -m "Updated file1 and file2"
git status
git log
Expected Output
[master bce79d5] Updated file1 and file2
 2 files changed, 2 insertions(+)

On branch master
nothing to commit, working tree clean

commit bce79d5014174e2659bdb75c6447276af43193fd
Author: somchai-dev <somchai.dev@example.com>
Date:   Tue Jul 14 04:27:03 2026 +0700

    Updated file1 and file2

Author: somchai-dev <somchai.dev@example.com>
Date:   Tue Jul 14 04:27:03 2026 +0700

    Initial commit with three files
📌 git log เรียง commit ใหม่สุดอยู่บนสุด — สายโซ่ประวัติของเรามี 2 ข้อแล้ว

📋 สรุป + Cheat Sheet

คำสั่งทำอะไร
git initเริ่มให้ Git จับตาดูโฟลเดอร์นี้ (สร้าง .git/)
git statusเข็มทิศ: ไฟล์ไหน untracked / modified / staged / clean
git add <file>ย้ายไฟล์เข้า Staging Area — เลือกเป็นรายไฟล์ได้
git commit -m "msg"ถ่าย snapshot จาก Staging เข้า Repository
git log · git log --onelineดูประวัติ commit — ใหม่สุดอยู่บนสุด
🔁 วงจรที่ต้องจำให้ขึ้นใจ: แก้ไฟล์ → git status → git add → git commit -m → git status / git log
10

✅ Checklist ก่อนไปต่อ

  • git status หลังสร้างไฟล์ใหม่ เห็น Untracked files ครบ 3 ไฟล์
  • git status หลัง git add เห็น Changes to be committed (สีเขียว)
  • commit สำเร็จ 3 ครั้ง และ git status ตอบ working tree clean หลัง commit ทุกครั้ง
  • STEP 2 stage เฉพาะ file1/file2 ได้ โดย file3 ไม่ติดเข้าไปใน commit ด้วย
  • git log --oneline แสดง 3 บรรทัด เรียงจากใหม่ → เก่า
  • อธิบายเส้นทาง Working Directory → Staging Area → Repository ให้เพื่อนฟังได้
  • บอกได้ว่าทำไม branch เริ่มต้นชื่อ master และทำไม GitHub ใช้ main

❓ คำถามทบทวน

  1. ไฟล์สถานะ untracked กับ modified ต่างกันอย่างไร? ใน LAB นี้เจอแต่ละแบบที่ STEP ไหน
  2. ทำไม Git ต้องมี Staging Area — commit ตรงจาก Working Directory เลยไม่ได้หรือ? ยกสถานการณ์ที่ staging ช่วยได้จริง
  3. ใน STEP 2 ถ้าเผลอสั่ง git add file3.txt ไปด้วย จะถอนออกจาก staging ด้วยคำสั่งอะไร? (คำใบ้: อ่าน output ของ git status — Git บอกเองทุกครั้ง)
