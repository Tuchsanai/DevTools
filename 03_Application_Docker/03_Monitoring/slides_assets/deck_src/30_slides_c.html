ออกแบบ dashboard ให้คนใช้จริง

dashboard ที่มี 40 panel = dashboard ที่ไม่มีใครดู

เรียงจากบนลงล่างตามลำดับการไล่ปัญหา

แถวบน : ผู้ใช้เจ็บไหม (RED — rate, error, p95)
แถวกลาง : service ไหนเป็นต้นเหตุ
แถวล่าง : ทรัพยากร (USE — CPU, RAM, disk)

คนเปิดดูจะได้กวาดตาจากบนลงล่างแล้วเจอคำตอบ

กฎเล็ก ๆ ที่ช่วยได้มาก

• 1 dashboard = 1 คำถาม อย่ายัดทุกอย่างไว้หน้าเดียว
• ตั้งหน่วยให้ถูก (percent · bytes(IEC) · seconds) อย่าปล่อยเป็นตัวเลขดิบ
• ใส่ threshold สี ให้เห็นว่า "เท่าไรถึงเรียกว่าแย่"
• ใช้ variable แทนการ copy dashboard ทีละ service
• เก็บ JSON ลง git เสมอ

ข้อควรจำจาก LAB 3 : dashboard ที่คลิกสร้างด้วยมือใน UI จะหายเมื่อ volume ถูกลบ และไม่มีประวัติว่าใครแก้อะไร
ในทางกลับกัน dashboard ที่ provision มาจากไฟล์จะแก้ใน UI ไม่ได้ (Grafana ตอบ Cannot save provisioned dashboard) — วิธีทำงานคือ แก้ที่ไฟล์ → commit → ให้ Grafana โหลดใหม่

ความปลอดภัยGrafana เปิด anonymous · Prometheus ไม่มี authปิด anonymous · ตั้งรหัสผ่าน admin จริง · ให้ทุก UI อยู่หลัง reverse proxy + TLS ไม่เปิดสู่อินเทอร์เน็ตตรง ๆ

ก้าวต่อไปหลังจากชุดนี้

metrics คือเสาแรก — เมื่อพร้อมแล้วค่อยต่อเสาที่เหลือ

Logs

เมื่อ metric บอกว่า "error พุ่งตอน 10:45" แต่ไม่บอกว่าทำไม → ถึงเวลาต่อ log

Loki ใช้แนวคิด label แบบเดียวกับ Prometheus จึงเรียนต่อได้ง่าย

Traces

เมื่อระบบมีหลาย service แล้ว "ช้าตรงไหน" ตอบไม่ได้จาก metric อีกต่อไป

Tempo / Jaeger + OpenTelemetry เป็นมาตรฐานกลางที่ควรเริ่มจากตรงนั้น

ขยายขนาด

เมื่อมีหลายเครื่อง หลายทีม

Service discovery (Docker / Kubernetes) แทน static_configs
Recording rules คำนวณล่วงหน้าให้ dashboard เร็วขึ้น
Federation / remote write รวมข้อมูลหลายที่

คำแนะนำ : อย่าเพิ่งรีบต่อทั้งสามเสาพร้อมกัน — ระบบส่วนใหญ่ได้ประโยชน์ 80% จากการมี metrics + alert ที่ตั้งไว้ดี ๆ เท่านั้น ทำเสาแรกให้แน่นก่อน แล้วค่อยขยาย

สรุปทั้งหมดในหน้าเดียว

ถ้าจำได้ 6 ข้อนี้ ก็ถือว่าได้แก่นของวิชานี้ครบแล้ว

1metric คือเส้น ไม่ใช่ตัวเลข

ชื่อ + ชุด label = 1 time series · label ทำให้หั่นดูได้ทุกมุม แต่ต้องมีค่าที่จำกัด

2Prometheus ไปดึงเอง

แอปแค่เปิด /metrics · ผลพลอยได้คือ up ที่บอกว่า target ยังอยู่ไหม

3อย่าอ่านค่าดิบของ counter

ถามเรื่องอัตราใช้ rate() · ถามยอดในช่วงใช้ increase() · หน้าต่างควร ≥ 4 เท่าของ scrape interval · rate ก่อน sum เสมอ

4ดู p95 ไม่ใช่ค่าเฉลี่ย

ค่าเฉลี่ยซ่อนคนที่เจ็บที่สุดไว้ · histogram รวมข้าม instance ได้ summary ทำไม่ได้

5dashboard คือโค้ด

provision ด้วยไฟล์ · fix datasource uid · commit ลง git
