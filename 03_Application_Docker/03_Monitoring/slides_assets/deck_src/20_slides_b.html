ติดตัววัดใช้โค้ดแค่ไม่กี่บรรทัด

client library จัดการเรื่องรูปแบบและ /metrics ให้หมด เราแค่บอกว่าจะนับอะไร
# 1) ประกาศตัววัด — ทำครั้งเดียวตอนแอปเริ่ม
REQS = Counter("app_requests_total", "จำนวน request ทั้งหมด", ["method", "endpoint", "status"])
DUR  = Histogram("app_request_duration_seconds", "เวลาที่ใช้ต่อ request", ["endpoint"],
                buckets=[.01,.025,.05,.1,.25,.5,1,2.5,5])
INFL = Gauge("app_inflight_requests", "request ที่กำลังทำอยู่ตอนนี้")

# 2) บันทึกรอบ request — ต้องอยู่ใน try/finally เสมอ
start, status = time.perf_counter(), "500"   # ตั้งไว้ก่อนว่าพัง ถ้ารอดค่อยเปลี่ยน
INFL.inc()
try:
    ...                                       # ทำงานจริง
    status = "200"
finally:                                     # ← ถึงจะ exception ก็ยังนับครบ
    INFL.dec()
    DUR.labels(endpoint="/api/items/:id").observe(time.perf_counter() - start)
    REQS.labels(method="GET", endpoint="/api/items/:id", status=status).inc()
บรรทัดที่อันตรายที่สุดคือ endpoint= : ต้องใส่เป็น รูปแบบ (/api/items/:id) ไม่ใช่ path จริงที่ผู้ใช้เรียก (/api/items/48213) — ถ้าใส่ path จริง = สร้าง series ใหม่ทุกครั้งที่มี id ใหม่ → cardinality ระเบิด (จะได้ลองทำให้พังจริงใน LAB 4)

Alerting

dashboard มีค่าก็ต่อเมื่อมีคนดู — alert คือสิ่งที่ทำงานตอนตี 3 ที่ไม่มีใครดู
Monitoring · Alerting

Alert rule คือ PromQL + เงื่อนไขเวลา

ถ้าเขียน query เป็นแล้ว ก็เขียน alert เป็นทันที
groups:
  - name: service-alerts
    rules:
      - alert: HighErrorRate
        expr: sum(rate(app_requests_total{status=~"5[0-9]{2}"}[2m]))
              / sum(rate(app_requests_total[2m])) > 0.05
        for: 30s                # ต้องจริงต่อเนื่องครบเวลานี้ก่อนถึงจะ firing
        labels:
          severity: warning     # ← Alertmanager ใช้เลือกปลายทาง
          service: app          # ← ใช้จับคู่ตอน inhibit (ดูสไลด์ถัดไป)
        annotations:
          summary: "error เกิน 5% ต่อเนื่อง"
          description: "ค่าปัจจุบัน {{ $value | humanizePercentage }}"
labels = ใช้ตัดสินใจ (ส่งหาใคร ด่วนแค่ไหน จัดกลุ่มกับใคร)
annotations = ข้อความให้คนอ่าน ไม่มีผลต่อการ route
regex ของ PromQL ยึดเต็มสตริง 5[0-9]{2} จึงอ่านตรงว่า "เลข 3 หลักขึ้นต้นด้วย 5"
(เขียนสั้นเป็น 5.. ก็ได้ แต่ . รับอักขระที่ไม่ใช่ตัวเลขด้วย)
ตรวจไฟล์ก่อนเสมอ :
docker compose exec prometheus \
  promtool check rules /etc/prometheus/rules/alerts.yml

Prometheus ตัดสินว่า "ผิดปกติไหม" · Alertmanager ตัดสินว่า "จะบอกใคร อย่างไร เมื่อไร"
Monitoring · Alerting

Alert ที่ดีต่างจาก alert ที่แย่อย่างไร

กฎข้อเดียวที่สำคัญที่สุด — เตือนที่อาการ ไม่ใช่ที่สาเหตุ

❌ alert ที่แย่

  • "CPU > 80%"แล้วไง? ถ้าผู้ใช้ยังใช้งานได้ปกติ นี่คือการปลุกคนโดยไม่มีเหตุ
  • "disk ใช้ไป 70%"ไม่บอกว่าเหลือเวลาอีกกี่วัน — ควรเตือนที่ "จะเต็มใน 4 ชั่วโมง" แทน
  • ไม่มี for:กระตุกวินาทีเดียวก็ปลุกคนแล้ว

✅ alert ที่ดี

  • "error เกิน 5% นาน 5 นาที"ผู้ใช้เจ็บจริง และเจ็บนานพอที่จะไม่ใช่เรื่องบังเอิญ
  • "p95 เกิน 1 วินาที นาน 10 นาที"ผูกกับ SLO ที่สัญญาไว้กับผู้ใช้โดยตรง
  • "up == 0 นาน 1 นาที"เราตาบอดอยู่ — ต้องรู้ก่อนเรื่องอื่นทั้งหมด
ทดสอบง่าย ๆ ว่า alert ตัวนี้ควรมีไหม : ถ้ามันดังตอนตี 3 คนที่ถูกปลุกต้องลุกขึ้นมาทำอะไรบางอย่างทันทีหรือเปล่า? ถ้าคำตอบคือ "ดูพรุ่งนี้ก็ได้" — มันไม่ควรเป็น alert ให้ทำเป็น dashboard หรือรายงานแทน
