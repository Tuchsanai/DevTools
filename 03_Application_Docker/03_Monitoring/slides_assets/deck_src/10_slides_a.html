Time series คืออะไรกันแน่

ไม่ใช่ "ตัวเลข 1 ค่า" แต่คือ "เส้น 1 เส้น" ที่มีค่าเรียงตามเวลา
# เวลา            ค่า
10:00:00   1000
10:00:15   1030   ← scrape ทุก 15 วินาที
10:00:30   1075
10:00:45   1105
1 series = ชื่อ metric + ชุด label ที่ไม่ซ้ำกัน 1 ชุด
เปลี่ยนค่า label แม้ตัวเดียว = กลายเป็นคนละเส้นทันที
seriesเก็บอะไร
app_requests_total{status="200"}เส้นของ request ที่สำเร็จ
app_requests_total{status="500"}เส้นของ request ที่พัง
app_requests_total{status="404"}อีกเส้นแยกออกไป
นี่คือจุดที่ทรงพลังและอันตรายพร้อมกัน : label ทำให้เราหั่นดูข้อมูลได้ทุกมุม แต่ก็ทำให้จำนวนเส้นระเบิดได้ถ้าเลือกผิด (เดี๋ยวเจอในหัวข้อ cardinality)

ชนิดของ metric มี 4 แบบ

เลือกผิดชนิดตั้งแต่ต้น = query ยังไงก็ได้คำตอบที่ไม่มีความหมาย
ชนิดพฤติกรรมใช้เมื่อตัวอย่างจริงในแล็บ
Counterขึ้นอย่างเดียว รีเซ็ตเป็น 0 เมื่อ restartนับ "จำนวนครั้งสะสม" ของเหตุการณ์app_requests_total
Gaugeขึ้นก็ได้ ลงก็ได้วัด "ค่า ณ ขณะนี้" ที่แกว่งไปมาnode_memory_MemAvailable_bytes
Histogramนับลงถังตามช่วงค่า (สะสม)ดูการกระจายตัว เช่น เวลาตอบสนองapp_request_duration_seconds
Summaryคำนวณ quantile ที่ฝั่งแอปเลยเมื่อต้องการ quantile แม่นของ instance เดียว(ชุดนี้ไม่ใช้ — เหตุผลอยู่สไลด์ถัดไป)
ธรรมเนียมการตั้งชื่อที่ควรทำตาม : counter ลงท้ายด้วย _total · ใส่หน่วยไว้ในชื่อเสมอ (_seconds, _bytes) · ใช้หน่วยฐาน (วินาที ไม่ใช่มิลลิวินาที · byte ไม่ใช่ MB) แล้วค่อยไปแปลงหน่วยตอนแสดงผลใน Grafana

ทำไม counter ถึงไม่เก็บเป็น "ต่อวินาที" ไปเลย?

คำถามที่ดีมาก — คำตอบคือเรื่องการทนต่อการ scrape ที่หลุด

ถ้าแอปเก็บเป็นอัตราให้เลย

แอปต้องเลือกช่วงเฉลี่ยเอง (1 นาที? 5 นาที?) แล้วทุกคนติดอยู่กับช่วงนั้นตลอดไป

ถ้า scrape หลุดไป 1 รอบ ข้อมูลช่วงนั้นหายถาวร เพราะค่าที่หายคือค่าเฉลี่ยของช่วงนั้น

เก็บเป็นค่าสะสม (แบบที่ Prometheus ใช้)

แอปแค่บวกเพิ่มอย่างเดียว ไม่ต้องรู้จักเวลา ไม่ต้องเก็บประวัติย้อนหลังเอง

ถ้า scrape หลุด 1 รอบ ยอดรวมไม่หาย — ค่าสะสมรอบถัดไปรวมของที่หายไว้ให้แล้ว (เสียแค่ความละเอียดว่าช่วงนั้นเกิดอะไรขึ้นบ้าง)

สรุปเป็นประโยคเดียว : counter เก็บ "ผลรวมตั้งแต่ process เริ่มทำงาน" แล้วปล่อยให้ คนถาม เป็นผู้เลือกช่วงเวลาเองตอน query ด้วย rate(...[1m]) — ความยืดหยุ่นนี้คือเหตุผลที่ Prometheus ไม่เก็บเป็นอัตราตั้งแต่ต้นทาง

Histogram — ทำไมค่าเฉลี่ยถึงหลอกเรา

ค่าเฉลี่ย 200ms ฟังดูดี แต่ถ้า 1% ของผู้ใช้รอ 8 วินาที เราจะไม่มีวันเห็นคนกลุ่มนั้นเลย
Monitoring · Metrics 101

Histogram หน้าตาจริงบน /metrics

histogram 1 ตัว = หลาย series : _bucket หลายเส้น + _sum + _count
# HELP app_request_duration_seconds เวลาที่ใช้ต่อ request
# TYPE app_request_duration_seconds histogram
app_request_duration_seconds_bucket{endpoint="/api/items",le="0.01"}  12
app_request_duration_seconds_bucket{endpoint="/api/items",le="0.05"}  88
app_request_duration_seconds_bucket{endpoint="/api/items",le="0.1"}   140
app_request_duration_seconds_bucket{endpoint="/api/items",le="+Inf"}  200   ← เท่ากับ _count เสมอ
app_request_duration_seconds_sum{endpoint="/api/items"}    14.7    ← เวลารวมทุก request (วินาที)
app_request_duration_seconds_count{endpoint="/api/items"}  200     ← จำนวน request ทั้งหมด
ค่าเฉลี่ยตลอดอายุ process : _sum / _count = 14.7 / 200 ≈ 0.073 วินาที
ถ้าอยากได้ค่าเฉลี่ยเฉพาะ 5 นาทีล่าสุด ต้องใช้ rate(_sum[5m]) / rate(_count[5m]) (คนละเลขกัน)
p95 จากตัวเลขชุดนี้ได้ 0.1 วินาที : อันดับที่ 95% ของ 200 คือครั้งที่ 190 ซึ่งเกินถัง le="0.1" (140 ครั้ง) ไปแล้ว จึงตกอยู่ในถัง +Inf
Prometheus จะคืนขอบบนของถังจำกัดใบสุดท้าย = 0.1 → สัญญาณว่า ถังหยาบเกินไป ต้องเพิ่มถังที่สูงกว่านี้

prometheus.yml — อ่านทีละบรรทัด

ไฟล์เดียวนี้ตอบคำถามว่า "ไปดึงจากใคร บ่อยแค่ไหน"
global:
  scrape_interval: 15s       # ดึงทุก 15 วิ — ถ้าไม่ใส่ ค่า default คือ 1 นาที!
  evaluation_interval: 15s   # ประเมิน alert rule ทุก 15 วิ

scrape_configs:
  - job_name: "node"          # กลายเป็น label job="node" ติดไปกับทุก series
    static_configs:
      - targets: ["node-exporter:9100"]   # ← ชื่อ service ใน compose ไม่ใช่ localhost

  - job_name: "prometheus"    # Prometheus เฝ้าตัวเองด้วย
    static_configs:
      - targets: ["localhost:9090"]
ความผิดพลาดอันดับหนึ่งของคนเริ่มใช้ : ใส่ localhost:9100 เป็น target
เพราะ localhost ในสายตาของ container ชื่อ prometheus คือ ตัวมันเอง ไม่ใช่เครื่อง host และไม่ใช่ container ตัวอื่น → target จะ DOWN ทันที (เรื่องนี้จะได้ลองทำให้พังจริงใน LAB 1)

Prometheus แถม label ให้อัตโนมัติ

และแถม metric พิเศษชื่อ up ที่สำคัญที่สุดตัวหนึ่งในระบบ

label ที่ติดมาให้เอง

job — มาจาก job_name ใน config
instance — คือ host:port ของ target ตัวนั้น

node_load1{job="node", instance="node-exporter:9100"} 0.42

up — metric ที่ Prometheus สร้างเอง

up = 1 → scrape รอบล่าสุดสำเร็จ
up = 0 → ติดต่อ target ไม่ได้ / ตอบไม่ถูกรูปแบบ

นี่คือสิ่งที่ push model ให้ไม่ได้ เพราะ "เงียบไป" กับ "ตายไป" แยกกันไม่ออก

alert แรกที่ทุกระบบควรมีคือ : up == 0 — ก่อนจะไปสนใจ CPU หรือ memory ใด ๆ ให้แน่ใจก่อนว่า "เรายังเห็นระบบอยู่ไหม" (ถ้า exporter ตายแล้วเราไม่รู้ กราฟจะดูสวยงามทั้งที่ระบบล่มไปแล้ว)

Monitoring · PromQL

PromQL มีข้อมูล 2 ชนิดที่ต้องแยกให้ออก

(ทั้งหมดมี 4 ชนิด — แต่ scalar กับ string เจอน้อยมาก) สับสนตรงนี้ = เจอ error "expected type instant vector" ตลอดกาล

Instant vector — ค่า ณ จุดเวลาเดียว

node_load1
node_load1{job="node"}

ได้ค่าล่าสุด 1 ค่าต่อ 1 series · เอาไปวาดกราฟได้เลย

Range vector — ค่าหลายจุดในช่วงเวลา

node_load1[5m]
node_cpu_seconds_total[1m]

ได้ชุดค่าย้อนหลัง 5 นาที · วาดกราฟตรง ๆ ไม่ได้ ต้องผ่านฟังก์ชันอย่าง rate() ก่อน

กฎจำง่าย : เห็น [...] เมื่อไร แปลว่าผลลัพธ์ยังวาดไม่ได้ ต้องมีฟังก์ชันมาห่ออีกชั้นเสมอ
rate() · increase() · avg_over_time() · max_over_time() ล้วนกิน range vector แล้วคืน instant vector

เลือก series ด้วย label matcher

4 ตัวดำเนินการนี้ใช้ได้กับทุก query
ตัวความหมายตัวอย่าง
=เท่ากับapp_requests_total{status="500"}
!=ไม่เท่ากับcontainer_cpu_usage_seconds_total{name!=""} ← ใช้บ่อยมากใน LAB 2
=~ตรงกับ regexapp_requests_total{status=~"5.."} ← จับ 500, 502, 503 ทั้งหมด
!~ไม่ตรงกับ regexnode_cpu_seconds_total{mode!~"idle|iowait"} ← เอาเฉพาะเวลาที่ CPU ทำงานจริง
regex ของ PromQL ยึดเต็มสตริงเสมอ (anchored)
status=~"5" จะไม่ตรงกับ "500"
ต้องเขียน status=~"5.." หรือ status=~"5.*"
ชื่อ metric ก็คือ label ตัวหนึ่ง ชื่อว่า __name__
{__name__=~"node_cpu.*"} ใช้ค้นหาแบบกวาดได้ (แต่ช้า อย่าใช้ใน dashboard จริง)

Monitoring · PromQL

rate · irate · increase ต่างกันอย่างไร

ทั้งสามตัวกิน range vector เหมือนกัน แต่ให้คำตอบคนละแบบ
ฟังก์ชันคำนวณอย่างไรใช้เมื่อไร
rate(x[5m])ค่าเฉลี่ยต่อวินาที ตลอดทั้งหน้าต่างค่าเริ่มต้นที่ควรใช้เสมอ — เรียบ ทนต่อ scrape ที่หลุด เหมาะกับ dashboard และ alert
irate(x[5m])ใช้แค่ 2 จุดสุดท้ายในหน้าต่างอยากเห็นการกระตุกแบบละเอียด · โดยทั่วไปไม่ควรใช้กับ alert เพราะไวเกินจนเตือนพร่ำเพรื่อ
increase(x[1h])จำนวนที่เพิ่มขึ้นรวมในช่วงนั้นตอบคำถามแบบ "ชั่วโมงที่ผ่านมามี error กี่ครั้ง" · เท่ากับ rate × วินาทีในช่วง
ทั้งสามตัวรู้จัก counter reset : ถ้า container restart แล้วค่าตกจาก 5000 กลับเป็น 0 ทั้งสามฟังก์ชันจะเข้าใจว่านี่คือการรีเซ็ต ไม่ใช่ค่าติดลบ แล้วชดเชยให้อัตโนมัติ — นี่คือเหตุผลว่าทำไมห้ามคำนวณผลต่างเองด้วยมือ
และทั้งสามตัวไม่ควรใช้กับ gauge — rate(node_memory_MemAvailable_bytes[5m]) เขียนได้แต่ผลไม่มีความหมาย เพราะ gauge ลดลงได้ตามปกติ ระบบจะตีความว่าเป็น reset · ถ้าอยากรู้ว่า gauge เปลี่ยนไปเท่าไรให้ใช้ delta() หรือ deriv()

ยุบหลายเส้นให้เหลือเส้นที่อยากดู

by = เก็บ label นี้ไว้ · without = ทิ้ง label นี้ ที่เหลือเก็บหมด
# มี 12 เส้น แยกตาม endpoint × status × method
rate(app_requests_total[1m])

# ยุบเหลือเส้นเดียว = อัตรารวมทั้งแอป
sum(rate(app_requests_total[1m]))

# ยุบให้เหลือแยกตาม status เท่านั้น (รวมทุก endpoint เข้าด้วยกัน)
sum by (status) (rate(app_requests_total[1m]))

# เอา 3 container ที่กิน CPU มากที่สุด
topk(3, rate(container_cpu_usage_seconds_total{name!=""}[1m]))
ตัวที่ใช้บ่อย : sum · avg · max · min · count · topk / bottomk
ลำดับสำคัญมาก : ต้อง rate() ก่อน แล้วค่อย sum()
sum(rate(x[5m])) ✅ ถูก
rate(sum(x)[5m]) ❌ เขียนไม่ผ่านตั้งแต่ parse (ใส่ [5m] ท้ายผลของ sum() ไม่ได้) — และต่อให้ดัดให้ผ่าน ค่าก็เพี้ยน เพราะพอ sum แล้ว counter reset ของแต่ละเส้นจะถูกกลบไป

กับดัก PromQL ที่ทุกคนต้องเจอ

รู้ไว้ก่อนจะประหยัดเวลาไล่ปัญหาไปได้เป็นชั่วโมง

1กราฟว่างเปล่า (No data)

หน้าต่าง rate() แคบเกินจนมีไม่ถึง 2 จุด → คำนวณอัตราไม่ได้
แก้ : ขยายเป็น [1m] ขึ้นไปเมื่อ scrape ทุก 15 วิ (เผื่อ scrape หลุดด้วย)

2ตัวเลขสูงเกินจริงเป็นเท่าตัว

ลืมกรอง series ที่เป็นค่ารวมของทั้งเครื่องออก เช่น cAdvisor มีเส้น id="/" ปนอยู่ · sum(node_filesystem_avail_bytes) ก็นับดิสก์ก้อนเดียวซ้ำได้หลายเท่าเพราะ mount หลายจุด
แก้ : ใส่ {name!=""} · ใช้ min() หรือระบุ mountpoint แทนการ sum() มั่ว

3หารกันแล้วได้ผลว่าง

ตัวเศษกับตัวส่วนมี label ไม่ตรงกัน PromQL จับคู่ไม่ได้เลยคืนค่าว่าง
แก้ : sum() ทั้งสองฝั่งก่อน หรือใช้ on(...) / ignoring(...)

4ตัวส่วนเป็น 0 ตอนไม่มี traffic

error ratio กลายเป็น NaN แล้ว alert เงียบหรือเด้งมั่ว
แก้ : เพิ่มเงื่อนไขว่าต้องมี traffic ขั้นต่ำก่อน เช่น and sum(rate(...)) > 0.1
