Kafka คืออะไร — เล่าแบบคนไม่เคยรู้จัก

อย่าเพิ่งจำศัพท์ ดูปัญหาก่อน แล้วจะเข้าใจเองว่าทำไมโลกต้องมีของแบบนี้

1 · ปัญหา: เกิดเรื่องหนึ่งเรื่อง แต่มีหลายระบบต้องรู้

สมมุติเราทำแอปสั่งอาหาร ทุกครั้งที่ลูกค้ากด "สั่ง" มี 4 ระบบที่ต้องรู้เรื่องนี้: ครัว (ทำอาหาร) · ไรเดอร์ (หาคนส่ง) · การเงิน (ตัดเงิน) · สถิติ (ยอดขายวันนี้)

2 · เทียบกับของที่รู้จัก: กลุ่มไลน์

พิมพ์ครั้งเดียว

ส่งข้อความลงกลุ่มครั้งเดียว ทุกคนในกลุ่มเห็น — ไม่ต้องทักทีละคน

= Producer ส่งลง Topic

อ่านตอนไหนก็ได้

คนที่ติดธุระ กลับมาเปิดทีหลังก็ยังอ่านได้ ไม่ต้องออนไลน์พร้อมกัน

= ข้อความเก็บไว้ใน Kafka

อ่านแล้วไม่หาย

เราอ่านแล้ว ข้อความยังอยู่ให้คนอื่นอ่าน · เลื่อนขึ้นไปอ่านย้อนหลังได้

= อ่านไม่ลบ · replay ได้

"อ่านถึงตรงนี้"

แต่ละคนมีจุดที่อ่านถึงของตัวเอง ใครอ่านช้าก็มีข้อความค้าง

= offset ของแต่ละ group · ข้อความค้าง = LAG

เข้ากลุ่มทีหลัง

(ถ้าตั้งให้เห็นประวัติ) สมาชิกใหม่อ่านย้อนหลังได้ทั้งหมด

= group ใหม่อ่านตั้งแต่ต้น

ประวัติไม่อยู่ตลอดไป

เก่าเกินช่วงเวลาหนึ่งก็หายเอง ไม่เกี่ยวว่ามีคนอ่านหรือยัง

= retention (ค่าเริ่มต้น 7 วัน)

ส่วน RabbitMQ (สัปดาห์ที่แล้ว) เหมือน ตะกร้ารับงาน: งานหนึ่งชิ้นมีคนหยิบไปทำคนเดียว ทำเสร็จ (ack) แล้วงานถูกเอาออกจากตะกร้า · ถ้าคนหยิบล้มกลางทางก่อนบอกว่าเสร็จ งานจะกลับเข้าตะกร้าให้คนอื่นทำ — ไม่ได้หายเพราะล่ม แค่ออกแบบมาให้ "ทำเสร็จแล้วทิ้ง" · ดูเปรียบเทียบเต็ม ๆ ที่ท้ายหน้านี้

ลงรายละเอียด 1 · ถ้าออเดอร์เยอะมาก Kafka แบ่งสมุดเป็นหลายเล่ม

ต่อจากเรื่องแอปสั่งอาหาร: ถ้ามีร้าน 3 สาขา ออเดอร์เยอะจนสมุดเล่มเดียวไม่ไหว Kafka ให้แบ่ง topic orders เป็น 3 เล่ม (เรียกว่า partition: p0 · p1 · p2) แล้วดูว่าแต่ละออเดอร์ลงเล่มไหน

อ่านภาพนี้ทีละข้อ

  1. key ตัดสินว่าลงเล่มไหน — ออเดอร์หาดใหญ่ทุกใบลง p0 เสมอ เชียงใหม่ลง p1 กรุงเทพลง p2 (Kafka คำนวณจากชื่อ key ไม่ได้สุ่ม) → ออเดอร์ของสาขาเดียวกันเรียงลำดับไม่สลับ · พิสูจน์ใน LAB 2
  2. แต่ละเล่มนับเลขของตัวเอง — เลขในช่องคือ offset เริ่มที่ 0 ทุกเล่ม · จะบอก "ที่อยู่" ของออเดอร์ต้องบอกครบว่า เล่มไหน + เลขอะไร เช่น p1 เลข 0
  3. ทีมผู้อ่านมีที่คั่นหนังสือแยกทุกเล่ม (เส้นดำ ▼) — Kafka จำไว้ให้ ปิดโปรแกรมแล้วเปิดใหม่ก็อ่านต่อจากตรงเดิม · พิสูจน์ใน LAB 3
  4. LAG = ช่องจางที่ยังไม่ได้อ่าน — เล่ม p1 ค้าง 2 ใบ ถ้าตัวเลขนี้โตเรื่อย ๆ แปลว่าอ่านไม่ทัน ต้องเพิ่มคนอ่าน

ทำไมต้องแบ่งหลายเล่ม? เพราะในทีมเดียว หนึ่งเล่มอ่านได้ทีละคน — 3 เล่มจึงให้พ่อครัว 3 คนช่วยกันอ่านพร้อมกันได้ (คนที่ 4 จะว่างงาน) · นี่คือเรื่องของ LAB 3

ลงรายละเอียด 2 · ในแล็บ ของทั้งหมดอยู่ตรงไหน

ในแล็บมี "กล่องซ้อนกัน 3 ชั้น" เหมือนตุ๊กตาแม่ลูกดก: ① เครื่องเรา ข้างในมี ② กล่องเรียน devtools ข้างในมี ③ กลุ่ม container ของ compose (Kafka + หน้าเว็บ) — ให้ดูแค่ 3 เส้นทาง A · B · C

เส้นใครคุยกับใครใช้ที่อยู่อะไรทำไม
Aเบราว์เซอร์บนเครื่องเรา → หน้าเว็บ Kafka UIlocalhost:8411ต้องทะลุ 2 ชั้น: -p 8411:8411 (เข้ากล่อง devtools) แล้ว 8411:8080 ใน compose (เข้า kafka-ui) — ลืมชั้นไหนเปิดไม่ขึ้น
Bโปรแกรม Python → Kafkalocalhost:9092Python อยู่นอก compose แต่อยู่เครื่องเดียวกับมัน · compose เปิดประตู 9092 ออกมาให้
Ckafka-ui / kafka-init → Kafkakafka:19092อยู่ใน compose ด้วยกัน เรียกกันด้วยชื่อ kafka ได้เลย (เหมือน Docker LAB 6)
ทำไม Kafka ต้องมี "ประตู 2 บาน" (9092 กับ 19092)?

เพราะคำว่า localhost ของแต่ละ container แปลว่า "ตัวฉันเอง" — ถ้า kafka-ui เรียก localhost:9092 มันจะหา Kafka ในกล่องของตัวเอง ซึ่งไม่มี

เทียบกับเบอร์โทรออฟฟิศ: คนนอกโทรเบอร์หลัก (localhost:9092) · คนในออฟฟิศกดเบอร์ต่อภายใน (kafka:19092) · Kafka จึงประกาศเบอร์ 2 ชุดไว้ใน KAFKA_ADVERTISED_LISTENERS ให้แต่ละกลุ่มใช้เบอร์ที่โทรถึง

เคล็ดลับ TA: เปิด port ครั้งเดียวใช้ได้ทั้ง 4 แล็บ

เอกสารให้ลบ/สร้างกล่องใหม่ทุกแล็บเพื่อเปิด port ของแล็บนั้น — เปิดทีเดียวทั้งหมดได้ (ผมรันแบบนี้ทั้ง 4 แล็บ ใช้ได้):

docker rm -fv devtools
docker run -dit --name devtools --privileged -p 2222:22 -p 8411:8411 -p 8412:8412 -p 8413:8413 -p 8414:8414 tuchsanai/devtools:2569_1

-v ใน rm -fv ลบ volume เก่าของกล่องทิ้งด้วย กันดิสก์เต็ม (image นี้ประกาศ VOLUME /var/lib/docker)

กลับมาทำต่อวันหลัง: docker start devtools แล้ว ssh เข้าไป · ถ้าขึ้น Cannot connect to the Docker daemon ใช้คำสั่งปลุก Docker ในแท็บ LAB 1 ข้อ 0 (เจอจริง 1 ใน 4 ครั้ง)

สรุปท้ายหน้า · ตกลง Kafka คืออะไร

Kafka คือ "สมุดจดเหตุการณ์กลาง" ของทั้งบริษัท — โปรแกรมไหนมีเรื่องเกิดขึ้นก็จดลงสมุด · โปรแกรมไหนอยากรู้ก็มาเปิดอ่านเอง · อ่านแล้วไม่ลบ ใครมาทีหลังก็อ่านย้อนได้ (ภายในช่วงเวลาเก็บ เช่น 7 วัน)

ใช้ทำอะไร

ให้หลายระบบรู้เรื่องเดียวกันโดยไม่ต้องเรียกหากันตรง ๆ · รับข้อมูลที่ไหลเข้ามาเยอะไม่หยุด (คลิก ตำแหน่งรถ เซ็นเซอร์ รายการเงิน) · เก็บไว้ให้ย้อนดู/ประมวลผลใหม่ได้

ได้อะไร

ตัวอ่านล่ม ข้อมูลไม่หาย รอไว้ กลับมาอ่านต่อจากที่ค้าง · เพิ่มระบบใหม่ไม่ต้องแก้ของเดิม · งานเยอะก็เปิดตัวอ่านเพิ่มในทีม

ไม่เหมาะกับ

งานสั่งทำครั้งเดียวจบที่อยากแจกคนละชิ้นแบบยืดหยุ่น (ส่งเมล ย่อรูป) — อันนั้น RabbitMQ ตรงกว่า

Kafka vs RabbitMQ · ต่างกันที่ "ปรัชญา"

ทั้งคู่ส่งข้อความระหว่างโปรแกรมได้ และทั้งคู่ทำให้ข้อความไม่หายเมื่อล่มได้ — ความต่างจริงอยู่ที่ออกแบบมาเพื่องานคนละแบบ ความต่างข้ออื่นทั้งหมดตามมาจากตรงนี้

RabbitMQ = "แจกงาน"

ข้อความ 1 ชิ้น = งาน 1 ชิ้น มีคนทำ คนเดียว · ทำเสร็จ (ack) ก็เอาออกทิ้ง · จบกัน

≈ ตะกร้ารับงาน / คิวรับบัตรที่ธนาคาร

Kafka = "บันทึกเหตุการณ์"

ข้อความ 1 ชิ้น = เหตุการณ์ 1 เรื่อง จดเก็บไว้ · ใครอยากรู้มาอ่านเองกี่รอบก็ได้ · ลบเมื่อหมดอายุเท่านั้น

≈ สมุดบันทึก / กลุ่มไลน์

ดูเป็นภาพบล็อก

เทียบทีละเรื่อง

เรื่องRabbitMQ (แจกงาน)Kafka (บันทึกเหตุการณ์)
อ่านแล้วข้อความไปไหนack แล้วลบออกจาก queueยังอยู่ แค่เลื่อนที่คั่น (offset) · ลบเมื่อหมดอายุ (retention เช่น 7 วัน)
ตัวรับหลายตัว ทีมเดียวกันแจกทีละชิ้น สลับกัน (round-robin) · 1 ชิ้นได้คนเดียวแบ่งกันถือคนละ partition · 1 ข้อความได้คนเดียวในทีม · คนเกินจำนวน partition ว่างงาน
ตัวรับหลายตัว ต่างทีมกัน ได้ข้อความเดียวกันครบได้ แต่ต้องใช้ fanout exchange ก๊อปปี้ไปหลาย queue (queue ต่อทีม)ได้เลย แค่ตั้ง group_id คนละชื่อ · อ่านจากที่เดียวกัน ไม่ต้องก๊อปปี้
มาทีหลัง อยากอ่านย้อน (replay)queue ปกติไม่ได้ — ของที่ ack ไปแล้วหายแล้วได้ — group ใหม่อ่านจากต้น log (เท่าที่ยังไม่หมดอายุ)
ตัวรับล่มกลางงานถ้าใช้ manual ack: งานที่ยังไม่ ack กลับเข้าคิวให้ตัวอื่นทำ (ได้ซ้ำได้) · ถ้าใช้ auto_ack=True: หายจริงอ่านต่อจากที่ commit ล่าสุด (auto ทุก 5 วิ) · ตายกะทันหันอาจได้งานซ้ำ · ⚠ บัค LAB 3: kill ตอนทำงานค้าง งานที่เหลือข้ามไป
ตัว broker ล่ม / restartรอดถ้าตั้ง durable queue + persistent message (เก็บลงดิสก์) · ถ้าไม่ตั้ง หายlog เขียนลงดิสก์ · stop/start รอด (LAB 1) · แต่ compose down ในแล็บลบ volume ทิ้ง
ยืนยันว่างานเสร็จbasic_ack ทีละข้อความcommit ตำแหน่ง (offset) ทีเดียวทั้งช่วง
ใครส่งข้อความหาตัวรับbroker ยัดให้ (push · callback)ตัวรับดึงเอง (pull · poll)
เลือกรับเฉพาะบางเรื่องbroker ทำให้: routing key + wildcard (kern.*)ไม่มี — แยก topic หรืออ่านมากรองเอง (จุดในชื่อไม่ใช่ wildcard)
ลำดับข้อความตามคิว แต่หลาย worker ทำสลับกันการันตีภายใน partition เดียว → key เดียวกันไม่สลับ

"RabbitMQ ล่มแล้วข้อความหาย" — ไม่จริง: ตัวรับล่มก่อน ack งานกลับเข้าคิว · broker ล่มก็รอดถ้า durable + persistent (RabbitMQ LAB 2 พิสูจน์ทั้งสองข้อ) · ที่หายจริงคือใช้ auto_ack=True (อย่าง receive.py ใน RabbitMQ LAB 1) หรือไม่ตั้ง durable · ถ้าต้องการชัวร์ขึ้นอีกขั้นฝั่งผู้ส่งต้องใช้ publisher confirms
  2. "Kafka ตัวรับหลายตัวไม่แย่งกันเสมอ" — จริงเฉพาะต่าง group · ถ้าอยู่ group เดียวกัน Kafka แบ่งงานให้ แต่ละข้อความไปถึงตัวเดียวในทีม (ตั้งใจ เพื่อช่วยกันทำ)
  3. "Kafka เก็บข้อมูลตลอดไป" — ไม่: มี retention (ค่าเริ่มต้น 7 วัน หรือตามขนาด) หมดอายุก็ลบ · replay ได้เฉพาะของที่ยังไม่หมดอายุ
  4. "RabbitMQ replay ไม่ได้เลย" — จริงสำหรับ queue ปกติ (แบบที่เรียนในวิชานี้) · แต่ RabbitMQ รุ่นใหม่มี Streams ที่ทำงานแบบ log อ่านซ้ำได้ (เห็นชื่อในแท็บ "Queues and Streams" ของ Management UI) — นอกขอบเขตแล็บ

LAB 1 · 001_LAB_Kafka_Setup

เปิด Kafka แล้วส่ง–รับข้อความแรก

UI localhost:8411topic hello (1 partition)ไฟล์ send.py · receive.pyผลรัน ตรงเอกสาร

เป้าหมายเดียว: เห็นกับตาว่า อ่านแล้วข้อความไม่หาย — จุดที่ Kafka ต่างจาก RabbitMQ มากที่สุด

    สรุป · แล็บนี้สอนอะไร

    แล็บนี้สอนว่า Kafka เป็น สมุดจด ไม่ใช่ตะกร้า: ส่งแล้วได้ "ที่อยู่" ถาวร (offset) · ไม่มีคนอ่านข้อความก็รอ · อ่านกี่รอบก็ยังอยู่ · broker ดับแล้วฟื้น ข้อมูลยังอยู่

    เห็นภาพ: เหมือนจดลงสมุดบันทึกประจำวัน — จดแล้วใครจะเปิดอ่านกี่รอบก็ได้ ไม่เหมือนโพสต์อิทที่ดึงออกแล้วหาย

    เอาไปใช้จริง:

    • ระบบปลายทางล่มชั่วคราว ข้อมูลไม่หาย รออยู่ใน Kafka กลับมาอ่านต่อได้
    • เก็บ "ประวัติเหตุการณ์" ไว้ตรวจย้อนหลัง (audit log) · debug ด้วยการอ่านซ้ำ
    • ทักษะที่ได้: เปิดระบบด้วย docker compose up -d รอให้ healthy · ส่อง topic ด้วย kafka-topics.sh · นับข้อความด้วย kafka-get-offsets.sh
    LAB 2 · 002_LAB_Partitions_Keys

    ใครเลือกว่าข้อความลง partition ไหน

    UI localhost:8412topic orders 3 → 4 partitionsผลรัน ตรงเอกสาร ระวัง 1 จุด

    กฎ 3 ชั้น (producer ตัดสิน): ระบุ partition ตรง ๆ ชนะทุกอย่าง → ไม่ระบุแต่มี key ใช้ hash → ไม่มีทั้งคู่ สุ่ม

      สรุป · แล็บนี้สอนอะไร

      แล็บนี้สอนว่า key คือป้ายบอกว่าข้อความไปเล่มไหน: key เดียวกัน → เล่มเดียวกันเสมอ → เรียงลำดับไม่สลับ · ไม่ใส่ key = สุ่ม คุมไม่ได้ · ระบุเล่มเองจะชนะ key · เพิ่มเล่มทีหลังทุกอย่างย้ายที่

      เห็นภาพ: เหมือนแยกกองเอกสารตามสาขา — เอกสารสาขาเดียวกันอยู่แฟ้มเดียวกันเรียงตามวัน แต่ข้ามแฟ้มไม่ได้เรียงกัน

      เอาไปใช้จริง:

      • ออเดอร์ของลูกค้าคนเดียวต้องไม่สลับ (สั่ง → จ่าย → ส่ง) → ใช้ customer_id เป็น key · อุปกรณ์ตัวเดียว → device_id
      • อย่าใส่ partition= ในโค้ดเอง ปล่อยให้ key ตัดสิน
      • วางจำนวน partition เผื่อโตตั้งแต่วันแรก — เพิ่มทีหลังลำดับต่อ key พัง · ระวัง key กระจุก (hot partition)
      LAB 3 · 003_LAB_Consumer_Groups

      ทีมแบ่งเล่มกันอ่าน · Rebalance · LAG

      UI localhost:8413topic tasks 3 partitionsgroup workersผลรัน ตรงเอกสาร บัค 1

      กฎเดียว: ในทีมเดียวกัน 1 เล่มมีเจ้าของได้ 1 คน — ทุกผลในแล็บนี้งอกจากกฎข้อนี้

      กติกาแล็บนี้: terminal หน้าต่างเดียว

      เปิด worker ด้วย & ต่อท้ายเสมอ · ปิดด้วย kill $(pgrep -f "worker.py B") · ดูว่าใครยังรันด้วย jobs · ข้อความของ worker จะพิมพ์แทรกปน prompt — ปกติ กด Enter เปล่า ๆ ได้

        สรุป · แล็บนี้สอนอะไร

        แล็บนี้สอนว่า ทีมเดียวกันช่วยกันอ่านโดยแบ่งเล่มกัน: เปิดเครื่องเพิ่ม Kafka แบ่งใหม่ให้เอง · ปิดเครื่อง เล่มกลับไปหาคนที่เหลือ · Kafka จำว่าทีมอ่านถึงไหน · LAG บอกว่างานค้างเท่าไร · คนเกินจำนวนเล่มว่างงาน

        เห็นภาพ: เหมือนพ่อครัว 3 คนกับสมุดออเดอร์ 3 เล่ม คนละเล่ม — มีพ่อครัวคนที่ 4 ก็ต้องยืนรอเป็นตัวสำรอง เพราะเล่มหนึ่งให้คนเดียวอ่าน

        เอาไปใช้จริง:

        • งานค้างเยอะ (LAG โต) → เปิด worker เพิ่ม ไม่ต้องแก้โค้ด — ระบบจริงตั้ง autoscale / alert จากตัวเลข LAG
        • อยากได้ worker สูงสุด N ตัว → topic ต้องมีอย่างน้อย N partition
        • โปรแกรมต้องปิดแบบสุภาพ (close()) ไม่งั้นทีมรอ 45 วิ · และระวัง kill ตอนงานค้าง (บัคข้อ +)
