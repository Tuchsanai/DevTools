ตอนที่ 3 · Product Backlog · นิยาม

Product Backlog — รายการเดียว · เรียงลำดับ · มองทั้งผลิตภัณฑ์

หนึ่งผลิตภัณฑ์ = หนึ่งรายการ · หนึ่งคนรับผิดชอบลำดับ · งานทุกชิ้นที่ทีมลงมือทำต้องมาจากรายการนี้
นิยาม — Product Backlog คือรายการที่ เกิดใหม่ได้ (emergent) และ เรียงลำดับแล้ว ของสิ่งที่จำเป็นเพื่อปรับปรุงผลิตภัณฑ์ เป็นแหล่งงานเดียวที่ Scrum Team นำไปทำ โดย Product Owner รับผิดชอบ (accountable) ต่อการจัดการให้มีประสิทธิผล— Scrum Guide 2020 (สรุปความ) · commitment ของอาร์ติแฟกต์นี้คือ Product Goal

ปัญหา · ก่อนมี Backlog

คำขอกระจายอยู่ในแชต อีเมล และไฟล์ของแต่ละคน ไม่มีใครตอบได้ว่า “ทำอะไรก่อน” ทุกคนจึงหยิบงานที่ตัวเองเห็น → งานซ้ำ งานหล่น งานแทรกตลอดเวลา

ทำไมสำคัญ · เมื่อมี Backlog

ทุกฝ่ายเห็นรายการเดียวและลำดับเดียว จึงถกกันที่ “ลำดับ” บนข้อมูลชุดเดียวกัน และใช้เวลาที่มีจำกัดกับงานที่พา Product Goal ไปข้างหน้าก่อน

CampusEats · ตัวอย่างจาก LAB 4

PO รวมงานของ CampusEats ทั้ง 10 ใบ (PBI-01…10) ไว้ในรายการเดียว แล้วเรียงตาม Product Goal “นักศึกษาสั่งและรับอาหารในมหาวิทยาลัยได้ครบวงจรภายในภาคเรียนนี้” — PBI-01…05 (ค้นหาร้าน → ดูเมนู → ตะกร้า → สั่งอาหาร → ร้านยืนยันออเดอร์) คือ flow หลักจึงอยู่บนสุด ส่วน PromptPay QR และงานของไรเดอร์รออยู่ล่าง

ภาพประกอบแนวคิด — การจัดลำดับเป็นบทสนทนาของทั้งทีมบนข้อมูลชุดเดียว แต่ความรับผิดชอบต่อลำดับสุดท้ายอยู่ที่ Product Owner
ความเข้าใจผิด — ❌ “อยู่ใน backlog = รับปากว่าจะทำทุกใบ” → ✅ backlog คือชุดทางเลือกที่เรียงไว้ ไม่ใช่สัญญา; ใบล่างถูกเลื่อน แก้ หรือถอดออกได้เมื่อเป้าหมายและข้อมูลเปลี่ยน

จากเป้าหมายสู่ Increment — เรียง · เตรียม · เลือก · ส่งมอบ · เรียนรู้

อ่านซ้าย→ขวา: รายการทั้งผลิตภัณฑ์ (commitment = Product Goal) → งานที่ทีมเลือกพร้อมแผน (Sprint Goal) → ของที่ผ่าน DoD และใช้งานได้จริง

1ส่วนประกอบ

PBI = งานหนึ่งชิ้นเพื่อปรับปรุงผลิตภัณฑ์ ซึ่งค่อย ๆ ได้ รายละเอียด · ลำดับ · ขนาด · Product Goal = commitment ที่บอกปลายทางของผลิตภัณฑ์

2กติกาการเรียง

ชั่งคุณค่าต่อผู้ใช้ · ความเสี่ยง · dependency · ความพร้อม ไม่ใช่ดูแค่ป้าย Urgent; ใบบนต้องชัดและเล็กพอจะทำจบใน 1 Sprint

3Workflow

PO รับผิดชอบลำดับ → ทีม refine ต่อเนื่อง → Developers กำหนดขนาด → Planning เลือกงาน → ทำจน Done ตาม DoD → feedback จาก Review กลับมาปรับ backlog

DEEP = Detailed · Emergent · Estimated · Prioritized เป็นแนวปฏิบัติที่จำง่าย; Scrum Guide 2020 ใช้คำว่า ordered และ sized
ความเข้าใจผิด — ❌ “เรียงตามป้าย priority ก็พอ” → ✅ ป้ายบอกระดับความเร่งด่วน แต่ backlog มีลำดับเดียวบนลงล่าง สองใบที่ High เท่ากันต้องรู้ว่าใบไหนก่อน
ความเข้าใจผิด — ❌ “ทุกใบต้องละเอียดครบก่อนเริ่มทำ” → ✅ รายละเอียดลดหลั่นตามลำดับ ใบบนละเอียดจนพร้อมทำ ใบล่างยังเป็นหัวข้อหยาบ ๆ ได้

ใน Plane — backlog คือ work items ของโปรเจกต์ ไม่ใช่หน้าจอแยกต่างหาก

state group backlog บอกว่างานยังไม่ถูกเลือกเข้ารอบ · ฟิลด์ sort_order เก็บลำดับที่ PO ลากไว้ (Order by › Manual)
Plane Lab (PLAB) · Work items · List · Group by State + Order by Priority — กลุ่ม Backlog 6 ใบ (มี “ชำระเงินด้วย PromptPay QR”) จากงานทั้งโปรเจกต์ 20 ใบ

Menu path · เปิด backlog

โปรเจกต์ → Work items → layout List → Display › Group by › State; งานใหม่เริ่มที่ state Backlog ซึ่งเป็น state ตั้งต้นของทุกโปรเจกต์ (group backlog)

Fields · ลำดับที่ PO กำหนดเอง

Display › Order by › Manual แล้วลากใบงานขึ้นลง Plane บันทึกตำแหน่งลง sort_order; ถ้าเลือก Order by อื่น (เช่น Priority ในภาพ) จะลากไม่ได้ แต่ลำดับเดิมยังอยู่

Related feature · Views

บันทึก filters + layout + display properties เป็นมุมมองชื่อ “พร้อมเข้า Sprint” (Private / Public) โดยไม่ต้องสร้าง backlog อีกชุด; CE ใช้ Views ได้ครบ

CE limit · Plane v1.4.2 — ไม่มีหน้าจอชื่อ Product Backlog และไม่มีฟิลด์ Product Goal: backlog คือ work items ของโปรเจกต์เอง ใบที่ยังไม่ถูกเลือกเข้ารอบอยู่ใน group backlog; Product Goal จึงเขียนไว้ใน description ของโปรเจกต์หรือ Page
