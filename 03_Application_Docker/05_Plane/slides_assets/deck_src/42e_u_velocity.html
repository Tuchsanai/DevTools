Velocity — ความเร็วที่วัดจากงาน Done จริงของทีม

หนึ่งตัวเลขต่อหนึ่ง Sprint · ใช้หลักฐานจากอดีตเพื่อวางแผน ไม่ใช่คำสัญญาว่าอนาคตต้องทำได้เท่าเดิม
Velocity คือ ผลรวม Story Points ของ work items ที่ผ่าน Definition of Done ภายใน Sprint หนึ่งรอบ งานที่ยังไม่ Done นับเป็น 0 หน่วย: points / sprint · เป็นมาตรวัดเฉพาะของทีมนั้น
  • ทำไมสำคัญ — ทำให้ Sprint Planning และ release forecast อิงความสามารถที่เคยเกิดขึ้นจริง
  • ปัญหาที่แก้ — แทนการเดาว่า “น่าจะรับได้ 30 points” ด้วยช่วงจากหลาย Sprint ล่าสุด
  • เงื่อนไข — ทีมต้องใช้สเกล points และ Definition of Done เดิมอย่างสม่ำเสมอ จึงเปรียบเทียบข้ามเวลาได้
ก่อนมีข้อมูลหลังมีประวัติ 3+ Sprint
รับงานตามความหวัง → มักเกินกำลังเลือกงานใกล้ช่วงที่เคย Done → อธิบายความเสี่ยงได้
ทีมใช้แนวโน้มจากหลายรอบเพื่อคุยเรื่องแผนและความไม่แน่นอนร่วมกัน

CampusEats · ตัวอย่าง Sprint 1

PBI-01 ค้นหาร้าน 3 pt + PBI-02 ดูเมนู 2 pt + PBI-10 ย้าย config 1 pt ผ่าน DoD รวม velocity = 6 points; งานที่เริ่มแล้วแต่ยังไม่ Done ไม่ถูกนับ

ความเข้าใจผิด — ❌ velocity สูง = ทีมเก่งกว่า · ✅ point เป็นสเกลภายในทีม จึงใช้ดูแนวโน้มและ forecast ของทีมเดิมเท่านั้น ห้ามเทียบคนหรือข้ามทีม

Velocity — ใช้ประวัติของทีมพยากรณ์อนาคต ไม่ใช่ตั้งเป้าให้ทีม

1วัดเมื่อ Sprint จบ

รวม points เฉพาะ work items ที่ Done: 18 · 22 · 20; งานครึ่งเสร็จ = 0 และนับใหม่เมื่อมัน Done ใน Sprint ถัดไป

2สร้างช่วงอ้างอิง

ค่าเฉลี่ย 3 Sprint = 20 pt/sprint; ช่วง 18–22 สะท้อนความผันผวน จึงควร forecast เป็นช่วง ไม่ใช่วันเดียว

3พยากรณ์และปรับใหม่

120 pt ÷ 20 = 6 Sprint; ใช้เร็วสุด 22 และช้าสุด 18 ได้ 5.5–6.7 Sprint แล้วคำนวณใหม่เมื่อ backlog หรือข้อมูลล่าสุดเปลี่ยน
