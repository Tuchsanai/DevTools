ตอนที่ 1 · ทำไมต้อง "วิศวกรรม" ซอฟต์แวร์

ซอฟต์แวร์ต้องการ วิศวกรรม ไม่ใช่แค่การเขียนโปรแกรม

"The application of a systematic, disciplined, quantifiable approach to the development, operation, and maintenance of software; that is, the application of engineering to software."— นิยาม Software Engineering · IEEE Std 610.12-1990 · ใช้ต่อใน SWEBOK (ISO/IEC TR 19759)

1Software crisis (NATO 1968)

การประชุม NATO Software Engineering Conference ที่ Garmisch ตั้งชื่อปัญหาที่ทุกคนเจอว่า "software crisis": โครงการล่าช้า เกินงบ คุณภาพต่ำ และดูแลรักษายาก เพราะขนาดของระบบโตเร็วกว่าวิธีทำงานที่มี

2คำตอบคือ "วิศวกรรม"

เป็นระบบ (systematic) มีวินัย (disciplined) และวัดได้ (quantifiable) ครอบคลุมทั้งการพัฒนา การใช้งาน และการบำรุงรักษา ไม่ใช่เฉพาะช่วงเขียนโค้ด

3องค์ความรู้ที่ตกลงร่วมกัน

SWEBOK (Software Engineering Body of Knowledge) รวบรวมสิ่งที่วิศวกรซอฟต์แวร์ควรรู้เป็น knowledge areas ใช้เป็นฐานของหลักสูตร การรับรอง และการประเมินตนเอง

systematic
มีกระบวนการ: backlog → cycle → review → release
+
disciplined
มีวินัย: test · code review · Definition of Done
+
quantifiable
วัดได้: estimate · velocity · burndown · lead time
ประเด็นของวิชานี้ — เครื่องมืออย่าง Plane ไม่ได้ทำให้ใครเป็นวิศวกร แต่ทำให้วินัยของวิศวกร (บันทึก ประเมิน ติดตาม ตรวจสอบย้อนหลัง) เกิดขึ้นได้จริงในทีม

สามกรณีศึกษาคลาสสิก — จุดร่วมไม่ใช่ "โปรแกรมเมอร์เก่งไม่พอ" แต่คือกระบวนการและความรับผิดชอบที่หายไป

Therac-25 (1985–1987)

เกิดอะไร: เครื่องฉายรังสีรักษามะเร็งให้ปริมาณรังสีเกินขนาดอย่างน้อย 6 ครั้ง มีผู้เสียชีวิต สาเหตุคือ race condition ในซอฟต์แวร์ควบคุม ขณะที่รุ่นนี้ถอด interlock ทางฮาร์ดแวร์ออกและพึ่งซอฟต์แวร์ล้วน

บทเรียน: การใช้โค้ดเดิมซ้ำโดยไม่วิเคราะห์ความปลอดภัยใหม่ · ความมั่นใจเกินจริงในซอฟต์แวร์ · รายงานอุบัติเหตุถูกมองข้าม

Ariane 5 เที่ยวบิน 501 (1996)

เกิดอะไร: จรวดระเบิดหลังปล่อยราว 37 วินาที ซอฟต์แวร์นำร่องที่ยกมาจาก Ariane 4 แปลงค่าทศนิยม 64 บิตเป็นจำนวนเต็ม 16 บิตแล้ว overflow ระบบสำรองรันโค้ดเดียวกันจึงล้มพร้อมกัน

บทเรียน: สมมติฐานของโค้ดเดิม (ช่วงค่าของ Ariane 4) ไม่ถูกทวนสอบใหม่ · การทดสอบไม่ครอบคลุมสภาพจริง · redundancy ที่ซ้ำข้อผิดพลาดเดิม

Boeing 737 MAX · MCAS (2018–2019)

เกิดอะไร: อุบัติเหตุ 2 ครั้ง มีผู้เสียชีวิต 346 คน ระบบ MCAS ปรับหัวเครื่องอัตโนมัติจากเซ็นเซอร์มุมปะทะเพียงตัวเดียว และนักบินไม่ได้รับข้อมูลเพียงพอว่าระบบนี้มีอยู่

บทเรียน: single point of failure ในระบบวิกฤต · ความโปร่งใสต่อผู้ใช้และผู้กำกับดูแล · แรงกดดันด้านเวลาและต้นทุนเหนือความปลอดภัย

จรรยาบรรณทำตามกฎของนายจ้างเป็นหลักมีหลักจริยธรรมของวิชาชีพที่อยู่เหนือคำสั่งนายจ้างACM/IEEE-CS Software Engineering Code of Ethics (1999)
การรับรอง / ใบอนุญาตไม่จำเป็นมีการรับรองความสามารถ บางสาขามีใบอนุญาตตามกฎหมายยังไม่มีใบอนุญาตบังคับในประเทศส่วนใหญ่ (ตัวอย่างเดียวคือ PE สาขา software engineering ของรัฐ Texas 1998–2019 ซึ่ง NCEES เลิกจัดสอบเพราะผู้สอบน้อย) · ที่มีคือ certification เช่น ISTQB, PSM, cloud certs
การเรียนรู้ต่อเนื่องตามความสนใจส่วนตัวเป็นหน้าที่ เพราะองค์ความรู้เปลี่ยนตลอดเวลาภาษา เฟรมเวิร์ก และแนวปฏิบัติเปลี่ยนทุก 2–3 ปี · หลักการ Self ในจรรยาบรรณ
ความรับผิดชอบต่อสาธารณะรับผิดชอบต่อลูกค้าและนายจ้างรับผิดชอบต่อสังคมและผู้ที่ได้รับผลกระทบ แม้ไม่ใช่ลูกค้าระบบสุขภาพ การเงิน การขนส่ง ข้อมูลส่วนบุคคล — ผู้ใช้ไม่มีทางตรวจสอบโค้ดเอง

วิศวกรซอฟต์แวร์

องค์ความรู้ร่วม (SWEBOK) · จรรยาบรรณของสมาคมวิชาชีพ · ยังไม่มีใบอนุญาตบังคับ — แต่ผลกระทบต่อสาธารณะไม่น้อยกว่า

ผลที่ตามมา — เมื่อกฎหมายยังไม่บังคับ ความเป็นมืออาชีพของวิศวกรซอฟต์แวร์จึงขึ้นกับวินัยของบุคคลและทีม: บันทึกสิ่งที่ตัดสินใจ ทดสอบสิ่งที่ส่งมอบ และรายงานสิ่งที่ผิดพลาด

1Software Requirementsเก็บ วิเคราะห์ ระบุ และตรวจสอบความต้องการuser story · acceptance criteria · Plane work item / Intakeแตะ
2Software Architecture ใหม่โครงสร้างระดับระบบและการตัดสินใจเชิงสถาปัตยกรรมC4 model · ADR (architecture decision record)
3Software Designออกแบบส่วนประกอบ อินเทอร์เฟซ และรูปแบบการแก้ปัญหาUML · design doc ใน Plane Pagesแตะ
4Software Constructionเขียนโค้ด unit test debug และ integrateGit · IDE · linter · pre-commitแตะ
5Software Testingวางแผน ออกแบบ และรันการทดสอบทุกระดับpytest · Playwright · CI pipelineแตะ
6Software Engineering Operations ใหม่deploy รัน และเฝ้าระวังระบบในสภาพจริงDocker Compose · CI/CD · logs และ metrics
7Software Maintenanceแก้ไขและปรับปรุงหลังส่งมอบissue tracker · changelog · semantic versioning
8Software Configuration Managementควบคุมเวอร์ชัน build และ releaseGit branch/tag · release notes
9Software Engineering Managementวางแผน ประเมิน ติดตาม และวัดผลโครงการPlane cycles · burndown · estimatesแตะ
หมายเหตุ — SWEBOK v3 (2014) มี 15 KA; v4 (2024) เพิ่ม Architecture, Operations และ Security เป็น 18 KA · แท็ก "แตะ" = KA ที่วิชานี้ฝึกผ่าน Plane โดยตรง

มืออาชีพวัดจาก พฤติกรรมที่สังเกตได้ ไม่ใช่จากตำแหน่ง

  • Technical competenceเลือกเครื่องมือได้ด้วยเหตุผล ทดสอบก่อนอ้างว่าเสร็จ
  • Ethics & responsibilityรายงานปัญหาทันทีแม้เป็นความผิดของตัวเอง
  • Communication & teamworkเขียน work item ที่คนอื่นทำต่อได้โดยไม่ต้องถาม
  • Continuous learningมี roadmap ของตัวเอง อ่าน source code และ retro ทุกรอบ
  • Quality & craftsmanshipโค้ดสะอาด commit เล็ก ขอ review และรับ review อย่างเปิดใจ
  • Transparency & traceabilityการตัดสินใจทุกครั้งมีร่องรอย: comment · commit · PR · activity log

Technical competenceทดสอบก่อนบอกว่าเสร็จ · เลือกเครื่องมือด้วยเหตุผลที่อธิบายได้"บนเครื่องผมรันได้" · เพิ่ม dependency เพราะเห็นในบล็อกลิงก์ผล test / CI แนบใน work item

Transparency & traceabilitystate บนบอร์ดตรงกับความจริงวันนี้ · ทุก PR อ้าง key ของ work itemIn Progress ค้างสามสัปดาห์ · ปิดงานโดยไม่มีหลักฐานactivity log · state ตรงกับสถานะ PR

1 Publicทำงานโดยยึดประโยชน์สาธารณะ1.03 อนุมัติซอฟต์แวร์เมื่อเชื่อได้อย่างมีเหตุผลว่าปลอดภัย ตรงสเปก และผ่านการทดสอบที่เหมาะสม
2 Client & Employerทำเพื่อประโยชน์ของลูกค้าและนายจ้าง โดยไม่ขัดประโยชน์สาธารณะ2.05 รักษาความลับที่รู้จากงาน · 2.06 รายงานทันทีเมื่อเห็นว่าโครงการมีแนวโน้มล้มเหลวหรือแพงเกินไป
3 Productผลิตภัณฑ์และการแก้ไขต้องได้มาตรฐานสูงสุดเท่าที่เป็นไปได้3.09 ประเมินต้นทุน เวลา และคุณภาพอย่างสมจริง พร้อมระบุระดับความไม่แน่นอน · 3.10 ทดสอบ ดีบัก และรีวิวอย่างเพียงพอ
4 Judgmentรักษาความซื่อตรงและความเป็นอิสระในการตัดสินใจทางวิชาชีพ4.01 ให้คุณค่าของมนุษย์กำกับการตัดสินใจทางเทคนิคทุกครั้ง
5 Managementผู้บริหารต้องยึดและส่งเสริมแนวทางที่มีจริยธรรม5.05 ประเมินอย่างสมจริงในฐานะผู้บริหาร (คู่กับ 3.09) · 5.11 ไม่สั่งให้วิศวกรทำสิ่งที่ขัดกับจรรยาบรรณ
6 Professionส่งเสริมความซื่อสัตย์และชื่อเสียงของวิชาชีพ6.13 รายงานการละเมิดจรรยาบรรณที่ร้ายแรงต่อผู้มีอำนาจ เมื่อการพูดคุยกับผู้เกี่ยวข้องเป็นไปไม่ได้หรืออันตราย
7 Colleaguesยุติธรรมและสนับสนุนเพื่อนร่วมวิชาชีพ7.03 ให้เครดิตงานของผู้อื่นอย่างเต็มที่ · 7.04 รีวิวงานของผู้อื่นอย่างเป็นกลาง ตรงไปตรงมา และมีบันทึก
8 Selfเรียนรู้ตลอดชีวิตและส่งเสริมแนวทางที่มีจริยธรรม8.02 พัฒนาความสามารถในการสร้างซอฟต์แวร์ที่ปลอดภัย เชื่อถือได้ และมีประโยชน์ ในต้นทุนและเวลาที่สมเหตุสมผล

Aเร่งส่งงานโดยตัดการทดสอบ

ผู้จัดการขอให้ข้าม integration test เพื่อให้ทัน demo วันศุกร์ โดยบอกว่า "ค่อยทดสอบทีหลัง" ระบบนี้เชื่อมกับการชำระเงินของลูกค้า

Bลูกค้าขอให้ปกปิดบั๊ก

ทีมพบว่าฟีเจอร์คำนวณดอกเบี้ยให้ผลผิดในบางกรณี ลูกค้าขอให้ "ไม่ต้องบันทึกไว้ในรายงานส่งมอบ" เพราะกลัวผู้บริหารตำหนิ

Cข้อมูลส่วนบุคคลของผู้ใช้

เพื่อนร่วมทีมคัดลอกฐานข้อมูล production ที่มีชื่อ อีเมล และเบอร์โทรของผู้ใช้ มาใช้ทดสอบบนเครื่องส่วนตัว เพราะ "สร้างข้อมูลปลอมเสียเวลา"

ลด scope · เลื่อนกำหนด · ใช้ข้อมูลสังเคราะห์ — ให้ผู้ตัดสินใจมีทางไปที่ถูกต้อง

3บันทึกเป็นลายลักษณ์อักษร

ความเสี่ยงและคำตัดสินใจอยู่ใน work item หรืออีเมล ไม่ใช่บทสนทนาที่หายไป

หัวหน้าทีม → ผู้บริหาร → หน่วยงานกำกับ เมื่อความปลอดภัยของสาธารณะถูกกระทบ

ความเป็นมืออาชีพ มองเห็นได้จากบอร์ด ทุกวัน

1บันทึกทันที

งานใหม่ บั๊ก หรือคำขอ ลงเป็น work item ตอนที่รู้ ไม่ใช่ตอนที่ว่าง

2อัปเดต state ทุกวัน

บอร์ดต้องสะท้อนความจริง ณ วันนี้ ไม่ใช่ความจริงของสัปดาห์ก่อน

3comment การตัดสินใจ

เลือกทางไหน เพราะอะไร ปฏิเสธทางไหน — เขียนไว้ที่ work item ไม่ใช่ในแชต

4แนบหลักฐาน

ลิงก์ PR ภาพหน้าจอ ผลการทดสอบ log — ให้คนอื่นตรวจได้โดยไม่ต้องเชื่อคำพูด

5ปิดงานพร้อมผล

ย้ายไป Done เมื่อผ่าน acceptance criteria และ DoD จริง พร้อมสรุปสั้น ๆ ว่าได้อะไร

6ไม่แชร์ token

API token และรหัสผ่านผูกกับคนเดียว ตั้งวันหมดอายุ ไม่ใส่ในโค้ดหรือแชต

7ประเมินใหม่เมื่อรู้มากขึ้น

estimate เปลี่ยนได้เมื่อเข้าใจงานมากขึ้น — ปล่อยตัวเลขเดิมไว้ทั้งที่รู้ว่าผิด เท่ากับโกหกแผน

8retro ทุกรอบ

ปิด cycle ด้วยการทบทวนกระบวนการ แล้วเปลี่ยนสิ่งที่ตกลงกันเป็น work item

ลึกหนึ่งด้าน กว้างพอจะทำงานกับทุกคน — และไม่หยุดเรียน

  • T-shaped: แนวตั้งคือความเชี่ยวชาญลึก แนวนอนคือความรู้กว้างพอจะคุยกับ tester, ops และ productทีม Agile ต้องการคนที่รับงานข้ามบทบาทได้ ไม่ใช่ผู้เชี่ยวชาญที่ทำได้เรื่องเดียว
  • Roadmap ส่วนตัว: เลือก 1 KA ของ SWEBOK ต่อภาคเรียน แล้วตั้งเป้าที่วัดได้เช่น "เขียน integration test ให้ทุก endpoint ที่ตัวเองสร้าง"
  • Kaizen: ปรับปรุงเล็ก ๆ ต่อเนื่อง ดีกว่าปฏิวัติปีละครั้งretrospective ทุก cycle คือ Kaizen ของทีม; เลือกแก้ 1–2 เรื่องต่อรอบ
  • อ่าน source code ของ open source: วิธีเรียนรู้ที่ถูกที่สุดจากวิศวกรที่เก่งกว่าดู test, commit history และ pull request discussion ไม่ใช่แค่โค้ด
  • สอนคนอื่นและเขียนสิ่งที่เรียนรู้: ความรู้ที่อธิบายไม่ได้คือความรู้ที่ยังไม่แน่นretro note · README · comment ใน work item ที่คนถัดไปทำต่อได้
