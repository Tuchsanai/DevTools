ตอนที่ 3 · Continuous Improvement · นิยาม

Continuous Improvement — ปรับกระบวนการทีละน้อยจากหลักฐานจริง

Kaizen / PDCA ทำให้ทุก Cycle เป็นทั้งรอบส่งมอบงานและรอบเรียนรู้ว่า “ครั้งหน้าจะทำให้ดีขึ้นอย่างไร”
Continuous Improvement คือการ วัดผล · ทบทวนสาเหตุ · เลือกการเปลี่ยนแปลงเล็ก ๆ · ทดลองในรอบถัดไป แล้ววัดซ้ำ เพื่อให้กระบวนการดีขึ้นอย่างต่อเนื่องโดยไม่อาศัยความรู้สึกล้วน ๆ

ปัญหาที่แก้ · ก่อน

ปัญหาเดิมเกิดซ้ำ: Review ค้าง · งานย้ายข้าม Sprint · Retro คุยดีแต่จบแล้วไม่มีเจ้าของหรือวันตรวจผล

ทำไมสำคัญ · หลัง

ทีมเห็นสัญญาณจากข้อมูล เลือกแก้เพียง 1–2 เรื่อง ทำเป็นงานจริง แล้วเทียบตัวชี้วัดก่อน–หลังในรอบถัดไป

ตัวอย่าง · CampusEats — ตอน Retro มีงานเดิมไม่เสร็จ 4 ใบ; หลังสร้าง action item จึง Transfer ไป Sprint 2 รวม 5 ใบ ทีมทดลองกติกา “ช่วยปิดงานที่เริ่มแล้วก่อนเริ่มใบใหม่” แล้ววัดจำนวนงานโอนและ Cycle time อีกครั้งเมื่อจบ Sprint 2
ทีมเปลี่ยนข้อสังเกตจากข้อมูลให้เป็นการทดลองขนาดเล็กที่มีเจ้าของและวัดผลได้

ความเข้าใจผิด · ❌ เปลี่ยนทุกอย่างตลอดเวลา

✅ เปลี่ยนทีละน้อยอย่างมีสมมติฐาน รักษาสิ่งที่ได้ผล และรอหลักฐานจากรอบถัดไปก่อนสรุป — ความต่อเนื่องอยู่ที่ วงจรเรียนรู้ ไม่ใช่จำนวนสิ่งที่เปลี่ยน

ตอนที่ 3 · Continuous Improvement · กลไก

วงจร Kaizen / PDCA — วัด → ทบทวน → ตัดสินใจ → ลงมือ → วัดซ้ำ

หนึ่ง Sprint หรือ Cycle ทำหน้าที่เป็นหนึ่งรอบทดลอง: ปัญหาต้องมีหลักฐาน และ action item ต้องกลับเข้าแผนงานจริง
PDCA: Plan = เลือกการทดลอง · Do = ทำในรอบถัดไป · Check = วัดและทบทวน · Act = เก็บวิธีที่ได้ผลหรือปรับสมมติฐานแล้ววนใหม่

1องค์ประกอบ · Measure

เลือก 1–3 สัญญาณที่ตรงปัญหา เช่น burndown · Cycle time · CFD · จำนวนงานโอนไปรอบถัดไป แล้วเก็บค่าเริ่มต้นไว้เทียบ

2องค์ประกอบ · Retrospective

Start / Stop / Continue ถามว่าจะเริ่ม เลิก และทำต่ออะไร · 4Ls ถาม Liked · Learned · Lacked · Longed for เพื่อหาสาเหตุร่วมกัน

3องค์ประกอบ · Action item

เลือกเพียง 1–2 ข้อ เขียนให้มีเจ้าของ เงื่อนไขสำเร็จ และตัวชี้วัดที่จะตรวจ; สร้างเป็น work item แล้วใส่ใน Cycle ถัดไป

Workflow ที่ปิดวงจร — Metric บอก “เกิดอะไร” → Retro ถาม “เพราะอะไร” → Action item ระบุ “จะลองเปลี่ยนอะไร” → รอบถัดไปตอบ “ดีขึ้นจริงหรือไม่” หากไม่มีเจ้าของ งานในแผน และวันวัดซ้ำ นั่นคือบทสนทนา ไม่ใช่การปรับปรุง

สร้าง Page “Sprint 2 Retro” แล้วบันทึก metric · Start/Stop/Continue หรือ 4Ls · สาเหตุ · การตัดสินใจ เพื่อไม่ให้เหตุผลหายไปหลังประชุม

3Act · Work item + label

เปลี่ยน action item เป็น work item มี assignee และ acceptance criteria ติด label improvement ที่ทีมสร้างเอง แล้วเลือกเข้า Cycle ถัดไป; LAB 4 ใช้ label tech-debt กับ action item ตัวอย่าง

LAB 4 · Retro บันทึก Sprint Review/Retro และทำ action item ให้เป็นงานจริง   LAB 9 · Metrics อ่าน burndown · velocity · CFD · Lead/Cycle time บน Tracking Dashboard   Mini exercise — เลือก metric ที่แย่ลง 1 ค่า เขียน action item แบบ “เจ้าของ + การทดลอง + เกณฑ์สำเร็จ” แล้วบอกว่าจะวัดซ้ำเมื่อใด
