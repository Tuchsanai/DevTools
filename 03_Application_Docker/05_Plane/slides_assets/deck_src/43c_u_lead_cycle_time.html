Lead time กับ Cycle time — นับงานใบเดียวกัน แต่เริ่มคนละจุด

ทั้งคู่คือเวลาที่ผ่านไปจริงจนงานเสร็จ จึงรวมเวลารอด้วย — ช่วยแยกว่า “ลูกค้ารอนาน” เพราะค้างก่อนเริ่ม หรือเพราะขั้นตอนทำงานช้า
CampusEats · PLAB-12: สร้าง 03/08 09:00 → เริ่ม 05/08 10:00 → เสร็จ 07/08 16:00 จึงมี Lead time 4 วัน 7 ชม. และ Cycle time 2 วัน 6 ชม.

Lead time · มุมลูกค้า

ตั้งแต่รับคำขอหรือสร้าง work item จน Done — รวมเวลารอใน backlog ก่อนทีมเริ่มทำ

Cycle time · มุมทีม

ตั้งแต่เข้า state กลุ่ม started ครั้งแรกจน Done — ใช้ดูความเร็วของระบบหลังเริ่มงาน

P85 · เห็นปลายหาง

ค่าที่งาน 85% เสร็จไม่เกินค่านี้ เหมาะกับคำถาม “ส่วนใหญ่ต้องรอกี่วัน” เพราะงานช้ามากไม่กี่ใบทำให้ค่าเฉลี่ยเพี้ยนได้

เข้าใจผิด — Cycle time ไม่ใช่ชั่วโมงที่ลงมือเขียนโค้ดล้วน ๆ; เวลารอ Review หรือ Test หลังเริ่มงานยังอยู่ใน Cycle time

Flow metrics ทำงานร่วมกัน — อยากให้งานออกเร็วขึ้น ให้ลดงานที่ค้าง

  • Lead time — ตั้งแต่ลูกค้าขอ (สร้าง) จน Done; สิ่งที่ลูกค้ารับรู้
  • Cycle time — ตั้งแต่เริ่มลงมือ (In Progress) จน Done; สิ่งที่ทีมควบคุมได้
  • Throughput — จำนวนงานที่ Done ต่อหน่วยเวลา เช่น 3 ใบ/วัน
  • WIP — งานที่เริ่มแล้วแต่ยังไม่ Done ในขณะหนึ่ง
  • Flow efficiency — เวลาที่ถูกทำจริง ÷ lead time; ทำจริง 6 ชม. จาก 32 ชม.ทำงาน ≈ 19% (ที่เหลือคือรอ)
Little's Law — Lead time เฉลี่ย ≈ WIP ÷ Throughput (ระบบต้องนิ่ง) · WIP 12 ÷ 3 ใบ/วัน = รอ 4 วัน; ลด WIP เหลือ 6 → รอ 2 วัน โดยไม่ต้องเพิ่มคน

Plane เก็บ “ร่องรอยเวลา” — แล้ว LAB คำนวณ metric เอง

Plane CE v1.4.2 ไม่มี Lead/Cycle time ที่คำนวณไว้ล่วงหน้าหรือกราฟสำเร็จรูป แต่มีข้อมูลต้นทางครบเมื่อทีมย้าย state ตามงานจริง
Activity ของ work item · ผู้กระทำ เวลา และรายการเปลี่ยน state คือหลักฐานสำหรับหาเวลาเริ่มทำครั้งแรก
จุดเวลาข้อมูลใน Plane
รับคำขอissues.created_at
เริ่มทำครั้งแรกissue_activities ที่ field='state' แล้ว new_identifier ชี้ไปยัง state กลุ่ม started
เสร็จissues.completed_at ถูกตั้งเมื่อเข้า state กลุ่ม completed

สูตรที่สคริปต์ใช้

Lead = completed_at − created_at
Cycle = completed_at − เวลาเข้า started ครั้งแรก
