State groups — คอลัมน์ตั้งเองได้ แต่ต้องสังกัด 1 ใน 5 กลุ่ม

state groupstate เริ่มต้นความหมายต่อ metrics
backlogBacklog defaultยังไม่ตัดสินใจทำ ไม่นับใน WIP
unstartedTodoเลือกแล้ว รอเริ่ม (จุดเริ่ม lead time ถ้านับจากที่นี่)
startedIn Progress= WIP; จุดเริ่ม cycle time
completedDoneเข้ากลุ่มนี้ → ตั้ง completed_at → burndown ลด
cancelledCancelledปิดโดยไม่ทำ ไม่นับเป็นความคืบหน้า

มีกลุ่มที่ 6 triage ซ่อนอยู่สำหรับ Intake; state ที่เป็น default หรือยังมีงานอยู่ลบไม่ได้ · ชื่อ state ต้องไม่ซ้ำในโปรเจกต์ · ย้ายออกจาก completed แล้ว completed_at กลับเป็นค่าว่าง

CE ไม่มี WIP limit และ workflow rule

ลากการ์ดจาก state ใดไป state ใดก็ได้ ไม่มีเงื่อนไข ไม่มีตัวเลขจำกัดต่อคอลัมน์ ("Automations and workflows" อยู่ในแผนเสียเงิน) — ทีมต้องบังคับด้วย policy ที่เขียนไว้ + สคริปต์ตรวจผ่าน API (LAB 5)

เทียบ Jira workflow

Jira นิยาม transition ระหว่าง status พร้อม condition / validator / post-function และตั้ง WIP limit ต่อคอลัมน์บนบอร์ดได้ — ยืดหยุ่นแต่ตั้งค่าซับซ้อน Plane เลือกความเรียบง่าย: state group 5 กลุ่มคือ "workflow" ขั้นต่ำที่ทุกโปรเจกต์ใช้ร่วมกัน

Automations ที่ CE มี

auto-archive งานที่ปิดแล้วนานเกิน 1–12 เดือน และ auto-close งานที่ไม่ขยับไปยัง state กลุ่ม cancelled — ทำงานผ่าน Celery beat เวลา 01:00 UTC (≈08:00 น. ไทย)

Cycle คือ Sprint ของ Plane — วันที่ · progress · burndown ที่คำนวณจาก completed_at

แผง Progress ของ cycle: เส้นทึบ = งานที่เหลือจริง, เส้นประ = ideal; สลับ Work items / Estimates ได้ (ต้องเปิด Cycles ที่ Settings › Projects › Features ก่อน)
  • Cycle มีแค่ start_date / end_date ไม่มีคอลัมน์สถานะ — In progress / Yet to start / Completed / Draft คำนวณจากวันที่ตอน query (timezone ของโปรเจกต์)
  • Active cycle = cycle ที่วันนี้อยู่ในช่วง — แผง Progress, Work item burndown, สถิติตาม priority / assignee / label อยู่ในหน้า Cycles ของโปรเจกต์; เมนู Active cycles ระดับ workspace ใน CE เป็นหน้า upsell
  • Progress นับ work items ต่อ state group (backlog / unstarted / started / completed / cancelled) และผลรวม points
  • Burndown: remaining(วัน) = total − Σ งานที่ completed_at ≤ วันนั้น; วันในอนาคตเป็น null · ideal = total × (1 − i/(n−1))
  • CE มีเฉพาะ burndown — ตัวเลือก Burn-up มีในโค้ดแต่ไม่ได้ต่อกับ UI; อยากได้ burn-up ต้องคำนวณเองจาก completed_at ของแต่ละใบ (cycle_report.py ใน LAB 4 คำนวณ burndown ด้วยสูตรเดียวกับ Plane)
  • จบ cycle แล้วงานที่ค้างใช้ Transfer ไป cycle ถัดไป (เก็บ snapshot ของสถิติเดิม) — ปุ่มนี้แสดงเฉพาะ cycle ที่ Completed (end_date ผ่านแล้ว)
  • ปฏิทินใน UI ไม่ให้เลือกวันในอดีต — cycle ที่ต้องเริ่มย้อนหลัง (เช่นใน LAB 4) สร้าง/แก้ผ่าน REST API
# app API ที่เบราว์เซอร์ใช้ (session cookie) — ไม่ใช่ /api/v1 ของ API key
GET /api/workspaces/<slug>/projects/<project_id>/cycles/<cycle_id>/analytics/?type=issues   (หรือ type=points)
{ "completion_chart": { "2026-09-01": 12, "2026-09-02": 10, "2026-09-03": 7, …, "2026-09-14": null }, "assignees": [...], "labels": [...] }
GET /api/workspaces/<slug>/projects/<project_id>/cycles/<cycle_id>/progress/   → จำนวนงานและ points ต่อ state group

ตอนที่ 3 · Anti-patterns

สิ่งที่มักพัง — บอร์ดสวยแต่ทีมไม่ได้ทำ Agile

1Mini-waterfall

ใน sprint 2 สัปดาห์: สัปดาห์แรกทุกคนเขียนโค้ด สัปดาห์สอง test ทั้งหมด — burndown ราบแล้วดิ่งตอนท้าย แก้: แตกงานให้แต่ละใบ Done ได้ใน 1–2 วัน

2Zombie Scrum

มีอีเวนต์ครบแต่ไม่มีผล: Daily เป็นการรายงานหัวหน้า Review ไม่มี stakeholder Retro ไม่มี action item แก้: ทุกอีเวนต์ต้องจบด้วยการตัดสินใจอย่างน้อยหนึ่งข้อ

3WIP ระเบิด

คนละ 4–5 ใบใน In Progress ทุกอย่าง "เกือบเสร็จ" แต่ไม่มีอะไร Done แก้: ตกลง WIP limit ต่อคน ต่อคอลัมน์ และให้สคริปต์แจ้งเตือนเมื่อเกิน

4Velocity เป็น KPI

ผู้บริหารตั้งเป้า "sprint หน้าต้อง 25" → ทีมประเมินเฟ้อ ตัด test ออกจาก DoD ตัวเลขขึ้นแต่ผลิตภัณฑ์แย่ลง แก้: วัดผลลัพธ์ต่อผู้ใช้ (outcome) ไม่ใช่ output

5บอร์ดไม่อัปเดต

คุยกันใน chat แล้วค่อยมาย้ายการ์ดตอนสิ้นสัปดาห์ — burndown, activity log, lead time ทั้งหมดผิด แก้: "ถ้าไม่อยู่บนบอร์ด ถือว่ายังไม่เกิด" และย้ายการ์ดตอน Daily Scrum

6ทุก work item เป็น Urgent

priority ถูกตั้งเป็น urgent เกือบทั้ง backlog จนไม่มีความหมาย ทีมเลือกงานตามความคุ้นเคยแทน แก้: PO จัดลำดับเดียว (sort order) และจำกัด urgent ให้ตรงกับ class of service Expedite

ตรวจจับได้จากข้อมูลใน Plane — burndown ที่ราบ (1), activity log ที่ว่างหลายวันแล้วมีการย้ายการ์ดเป็นชุด (5), จำนวน work items ใน started ต่อ assignee (3), สัดส่วน urgent ใน Analytics (6)

สรุปตอนที่ 3 — จากทฤษฎี Scrum & Kanban สู่ LAB 4–5

  • Agile คือการย่นระยะระหว่างตัดสินใจกับเห็นผลจริง4 คุณค่า 12 หลักการ — เครื่องมือต้องรับใช้หลักการ ไม่ใช่กลับกัน
  • Scrum = 3 บทบาท · 5 อีเวนต์ · 3 อาร์ติแฟกต์ + commitmentวัดด้วย velocity และ burndown; DoD คือหัวใจของคำว่า Done
  • Kanban = visualize, limit WIP, manage flowLittle's Law: ลด WIP แล้ว lead time สั้นลงโดยไม่ต้องเพิ่มคน
  • Plane: Cycle = sprint, states 5 กลุ่ม, Board + swimlanes, Estimates, PageCE ไม่มี WIP limit / workflow rule — ทีมต้องมี policy และสคริปต์
  • metrics ของ Plane คำนวณจาก completed_at และ state groupข้อมูลดีได้เท่ากับวินัยในการย้ายการ์ดบนบอร์ด
คำถามทบทวน — (1) ทำไม burndown ของ Plane ถึงต้องพึ่ง completed_at ไม่ใช่ประวัติ state (2) ถ้า throughput 5 ใบ/วัน และ WIP 20 ใบ lead time เฉลี่ยเท่าไร (3) Sprint Goal ต่างจากรายการงานใน Cycle อย่างไร
