Kanban — ทำให้งานไหลจาก “รอ” ไปสู่ “เสร็จ”

“Kanban คือวิธีปรับปรุง flow โดยทำให้งานมองเห็น จำกัดงานที่เริ่มแล้ว และดึงงานใหม่เมื่อระบบมีความจุ”
เป้าหมายไม่ใช่ให้ทุกคน ยุ่งตลอดเวลา แต่ให้ชิ้นงาน เสร็จและส่งคุณค่าได้ต่อเนื่องflow = การเคลื่อนของงานผ่านขั้นตอนต่าง ๆ จน Done

ก่อนใช้ Kanban · งานมองไม่เห็น

คำขอกระจายใน chat · แต่ละคนเริ่มหลายใบ · งานค้างระหว่างพัฒนา ทดสอบ และ review จึงไม่มีใครรู้ว่าคอขวดอยู่ตรงไหน

หลังใช้ Kanban · เห็นทั้งระบบ

การ์ดทุกใบอยู่บน workflow เดียว จำนวนงานค้างเห็นชัด และทีมดึงงานใหม่เมื่อขั้นถัดไปพร้อมรับ งานจึงจบก่อนเริ่มเพิ่ม

ทำไมสำคัญ — งานที่ค้างคือเวลาและความเสี่ยงที่ยังไม่สร้างคุณค่า การลดงานค้างช่วยให้ feedback เร็วขึ้น คอขวดโผล่เร็วขึ้น และเวลาส่งมอบคาดการณ์ได้ดีขึ้น
บอร์ดจริงทำให้งานที่กระจายอยู่ในหัวและบทสนทนากลายเป็นสถานะร่วมที่ทั้งทีมมองเห็น

จาก Toyota สู่ software — ดึงทีละใบ · จำกัด WIP · มีกติกาชัด

การ์ดเคลื่อนซ้าย → ขวา; ขั้นถัดไป “ดึง” เมื่อมีที่ว่าง หากคอลัมน์เต็ม ทีมช่วยปิดงานค้างก่อนเริ่มใบใหม่
6 practices
  • Visualise — เห็นขั้นตอน งานค้าง และเจ้าของบนบอร์ดเดียว
  • Limit WIP — จำกัดงานที่เริ่มแล้วแต่ยังไม่เสร็จ
  • Manage flow — ดูว่างานติดที่ใด แล้วลดเวลารอ
  • Explicit policies — เขียนเงื่อนไขเข้า–ออกของแต่ละคอลัมน์
  • Feedback loops — ทบทวนงานและข้อมูลตาม cadence สม่ำเสมอ
  • Improve collaboratively — ปรับระบบทีละน้อยร่วมกันจากหลักฐาน
จากป้ายสัญญาณสู่การ์ดงาน — โรงงานใช้ kanban เป็นสัญญาณให้ขั้นก่อนหน้าผลิตเมื่อขั้นถัดไปต้องการ; ทีม software ใช้พื้นที่ว่างเป็นสัญญาณดึงงาน โดยไม่ต้องเปลี่ยนบทบาทเดิมขององค์กร

CampusEats support — หยุดเริ่ม แล้วช่วยกันทำให้เสร็จ

สถานการณ์: ช่วงเที่ยงมีรายงานว่า “ชำระเงินแล้วแต่คำสั่งซื้อไม่เข้าโรงอาหาร” ทีมต้องแก้เร็วโดยไม่ทิ้งงานเดิมกลางทาง

1พบว่าคอลัมน์เต็มIn Progress มี 3/3 ใบแล้ว จึงยังไม่ดึงปัญหาใหม่เข้าไป แม้ใบนี้มีความสำคัญสูง
2ช่วยปิดงานที่ใกล้เสร็จนักพัฒนาช่วย review ใบเดิมให้พ้นคอขวด เกิดช่องว่าง 1 ตำแหน่งในระบบ
3ดึงและส่งมอบดึงบั๊ก CampusEats จาก Ready ไปทำ ทดสอบ review และยืนยันกับผู้แจ้งก่อน Done
การวางแผนแบบ Kanban — ทีมยังจัดลำดับ backlog และทำ replenishment เพื่อเติม Ready; ความต่างคือเลือกเริ่มงานตามความจุจริง ไม่ผูกกับ sprint ที่ตายตัว

❌ “Kanban คือบอร์ดที่มีคอลัมน์”

บอร์ดที่ไม่มี WIP limit, pull, policy และการวัด flow เป็นเพียงภาพสถานะ งานอาจกองเต็มทุกคอลัมน์เหมือนเดิม

✅ ที่ถูก: บอร์ดช่วยให้เห็น ส่วนทีมต้องหยุดดึงเมื่อเต็มและช่วยแก้คอขวด

❌ “Kanban ไม่มีการวางแผน”

✅ Kanban วางแผนแบบต่อเนื่อง: จัดลำดับงาน เติมคิว Ready และทบทวนนโยบายตาม cadence แทนการรอ Sprint Planning
