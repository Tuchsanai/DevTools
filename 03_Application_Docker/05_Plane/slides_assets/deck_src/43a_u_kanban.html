Kanban — ทำให้งานไหลจาก “รอ” ไปสู่ “เสร็จ”

ไม่ใช่กรอบงานที่ต้องรื้อทีมใหม่ แต่เป็นวิธีมองงานที่ทำอยู่แล้วให้เห็นชัด แล้วค่อย ๆ ปรับให้ไหลดีขึ้นจากหลักฐาน
นิยาม — Kanban คือกลยุทธ์สำหรับปรับการไหลของคุณค่าผ่านกระบวนการหนึ่งให้ดีที่สุด โดยใช้ระบบที่มองเห็นได้และดึงงาน (pull)— Kanban Guide · เป้าหมายคือให้ชิ้นงานเสร็จต่อเนื่อง ไม่ใช่ให้ทุกคนยุ่งตลอดเวลา

ปัญหา · ก่อนใช้ Kanban

คำขอกระจายในแชต · แต่ละคนเริ่มหลายใบ · งานค้างระหว่างพัฒนา ทดสอบ และรีวิว จึงไม่มีใครรู้ว่าคอขวดอยู่ตรงไหน

ผลลัพธ์ · หลังใช้ Kanban

การ์ดทุกใบอยู่บน workflow เดียว ทีมมองเห็นงานค้างและดึงงานใหม่เมื่อขั้นถัดไปพร้อมรับ จึงทำงานให้เสร็จก่อนเริ่มเพิ่ม

ทำไมสำคัญ — งานที่ค้างคือเวลาและความเสี่ยงที่ยังไม่สร้างคุณค่า การลดงานค้างทำให้ feedback มาเร็วขึ้น เห็นคอขวดเร็วขึ้น และคาดการณ์เวลาส่งมอบได้ดีขึ้นโดยไม่ต้องเพิ่มคน
4 หลักการพื้นฐาน — ① เริ่มจากสิ่งที่ทีมทำอยู่ตอนนี้ ② ตกลงกันว่าจะเปลี่ยนแบบค่อยเป็นค่อยไป ③ เคารพกระบวนการ บทบาท และตำแหน่งเดิม ④ ส่งเสริมภาวะผู้นำในทุกระดับ — Kanban จึงเริ่มใช้ได้ในวันจันทร์ ต่างจากการเปลี่ยนไปใช้ Scrum ที่ต้องนิยามบทบาทและอีเวนต์ใหม่
บอร์ดจริงทำให้งานที่กระจายอยู่ในหัวและบทสนทนากลายเป็นสถานะร่วมที่ทั้งทีมมองเห็น

จาก Toyota สู่ซอฟต์แวร์ — ดึงตามความจุ · จำกัด WIP · มีกติกาชัด

Workflow · การ์ดเดินซ้าย → ขวา และขั้นถัดไปเป็นฝ่าย “ดึง” เมื่อมีที่ว่าง — ในภาพ In Progress เต็ม 3/3 จึงหยุดดึง ส่วน Review ยังว่าง (1/2) · แถบใต้ทุกคอลัมน์คือ explicit policy = เงื่อนไขที่ต้องจริงก่อนการ์ดจะเข้าคอลัมน์นั้น
องค์ประกอบ · 6 practices
  • Visualize — ทำให้งานทุกใบและทุกขั้นตอนปรากฏบนบอร์ดเดียว
  • Limit WIP — ตั้งเพดานงานที่เริ่มแล้วแต่ยังไม่เสร็จ
  • Manage flow — ดูว่างานติดตรงไหน แล้วลดเวลารอ ไม่ใช่เร่งคน
  • Make policies explicit — เขียนเงื่อนไขเข้า–ออกให้ทุกคนเห็น
  • Feedback loops — มีรอบทบทวนงานและตัวเลขตาม cadence
  • Improve collaboratively — ปรับระบบร่วมกันแบบทดลอง วัดผล แล้วปรับต่อ
จากป้ายสัญญาณสู่การ์ดงาน — kanban ในสายการผลิตของ Toyota คือป้ายที่ส่งสัญญาณให้ขั้นก่อนหน้าผลิตเมื่อขั้นถัดไปใช้ของไป ทีมซอฟต์แวร์ใช้ “ช่องว่างในคอลัมน์” เป็นป้ายนั้น: มีที่ว่างจึงดึงงานใหม่ได้

1คอลัมน์เต็ม จึงยังไม่ดึงIn Progress มีอยู่ 3/3 ใบตามเพดานที่ทีมประกาศไว้ บั๊กใบนี้จึงรออยู่ที่ Ready — จะแซงคิวได้ก็ต่อเมื่อประกาศเป็น Expedite (Priority = Urgent) ซึ่งมีได้ครั้งละ 1 ใบทั้งบอร์ด
2เปิดช่องจากขวาไปซ้ายDaily kanban เดินบอร์ด Done ← In Review ← In Progress: เคลียร์คิวรีวิวก่อน แล้วดันใบที่ใกล้เสร็จออกจาก In Progress จนเหลือที่ว่าง 1 ช่อง
3ดึงแล้วส่งมอบดึงบั๊กไปแก้พร้อมเพิ่ม test → ผ่านรีวิวของคนที่ไม่ใช่ผู้ทำ → ยืนยันกับผู้แจ้ง แล้วจึงย้ายเป็น Done
Cadences ของทีม (feedback loops) — Daily kanban ทุกวัน 10:00 เดินบอร์ดจากขวาไปซ้าย · Replenishment สัปดาห์ละครั้ง เติม Ready เท่าที่ throughput รับไหว · Intake triage ตอบทุกใบภายใน 1 วันทำการ — ใบที่ตัดสินใจไม่ทำต่อจบที่ Cancelled พร้อมเหตุผล ไม่ปล่อยค้างบนบอร์ด

❌ “Kanban คือบอร์ดที่มีคอลัมน์”

บอร์ดที่ไม่มี WIP limit, การดึงงาน, policy และการวัด flow เป็นเพียงภาพสถานะ — งานยังกองเต็มทุกคอลัมน์ได้เหมือนเดิม

✅ ที่ถูก: บอร์ดคือครึ่งเดียว อีกครึ่งคือกติกา: เต็มแล้วหยุดดึง แล้วไปช่วยแก้คอขวด

❌ “Kanban ไม่มีการวางแผน”

ไม่มี Sprint Planning ไม่ได้แปลว่าไม่วางแผน

✅ ที่ถูก: Kanban วางแผนแบบต่อเนื่องตาม cadence — จัดลำดับ backlog, เติมคิว Ready, ทบทวนนโยบายและตัวเลข flow; งานเริ่มเมื่อมีความจุจริง ไม่ต้องรอต้นรอบ
