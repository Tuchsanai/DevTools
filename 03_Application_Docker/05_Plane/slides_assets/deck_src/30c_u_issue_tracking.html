Issue คือ หน่วยความจำของงานที่ทีมตรวจสอบร่วมกันได้

ไม่ใช่เพียงข้อความว่า “ช่วยทำหน่อย” แต่เป็นบันทึกหนึ่งหน่วยที่ระบุงาน ผู้รับผิดชอบ สถานะ และประวัติไว้ในที่เดียว
“Issue คือบันทึกงานหนึ่งหน่วยที่บอกว่า ต้องทำอะไร · ใครรับผิดชอบ · ตอนนี้อยู่ขั้นไหน · เคยเปลี่ยนอะไรไปแล้ว”

ก่อนมี tracker

คำขอกระจายใน chat · email · spreadsheet บางเรื่องถูกลืม หลายคนทำซ้ำ และคำถาม “ใครกำลังทำอะไร” ต้องถามใหม่ทุกครั้ง

เมื่อมี tracker

ทุกคนอ้างถึงงานใบเดียวกัน เห็นเจ้าของและสถานะล่าสุด ติดตามเหตุผลย้อนหลังได้ และใช้รายการเดียวเป็น single source of truth

ทำไมสำคัญ — Issue tracking เปลี่ยนความจำของบุคคลให้เป็นความจำขององค์กร: ส่งต่องานได้ รับผิดชอบได้ และไม่สูญหายเมื่อคนออกจากห้องสนทนาหรือออกจากทีม
คำขอจากผู้ใช้เริ่มเป็นงานที่ติดตามได้เมื่อถูกบันทึกเป็น issue ไม่ใช่ค้างอยู่ในบทสนทนา

หนึ่ง issue เดินทางอย่างไร — รับเข้า · ตัดสินใจ · ทำ · ตรวจ · ปิด

วงจรทำให้คำขอทุกชิ้นมี “ขั้นถัดไป” ที่มองเห็นได้ ส่วนข้อมูลประกอบทำให้คนรับช่วงต่อเข้าใจตรงกัน
แถวบน = lifecycle เชิงแนวคิด · แถวล่าง = state groups ของ Plane; Intake เก็บผล reject/duplicate/snooze แยก และ accept จึงย้ายงานออกจาก triage

Descriptionบริบท · สิ่งที่คาดหวัง · เกณฑ์ยอมรับ
State · priorityอยู่ขั้นไหน · ควรทำก่อนหลังอย่างไร

CampusEats: จาก “เวลาไปรับหาย” สู่ บั๊กที่พิสูจน์ว่าแก้แล้ว

นักศึกษารายงานว่าเลือกโรงอาหารแล้วช่องเวลาไปรับว่าง — ทีมต้องเปลี่ยนคำบอกเล่าให้เป็นงานที่ทำซ้ำ ตรวจ และส่งมอบได้
ขั้นการตัดสินใจของทีมหลักฐานที่เพิ่มลง issueผลลัพธ์
1 · Reportรับคำแจ้งจากนักศึกษาขั้นทำซ้ำ: Android Chrome → เลือกร้าน → เลือกอาหาร → ช่องเวลาไปรับว่าง · แนบภาพหน้าจอทุกคนเห็นอาการเดียวกัน
2 · Triageทีมทำซ้ำได้ จึง acceptExpected: มีช่วงเวลาให้เลือก · Actual: รายการว่าง · label bug · priority High · assigneeเข้า backlog และมีเจ้าของ
3 · Fixแก้การอ่านเวลาจาก APIลิงก์ commit/PR · test ป้องกันบั๊กย้อนกลับ · ย้าย In progress → Reviewโค้ดพร้อมให้ตรวจ
4 · VerifyQA ทดสอบขั้นเดิมซ้ำผลบน Android Chrome ผ่าน · acceptance criteria และ Definition of Done ครบย้าย Done; ถ้ายังเสียให้ Reopen

❌ “Issue แปลว่า bug”

Issue คือหน่วยของงานทุกชนิด: feature, task, bug, research หรือคำขอ support ต่างกันที่เนื้อหาและป้าย ไม่ใช่การมี tracker คนละระบบ

❌ “กด Close แล้วแปลว่าเสร็จ”

✅ Done ต้องผ่าน Definition of Done: ผลลัพธ์ตรวจได้ test ผ่าน และผู้ใช้ได้พฤติกรรมที่ตกลงกัน การเปลี่ยนสถานะอย่างเดียวไม่สร้างคุณภาพ

หลักคิด — Issue ที่ดีทำให้คนซึ่งไม่ได้อยู่ตอนรับแจ้งสามารถทำซ้ำอาการ ลงมือแก้ และตรวจผลได้โดยไม่ต้องถามผู้รายงานใหม่

ตอนที่ 2 · Issue Tracking · ใน Plane

Plane เรียก issue ว่า Work item — รายละเอียดเดียว · ประวัติเดียว · อ้างอิงได้ตลอด

ในโปรเจกต์เลือก Work items → เปิดรายการหนึ่ง เพื่อดูรายละเอียดและ Activity ของงานใบเดียวกัน
Work item detail — description และ properties เช่น state · priority · assignee · estimate · labels · cycle · module · dates
Activity — ประวัติการเปลี่ยน state พร้อมผู้กระทำและเวลา ช่วยตรวจย้อนหลังได้

ชื่อใน UI กับฐานข้อมูล

UI ใช้คำว่า Work item; โค้ดใช้โมเดล Issue และตาราง issues งานย่อยใช้ parent อ้าง work item แม่

หมายเลขไม่ย้อนกลับ

PLAB-17 = project identifier + sequence_id; แถว IssueSequence ยังอยู่หลังลบ จึงไม่นำเลขเก่ากลับมาใช้

ฟีเจอร์ที่เชื่อมกัน

Relations บอก blocked by/relates to · comments และ attachments เก็บการสนทนา/หลักฐาน · Intake รับคำขอไว้ Triage ก่อนเข้า backlog

LAB 3 Mini exercise — เลือก feature ที่รู้จัก 1 อย่าง แล้วเขียน work item แบบมืออาชีพ: title ที่ระบุผลลัพธ์ · บริบท · acceptance criteria อย่างน้อย 3 ข้อ · priority · assignee · label · due date จากนั้นถามเพื่อนว่า “อ่านใบนี้แล้วทำและตรวจได้โดยไม่ถามผู้เขียนหรือไม่?”
