ตอนที่ 2 · ASYNC · CELERY + RABBITMQ

ทำไมต้องมี worker และ queue — งานช้าต้องไม่ทำให้ request ช้า

api ตอบผู้ใช้ทันที แล้วฝากงานที่เหลือไว้ใน queue ให้ worker ทำ — โครงสร้างเดียวกับ LAB RabbitMQ ที่เรียนมาแล้ว
  • api บันทึกลง DB แล้วโยนงานเข้า queue → ตอบ 201 ทันทีproducer → exchange → queue → consumer เหมือนที่เคยทดลอง
  • งานหลังบ้านใน Planeบันทึก activity, สร้าง notification, ยิง webhook (retry 5 ครั้ง), export CSV/XLSX/JSON, ส่งอีเมล, seed workspace
  • Celery = ตัวรันงาน · RabbitMQ = brokerไม่ตั้ง task_routes จึงมี queue เดียวชื่อ celery และไม่เก็บผลลัพธ์ (ไม่มี result backend)
  • beat-worker = นาฬิกาที่ผลิตงานตามตารางdigest อีเมลทุก 5 นาที · hard delete 00:00 UTC · ลบ export เก่า
docker compose exec plane-mq rabbitmqctl list_queues name messages consumers   # เห็น queue 'celery' และจำนวน consumer
docker compose stop worker     # สร้าง work item 2–3 ชิ้น → messages ค้างเพิ่มขึ้น
docker compose start worker    # queue ระบายจนเป็น 0 — นี่คือ backpressure ที่มองเห็นได้ (LAB 2)

Configuration as code — docker-compose.yml + plane.env

# plane.env · บรรทัดสำคัญ (ค่าเริ่มต้นจาก variables.env)
APP_DOMAIN=localhost
APP_RELEASE=stable            # tag ของ image ทุกตัว
LISTEN_HTTP_PORT=80           # พอร์ตฝั่ง host (LAB: 8080)
WEB_URL=http://${APP_DOMAIN}  # ต้องตรงกับ origin ของเบราว์เซอร์
# LAB: APP_DOMAIN=localhost:8080 → WEB_URL=http://localhost:8080
CORS_ALLOWED_ORIGINS=http://${APP_DOMAIN}
SECRET_KEY=change-this-key-on-deployment
DATABASE_URL=   # ว่าง → postgresql://plane:plane@plane-db/plane
AMQP_URL=       # ว่าง → amqp://plane:plane@plane-mq:5672/plane
USE_MINIO=1
API_KEY_RATE_LIMIT=60/minute
docker-compose.yml อ้างค่าเหล่านี้ด้วย ${VAR:-default} — ไฟล์เดียวกันจึงใช้ได้ทั้งเครื่องแล็บและเซิร์ฟเวอร์จริง
# ดูค่าที่ compose resolve แล้วก่อน up — ตรวจพอร์ตและ URL ให้ตรงกัน
docker compose --env-file plane.env config | grep -E 'published|WEB_URL|CORS_ALLOWED'
  • Config in environmentค่าที่ต่างกันตามเครื่อง (domain, port, secret) อยู่ใน env ไม่ฝังใน image
  • Backing services ต่อผ่าน URLDATABASE_URL, AMQP_URL, REDIS_URL — เปลี่ยนไปใช้ DB นอกเครื่องได้โดยไม่แก้โค้ด
  • Stateless processesapi และ worker ไม่เก็บสถานะในตัว ข้อมูลอยู่ใน Postgres/MinIO — scale เป็นหลาย replica ได้ (*_REPLICAS)
  • Logs as event streamsทุก container เขียน stdout แล้ว docker compose logs รวมให้ ไม่ต้องเข้าไปเปิดไฟล์ในเครื่อง
ข้อควรระวัง — ค่าอย่าง ENABLE_SIGNUP และ EMAIL_* ถูกอ่านจาก env เฉพาะครั้งแรกแล้วเก็บลงตาราง instance_configurations (SKIP_ENV_VAR=1) แก้ env ภายหลังจึงไม่มีผล ต้องแก้ใน god-mode

ตอนที่ 2 · APPLICATION SECURITY · พื้นฐานที่ต้องมี

ความปลอดภัยพื้นฐานของแอป และค่าเริ่มต้นของ Plane ที่ต้องแก้ก่อนใช้จริง

ประเด็นหลักการใน Plane · ค่าเริ่มต้นและสิ่งที่ต้องทำ
Secretsไม่ฝังใน image หรือโค้ด ไม่ commit ลง git หมุนเวียนได้SECRET_KEY และ LIVE_SERVER_SECRET_KEY เริ่มต้นเป็น change-this-key-on-deployment (api log ระดับ CRITICAL) รวมถึง MinIO access-key/secret-key และ RabbitMQ plane/plane ต้องเปลี่ยนก่อนใช้จริง
TLSเข้ารหัสระหว่างเบราว์เซอร์กับ proxy และตั้ง cookie เป็น SecureCaddy ขอใบรับรอง Let's Encrypt ให้อัตโนมัติเมื่อตั้ง SITE_ADDRESS=<domain> พร้อม CERT_EMAIL และเปิด LISTEN_HTTPS_PORT 443 (ค่าเริ่มต้น SITE_ADDRESS=:80 = http เท่านั้น) — origin แบบ http: ทำให้ session cookie ไม่ Secure (รับได้เฉพาะใน LAB)
Least privilegeให้สิทธิ์เท่าที่งานต้องการ แยกผู้ดูแลระบบออกจากผู้ใช้บทบาท Admin 20 / Member 15 / Guest 5 ต่อ workspace และ project, instance admin แยกใน god-mode; ALLOWED_HOSTS=* และ TRUSTED_PROXIES=0.0.0.0/0 ควรจำกัดใน production
Rate limitกันการยิงถล่มและเดารหัสผ่านAPI_KEY_RATE_LIMIT=60/minute ต่อ token (เกินได้ 429 พร้อม X-RateLimit-Remaining) และ AUTHENTICATION_RATE_LIMIT=10/minute สำหรับ sign-in / sign-up
Outbound request (SSRF)แอปที่ยิง HTTP ออกไปตาม URL ที่ผู้ใช้กรอก ต้องกันไม่ให้ยิงเข้าเครือข่ายภายในwebhook ส่งผ่าน pinned_fetch: ไม่ตาม redirect, timeout 30 s และปฏิเสธ private IP เว้นแต่อยู่ใน WEBHOOK_ALLOWED_IPS / WEBHOOK_ALLOWED_HOSTS — receiver ใน LAB 8 จึงต้องถูกใส่ใน allow-list
Session vs API keyเบราว์เซอร์ใช้ cookie + CSRF token ส่วนโปรแกรมใช้ token ใน headercookie session-id (7 วัน) และ admin-session-id (1 ชั่วโมง) กับ csrfmiddlewaretoken ในฟอร์ม; /api/v1 ใช้ header X-API-Key (plane_api_…) โดยไม่ต้องมี CSRF
Checklist ก่อนขึ้น production — 1) เปลี่ยน SECRET_KEY, LIVE_SERVER_SECRET_KEY, รหัส MinIO และ RabbitMQ  2) ตั้ง APP_DOMAIN และ SITE_ADDRESS เป็นโดเมนจริง (WEB_URL / CORS เป็น https)  3) จำกัด ALLOWED_HOSTS และ TRUSTED_PROXIES  4) สำรอง volume (pgdata, uploads) ตามรอบ — install.sh มีเมนู Backup ให้

Observability ของแอป — รู้ว่าระบบทำอะไรอยู่โดยไม่ต้องเดา

Logs

ทุก container เขียน stdout เป็น stream: docker compose logs -f api --tail 50 — api และ worker พิมพ์ JSON หนึ่งบรรทัดต่อเหตุการณ์ จึง grep และ jq ได้ ส่วน error ยังลงไฟล์ plane-error.log ใน volume logs_api

Health endpoints

GET / ของ api ตอบ {"status":"OK"} (install.sh ใช้เป็น probe) · GET /api/instances/ บอกสถานะ setup · live มี /live/health · web, admin, space มี HEALTHCHECK ใน Dockerfile

Metrics

Plane CE ไม่มี /metrics แบบ Prometheus ที่มีคือ telemetry แบบ OTLP ส่งไป plane.so (ปิดได้ใน god-mode → General) ระดับ container จึงใช้ docker stats หรือ cAdvisor + Grafana

ตอนที่ 2 · EXTENSION POINTS · แอปคุยกับแอป

จุดต่อขยาย — "แอปคุยกับแอป" ได้ 4 ทาง

REST API v1

prefix /api/v1/ ยืนยันตัวด้วย header X-API-Key (token plane_api_… จาก Settings → Developer → Personal Access Tokens, แสดงครั้งเดียว) · 60 req/นาที · pagination แบบ cursor · ใช้เขียนสคริปต์ import จาก Trello/Jira เอง เพราะ CE ไม่มี importer (LAB 7)

Webhooks

Plane POST JSON ไปยัง URL ของเราเมื่อ project, work item, cycle, module, comment เปลี่ยน · header X-Plane-Event, X-Plane-Delivery, X-Plane-Signature (HMAC-SHA256 ด้วย secret plane_wh_…) · retry 5 ครั้งแล้วปิดตัวเอง (LAB 8)

Exports

Workspace settings → Exports เลือก CSV / XLSX / JSON · worker สร้าง zip ลง MinIO และให้ลิงก์ดาวน์โหลด 7 วัน · นำไปทำ dashboard หรือวิเคราะห์ต่อภายนอกได้ (LAB 6, 9)

Sites (space)

เผยแพร่โปรเจกต์เป็นบอร์ดสาธารณะที่ /spaces/… แบบ list / kanban อ่านอย่างเดียว เปิด comment, reaction, vote ได้ · ให้ลูกค้าดูความคืบหน้าโดยไม่ต้องมีบัญชี (LAB 6)

เกณฑ์เลือกเครื่องมือ — ถามให้ครบ 8 ข้อก่อนตัดสินใจ

เกณฑ์คำถามที่ควรถามตัวอย่างการประเมิน Plane CE v1.4.2
Fit กับกระบวนการรองรับ Scrum/Kanban ที่ทีมใช้จริงไหม หรือต้องดัดกระบวนการเข้าหาเครื่องมือมี Cycles, Modules, board, Intake — แต่ไม่มี WIP limit และ workflow rule ใน CE
Integrationมี API, webhook, import/export ให้ต่อกับ toolchain เดิมไหมREST v1 + webhooks + export CSV/XLSX/JSON — ไม่มี importer Jira/Trello ใน CE ต้องเขียนสคริปต์
ต้นทุนค่า license รายหัว เทียบกับค่าเครื่องและคนดูแลฟรี แต่ต้องมีเครื่องรัน 13 container และคนดูแล backup / upgrade
Lock-inย้ายออกได้ไหม ข้อมูลอยู่ในรูปแบบเปิดหรือไม่ข้อมูลอยู่ใน Postgres/MinIO ของเรา export ได้ schema เป็น open source
Data ownershipข้อมูลอยู่ที่ใคร ใครเข้าถึงได้ ส่งอะไรออกนอกองค์กรบ้างอยู่ในเครื่องเราทั้งหมด telemetry ปิดได้ใน god-mode
Communityโครงการยังมีชีวิตไหม release ถี่ issue ได้รับคำตอบเร็วไหมGitHub makeplane/plane ออก release เป็น tag vX.Y.Z สม่ำเสมอ
Licenseใช้ แก้ และให้บริการต่อได้ในเงื่อนไขใดAGPL-3.0 — ใช้ภายในองค์กรได้อิสระ ให้บริการรุ่นที่แก้ต้องเปิดซอร์ส
Self-host ได้ไหมมี compose / Helm / image สำเร็จรูป และเอกสารเพียงพอไหมมี docker compose, Swarm, Helm chart และ AIO image พร้อม setup.sh
หลักสำคัญ — ให้น้ำหนักเกณฑ์ตามบริบทของทีม ก่อนดูฟีเจอร์ของเครื่องมือ มิฉะนั้นจะเลือกจากความคุ้นเคยหรือหน้าตาแทนความต้องการจริง
กับดักที่พบบ่อย — เลือกเพราะ "ทุกคนใช้ Jira" · เลือกจาก demo ที่สวย · ไม่เคยลอง export ข้อมูลกลับออกมา · ลืมคิดค่าดูแลระบบหลังปีแรก

สรุปตอนที่ 2 — และสิ่งที่จะลงมือทำใน LAB 1–2

  • ทุกขั้นของ SDLC มีแอปช่วย และแอป PM คือ single source of truth ที่ร้อยทุกขั้นไว้
  • เว็บแอปสมัยใหม่คือหลาย process ที่แบ่งหน้าที่: proxy · frontend · api · worker · scheduler · realtime บนฐาน DB · cache · queue · object storage
  • request วิ่งตาม URL prefix ส่วนงานช้าถูกโยนเข้า queue ให้ worker ทำ
  • config อยู่ใน env, ตรึง image tag, migrator รันครั้งเดียว และ Up ยังไม่ใช่ Ready
  • ความปลอดภัยเริ่มที่ secrets, TLS, least privilege, rate limit; สังเกตระบบผ่าน log JSON และ health endpoint
  • เลือกเครื่องมือด้วยเกณฑ์และ spike ไม่ใช่ความคุ้นเคย

คำถามทบทวนก่อนเข้าแล็บ

1) ถ้า worker หยุดทำงาน ผู้ใช้ยังสร้าง work item ได้ไหม เพราะอะไร  2) ทำไม WEB_URL ต้องมี :8080 ต่อท้าย  3) request ไปที่ /uploads/… ถูกส่งไปยัง container ใด
