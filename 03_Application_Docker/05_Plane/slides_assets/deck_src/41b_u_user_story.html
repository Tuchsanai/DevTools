User Story — เล่าความต้องการผ่านคุณค่าของผู้ใช้

ประโยคสั้นเริ่มการสนทนา ไม่ใช่เอกสารข้อกำหนดฉบับย่อ
User Story คือคำอธิบายความต้องการจากมุมของผู้ใช้: ใครต้องการอะไร และเพื่อให้เกิดคุณค่าใด รูปแบบช่วยคิด: ในฐานะ… ฉันต้องการ… เพื่อ…

ก่อน: รายการฟีเจอร์ยาวแต่ไม่รู้ว่าใครได้ประโยชน์
หลัง: งานหนึ่งใบมีผู้ใช้ เป้าหมาย และเกณฑ์ยอมรับที่คุยกันได้

CampusEats

“ในฐานะนักศึกษา ฉันต้องการสั่งอาหารล่วงหน้าจากมือถือ เพื่อรับอาหารได้ทันระหว่างคาบ” — ทีมถามต่อเรื่องเวลา ร้าน และสถานะออเดอร์

เข้าใจผิด: ❌ เขียนครบหนึ่งประโยค = พร้อมพัฒนา → ✅ ประโยคเป็นจุดเริ่มคุย; ต้องเติมตัวอย่าง เงื่อนไข และ acceptance criteria ที่ทดสอบได้ก่อนเลือกเข้าสู่ Sprint

User Story ที่ดี — แบบฟอร์ม · เกณฑ์ INVEST

Backlog refinement — กิจกรรมต่อเนื่อง (ไม่ใช่อีเวนต์) ที่ PO และ Developers แตกงาน เพิ่มรายละเอียด และประเมินขนาด backlog items ล่วงหน้า ให้พร้อมสำหรับ Sprint Planning; Scrum Guide 2017 เคยแนะนำสัดส่วนไม่เกิน 10% ของ capacity — ฉบับ 2020 ไม่กำหนดตัวเลข
# แบบฟอร์ม user story
ในฐานะ <บทบาท> ฉันต้องการ <สิ่งที่ต้องการ>
เพื่อ <คุณค่าที่ได้>

# ตัวอย่าง (work item ใน Plane)
ในฐานะ ผู้ใช้ที่ลืมรหัสผ่าน
ฉันต้องการ รับลิงก์รีเซ็ตทางอีเมล
เพื่อ กลับเข้าใช้งานได้เองโดยไม่ต้องติดต่อแอดมิน

# Acceptance criteria (ใส่ใน description)
- ลิงก์หมดอายุใน 30 นาที
- อีเมลที่ไม่มีในระบบ ต้องไม่บอกว่า "ไม่พบผู้ใช้"
INVESTความหมาย
Independentทำแยกจาก story อื่นได้ ลำดับสลับได้
Negotiableเป็นหัวข้อคุย ไม่ใช่สเปกตายตัว
Valuableผู้ใช้หรือธุรกิจได้อะไรชัดเจน
Estimableทีมประเมินขนาดได้ (รู้พอที่จะเดา)
Smallทำเสร็จได้ใน sprint เดียว
Testableมี acceptance criteria ที่ตรวจได้
ใน Plane: ชื่อ work item = ประโยค user story, description = acceptance criteria, sub-work items = งานย่อยที่แตกตอน Planning

แมปข้อมูลลง Plane

Description = บริบท + acceptance criteria
Labels = ป้ายค้นหา/กรอง เช่น story หรือ mobile
