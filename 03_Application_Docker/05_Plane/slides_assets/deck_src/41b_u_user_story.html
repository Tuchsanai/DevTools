User Story — เล่าความต้องการผ่านคุณค่าของผู้ใช้

ประโยคสั้นที่เปิดการสนทนา ไม่ใช่เอกสารข้อกำหนดฉบับย่อ
นิยาม — User Story คือคำอธิบายความต้องการหนึ่งอย่างจากมุมของผู้ใช้ ระบุว่า ใคร ต้องการ อะไร และ เพื่อคุณค่าใด โดยตั้งใจให้สั้นจนต้องคุยกันต่อ — เป็น “คำสัญญาว่าจะได้คุยกัน” ไม่ใช่สเปกที่เขียนจบแล้วส่งต่อรูปแบบ “ในฐานะ… ฉันต้องการ… เพื่อ…” มาจากทีม Connextra ในสาย XP · วลี “a promise for a conversation” ของ Alistair Cockburn

ทำไมจึงสำคัญ

ประโยคเดียวบอก “ใครได้อะไร” ทีมจึงถกทางเลือกของวิธีทำได้เอง จัดลำดับตามคุณค่าได้ และตรวจตอนจบได้ว่างานนี้ช่วยผู้ใช้จริงหรือไม่

ปัญหาที่แก้ · ก่อน → หลัง

ก่อน: ใบงานเขียนว่า “ทำหน้าสั่งอาหาร” — ไม่รู้ว่าใครใช้ ทำไม และเสร็จเมื่อไร ต้องเดาแล้วแก้ทีหลัง
หลัง: ใบงานมีผู้ใช้ · คุณค่า · เกณฑ์ที่ตัดสินผ่าน/ไม่ผ่านได้

ตัวอย่างจริง · CampusEats

“ในฐานะนักศึกษา ฉันต้องการสั่งอาหารล่วงหน้าจากมือถือ เพื่อรับอาหารได้ทันระหว่างคาบ” → ทีมถามต่อ: ล่วงหน้าได้กี่นาที · ร้านปิดรับตอนไหน · ยกเลิกได้หรือไม่

ความเข้าใจผิด ① ❌ เขียนครบหนึ่งประโยคแล้ว = พร้อมลงมือ → ✅ ประโยคคือจุดเริ่มของการสนทนา ทีมยังต้องคุยตัวอย่างและข้อยกเว้นกับผู้ที่ขอ แล้วสรุปเป็นเกณฑ์การยอมรับ (acceptance criteria) ที่ทดสอบได้ก่อนดึงเข้างาน

จากบทสนทนาเป็น Work item — Name · Description · Labels

Story หนึ่งใบ = work item หนึ่งใบ: ชื่อ = ผลลัพธ์ที่ผู้ใช้ได้ · ประโยค “ในฐานะ…” และเกณฑ์การยอมรับอยู่ใน Description
ภาพจริง · Create new work item ของ Plane Lab — Name “นักศึกษาสั่งอาหารล่วงหน้าจากมือถือ” + Description กรอกแล้ว · แถวคุณสมบัติ (Backlog · None · Assignees · Labels · Start/Due date · Cycle · Modules · Estimate · Add parent) ยังเป็นค่าเริ่มต้น · ยังไม่กด Save

Menu path · สร้าง Story

โปรเจกต์ Plane Lab → Work items → ปุ่ม Add work item → กรอก Name และ Description → ตั้งค่าจากแถวคุณสมบัติ → Save

Fields · เก็บ story ไว้ตรงไหน

Name (issues.name จำเป็น ≤ 255 ตัวอักษร) = ผลลัพธ์ที่ผู้ใช้ได้
Description (description_html/json/binary) = ประโยค story + เกณฑ์การยอมรับ (พิมพ์ [] เว้นวรรค = checkbox)
Labels = feature · bug · docs · tech-debt ของ LAB 3

ฟีเจอร์ที่เกี่ยวข้อง — เลข PLAB-4 (sequence_id) ไม่ถูกใช้ซ้ำ · แก้ฟิลด์ครั้งใดก็ถูกบันทึกใน Activity · ใบใหญ่เกิน “Small” แตกเป็น sub-work items
ข้อจำกัด CE · v1.4.2 — ไม่มีฟิลด์ acceptance criteria แยก และไม่มีหน้าจัดการ work item types → เกณฑ์ยอมรับอยู่ใน Description แยกชนิดงานด้วย Label
LAB 3 แบบฝึกหัด — เขียน “ทำระบบสั่งอาหาร” ใหม่เป็น Story 1 ใบ (ชื่อ = ผลลัพธ์ · story + เกณฑ์ยอมรับ 3 ข้อ · priority label due date) แล้วตอบ: ขาด INVEST ข้อใด · lint_work_items.py ให้กี่คะแนนจาก 5
