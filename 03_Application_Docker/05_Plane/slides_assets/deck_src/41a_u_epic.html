ตอนที่ 3 · Epic · นิยาม

Epic คือกลุ่มงานข้ามหลาย Sprint — ต้องแตกเป็น Stories

Epic เชื่อมภาพระดับ roadmap เข้ากับงานเล็กที่ทีมส่งมอบและตรวจรับได้จริงในแต่ละรอบ
นิยาม Epic คือ กลุ่มงานขนาดใหญ่ที่มุ่งสู่ผลลัพธ์เดียวกัน ใหญ่เกินกว่าจะทำให้เสร็จในหนึ่ง Sprint จึงถูกแตกเป็น User Stories ที่ส่งมอบและตรวจรับได้ทีละใบ คำในงาน Product/Agile — Scrum Guide 2020 ไม่มี Epic

ปัญหาเดิม · ก่อน

roadmap เขียนว่า “ระบบสั่งอาหาร” แต่ backlog มีงานย่อยกระจัดกระจาย ไม่มีใครตอบได้ว่าใบไหนร่วมเป้าหมายเดียวกัน และเส้นทางนี้ไปถึงไหนแล้ว

วิธีแก้ · หลัง

รวม Stories ที่พาไปสู่ผลลัพธ์เดียวกันไว้ในกล่องเดียว ตั้งเจ้าของและช่วงเวลา แล้วอ่านความคืบหน้าระดับ roadmap ได้ทันที

ทำไมสำคัญ — Epic เป็น “กล่องติดตาม” ที่คั่นระหว่าง Product Goal กับ backlog: ผู้มีส่วนได้เสียเห็นทิศทางของผลิตภัณฑ์ ส่วนทีมยังส่งมอบผ่าน Stories ขนาดเล็กตามเดิม
ทีมจัดกลุ่มบัตรงานย่อยใต้หมุดหมายบน roadmap เพื่อเห็นทั้งลำดับเวลาและภาพรวมของผลลัพธ์

ความเข้าใจผิด · ❌ Epic = ใบงานใหญ่ของคนเดียว

✅ ไม่มีใครลงมือทำ “ทั้ง Epic”: ทีมทำ Stories ที่แตกออกมา แต่ละใบต้องให้คุณค่า ตรวจรับได้ และเล็กพอจบใน Sprint เดียว ส่วน Epic เป็นกรอบไว้ดูภาพรวม

CampusEats · ตัวอย่างจาก LAB 6 — Epic “Ordering” คือเส้นทางสั่งอาหารหนึ่งเส้น: ค้นหาร้าน → ดูเมนูและราคา → เพิ่มเมนูลงตะกร้าและแก้จำนวน → สั่งอาหารและรับหมายเลขออเดอร์; แต่ละขั้นเป็น Story ที่ส่งมอบได้เอง ทยอยเสร็จข้าม Sprint แต่ทุกใบพาไปสู่ผลลัพธ์เดียวกัน

ตอนที่ 3 · Epic · กลไก

แตก Epic ให้ไหลสู่การส่งมอบ — Stories คือหน่วยความก้าวหน้า

อย่าวัด Epic ด้วยความรู้สึกว่า “ทำไปประมาณกี่เปอร์เซ็นต์” ให้นับจาก Stories ที่ผ่านเกณฑ์ Done เท่านั้น
ส่วนประกอบ — Epic แตกเป็น Stories ที่ให้คุณค่า; Task/Subtask อธิบายวิธีทำ · ใน Plane CE ใช้ Module → Work item → Sub-work item
วิธีแตก Epic เป็น Stories — แตกตามขั้นของผู้ใช้ (ค้นหา → ดูเมนู → ตะกร้า → ยืนยันออเดอร์) · ตามกฎธุรกิจหรือกรณีข้อมูล (ราคาปกติ vs มีโปรโมชันซ้อนกัน) · ทำเส้นทางหลักก่อน แล้วค่อยกรณียกเว้น — เกณฑ์ตัดสินคือแต่ละใบยังส่งคุณค่าและตรวจรับได้เอง ไม่ใช่แค่ขั้นตอนทางเทคนิค

1Plan · ระบุผลลัพธ์

ตั้งชื่อ Epic จากผลลัพธ์ กำหนดขอบเขต เจ้าของ และช่วงเวลา แล้วแตกเป็น Stories เรียงตามคุณค่าหรือความเสี่ยง

2Do · ส่งมอบข้าม Sprint

เลือก Stories เข้าแต่ละ Sprint; ภายใน Story แตกเป็น Task/Subtask ได้ แต่ Epic ไม่จำเป็นต้องจบในรอบเดียว

3Track · นับ Done

progress = Stories ที่ Done ÷ Stories ทั้งหมด เช่น 3/5 = 60% — เป็นสัดส่วน “จำนวนใบ” ไม่ใช่คุณค่าหรือ effort และจะลดลงเมื่อเพิ่มขอบเขตกลางทาง

Workflow · วงจรของ Epic — วางแผน → กำลังทำ → เสร็จ: เปลี่ยนเป็น “เสร็จ” เมื่อผลลัพธ์เกิดจริงและ Stories ที่จำเป็นผ่านเกณฑ์รับงาน ไม่ใช่เพราะถึงวันกำหนด; Epic ที่ยังไม่จบเดินต่อในรอบถัดไปได้เลย

Plane CE ใช้ Module แทน Epic — รวม Work items แล้วติดตามภาพรวม

เส้นทาง Plane Lab › Modules — ตั้งเจ้าของและช่วงเวลาให้กลุ่มงาน แล้วอ่าน progress โดยไม่ต้องเปิดงานทีละใบ
ภาพจริง · Gallery — Notifications 0/2 (Backlog) · Ordering 5/8 (In Progress) · Payments 0/1 (Planned) พร้อมช่วงวันที่
ภาพจริง · Ordering — In Progress · lead + members · Work items 5/8 · Points 13/18 · Progress 63% + กราฟ burndown

1Menu path · สร้าง Module

เปิดฟีเจอร์ที่ Project settings › Features › Modules แล้ว Modules › Add Module — name (ห้ามซ้ำ) · dates · lead · members · status

2Related feature · Progress

งานหนึ่งใบอยู่ได้หลาย Module (module_issues) ต่างจาก cycle · Progress นับใบตาม state group สลับเป็น Points เมื่อใช้ Estimate ชนิด Points

3CE limit · Status ตั้งเอง

Epic แบบ work-item type เป็นของรุ่นเสียเงิน CE จึงใช้ Module แทน · status ทั้ง 6 ค่า (backlog … cancelled) คนตั้งเอง ไม่คำนวณจาก progress

LAB 6 Mini exercise — จากแผงของ Ordering: Progress 63% มาจาก 5/8 ใบ — ถ้าสลับเป็นโหมด Points (13/18) จะได้กี่เปอร์เซ็นต์ และเหตุใดสองค่าจึงต่างกัน? แล้วอธิบายว่าเหตุใด status จึงยังเป็น In Progress
