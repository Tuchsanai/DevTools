12 หลักการของ Agile และผลที่มีต่อการออกแบบเครื่องมือ

#หลักการ (ย่อ)ผลต่อเครื่องมือ
1ส่งมอบซอฟต์แวร์ที่มีคุณค่า เร็วและต่อเนื่องรอบสั้น (Cycle) มี increment ทุกรอบ
2ยินดีรับ ความต้องการที่เปลี่ยน แม้ช่วงท้ายbacklog ลากจัดลำดับใหม่ได้ตลอด
3ส่งมอบซอฟต์แวร์ที่ใช้ได้ บ่อย ๆ (สัปดาห์–เดือน)Cycle 1–4 สัปดาห์ มีวันเริ่ม–จบชัด
4ฝ่ายธุรกิจและนักพัฒนา ทำงานร่วมกันทุกวันcomment / mention / activity บน work item
5สร้างงานรอบ คนที่มีแรงจูงใจ และไว้ใจเขาself-assign; เครื่องมือไม่ใช่ตัวจับผิด
6คุยต่อหน้า คือการสื่อสารที่ดีที่สุดบอร์ดเป็นฉากหลังของ Daily Scrum
#หลักการ (ย่อ)ผลต่อเครื่องมือ
7ซอฟต์แวร์ที่ใช้ได้ คือมาตรวัดความก้าวหน้าหลักนับเฉพาะ state group completed
8รักษา จังหวะที่ยั่งยืน ไปได้เรื่อย ๆvelocity คงที่, จำกัด WIP
9ใส่ใจ ความเป็นเลิศทางเทคนิค และการออกแบบDefinition of Done มี review/test
10ความเรียบง่าย — ทำเฉพาะสิ่งจำเป็นตัด/cancel งานที่ไม่คุ้มออกจาก backlog
11สถาปัตยกรรมที่ดีมาจาก ทีมที่จัดการตนเองทีมกำหนด states และ policy ของบอร์ดเอง
12ทีม ทบทวนและปรับ วิธีทำงานเป็นระยะRetrospective + activity log + analytics
สังเกต — ไม่มีหลักการข้อใดพูดถึง "เครื่องมือ" โดยตรง เครื่องมือที่ดีคือเครื่องมือที่ทำให้ 12 ข้อนี้เกิดขึ้นได้ง่าย ไม่ใช่เครื่องมือที่บังคับให้ทีมทำงานตามซอฟต์แวร์
คำถามชวนคิด — ถ้าทีมใช้ Plane ครบทุกฟีเจอร์ แต่ลูกค้าเห็นของจริงครั้งแรกในเดือนที่ 6 ทีมนั้นละเมิดหลักการข้อใดบ้าง (อย่างน้อยข้อ 1, 3, 4, 7)

Scrum Master

3 อาร์ติแฟกต์ แต่ละชิ้นผูกกับ commitment หนึ่งข้อ

Scrum Guide 2020 เพิ่ม commitment เพื่อให้ทุกอาร์ติแฟกต์วัดได้ว่า "ดีพอหรือยัง" — และทั้งสามชิ้นต้องโปร่งใสต่อทุกคน

1Product Backlog ↔ Product Goal

รายการงานทั้งหมดที่จัดลำดับแล้ว มีเจ้าของคนเดียวคือ PO; Product Goal คือเป้าหมายระยะยาวที่ backlog ทุกข้อควรพาไปถึง — ข้อที่ไม่พาไปถึงควรถูกตัดออก

2Sprint Backlog ↔ Sprint Goal

ชุดงานที่ Developers เลือกมาทำใน sprint นี้ + แผนว่าจะทำอย่างไร; Sprint Goal คือประโยคเดียวที่บอกว่า sprint นี้ "สำเร็จ" หมายถึงอะไร แม้บางงานทำไม่เสร็จ

3Increment ↔ Definition of Done

ผลรวมของงานที่ Done ทั้งหมดจนถึงตอนนี้ ต้องใช้งานได้จริง; Definition of Done คือเช็กลิสต์คุณภาพที่ทุกงานต้องผ่านก่อนนับเป็น Done

Backlog refinement — กิจกรรมต่อเนื่อง (ไม่ใช่อีเวนต์) ที่ PO และ Developers แตกงาน เพิ่มรายละเอียด และประเมินขนาด backlog items ล่วงหน้า ให้พร้อมสำหรับ Sprint Planning; Scrum Guide 2017 เคยแนะนำสัดส่วนไม่เกิน 10% ของ capacity — ฉบับ 2020 ไม่กำหนดตัวเลข

ฉันต้องการ รับลิงก์รีเซ็ตทางอีเมล

# Acceptance criteria (ใส่ใน description)
- ลิงก์หมดอายุใน 30 นาที
- อีเมลที่ไม่มีในระบบ ต้องไม่บอกว่า "ไม่พบผู้ใช้"
INVESTความหมาย
Independentทำแยกจาก story อื่นได้ ลำดับสลับได้
Negotiableเป็นหัวข้อคุย ไม่ใช่สเปกตายตัว
Valuableผู้ใช้หรือธุรกิจได้อะไรชัดเจน
Estimableทีมประเมินขนาดได้ (รู้พอที่จะเดา)
Smallทำเสร็จได้ใน sprint เดียว
Testableมี acceptance criteria ที่ตรวจได้

Story points — ประเมินขนาดแบบสัมพัทธ์ ไม่ใช่เป็นชั่วโมง

  • Story point = ขนาดสัมพัทธ์ รวม ความพยายาม + ความซับซ้อน + ความไม่แน่นอนเลือก story อ้างอิงที่ทีมเข้าใจตรงกันเป็น "2 แต้ม" แล้วเทียบข้ออื่นกับมัน
  • ใช้ลำดับ Fibonacci ดัดแปลง 1 · 2 · 3 · 5 · 8 · 13 · 20 · 40 · 100ช่องห่างกว้างขึ้นตามขนาด เพราะของใหญ่เดายากกว่า ถกเถียงเรื่อง 13 กับ 14 จึงไม่มีประโยชน์
  • ประเมินโดย Developers ทั้งทีม ไม่ใช่ PO หรือหัวหน้าเปิดไพ่พร้อมกันเพื่อกันการคล้อยตามคนแรก (anchoring); การคุยระหว่างประเมินคือคุณค่าหลัก
  • ข้อที่ได้ ≥ 13 ควรแตกให้เล็กลงก่อนดึงเข้า sprint
  • ประเมินใหม่เมื่อรู้ข้อมูลเพิ่ม ไม่ใช่เมื่อทำช้ากว่าแผนpoint วัดขนาดของงาน ไม่ใช่ผลงานของคน
ใน Plane — ต้องเลือกระบบประเมินที่ Settings › Projects › Estimates ก่อน (1 ระบบต่อโปรเจกต์) จึงจะใส่ point ให้ work item ได้

# นิยาม
velocity(sprint) = Σ points ของ work items ที่ Done ใน sprint นั้น
   (งานที่ทำไปครึ่งหนึ่ง = 0 point — ไม่มี partial credit)

# พยากรณ์ release
backlog ที่เหลือ 120 points ÷ velocity เฉลี่ย 20 = 6 sprints
ช่วงความเชื่อมั่น: 120 ÷ 22 … 120 ÷ 18  = 5.5 – 6.7 sprints
sprint ละ 2 สัปดาห์ → ประมาณ 11 – 14 สัปดาห์
velocity 1–2 sprint แรกยังไม่นิ่ง ใช้ค่าเฉลี่ยเคลื่อนที่ของ 3 sprint ล่าสุด และคำนวณใหม่ทุกครั้งที่ backlog เปลี่ยน

ใช้ velocity ทำอะไร

เลือกจำนวนงานใน Sprint Planning ให้พอดีความสามารถจริง · ตอบคำถาม "เมื่อไรจะเสร็จ" เป็นช่วง ไม่ใช่วันเดียว · เห็นแนวโน้มว่าทีมนิ่งหรือแกว่ง (แกว่งมาก = story ใหญ่เกินหรือมีงานแทรก)

ห้ามใช้เป็น KPI ของคนหรือทีม

ตอนที่ 3 · Scrum · Burndown & Burn-up

อ่าน burndown ให้เป็น — เส้น ideal · เส้น actual · และรูปแบบที่บอกปัญหา

ซ้าย: burndown ของ sprint 10 วัน — งานที่เหลือ (points) ควรลดตามเส้น ideal · กลาง: CFD (ดูสไลด์ Kanban) · ขวา: velocity ต่อ sprint
  • Ideal — เส้นตรงจาก total ในวันแรกถึง 0 ในวันสุดท้าย เป็นเพียงจุดอ้างอิง
  • Actual — งานที่เหลือจริง ณ สิ้นวัน ลดลงเมื่องาน Done เท่านั้นงานทำไปครึ่งหนึ่งไม่ทำให้เส้นตก — จึงเห็นเป็นขั้นบันได
  • เส้นราบนาน แล้วดิ่งตอนท้าย = late finish: งานใหญ่เกิน หรือ review/test กองอยู่ปลาย sprint
  • เส้นกระโดดขึ้น = scope creep: มีงานถูกเพิ่มเข้า sprint กลางคัน
  • เหนือ ideal ตลอด = รับงานมากเกิน velocity — ต้องคุยกับ PO ว่าจะตัดอะไร
  • Burn-up — วาดงานที่ Done สะสมกับเส้น scope รวม จึงเห็น scope ที่เปลี่ยนแยกจากความคืบหน้า

ตอนที่ 3 · Kanban · Toyota → Software (Anderson 2010)

Kanban คือวิธีปรับปรุง flow — "เริ่มจากสิ่งที่ทำอยู่ตอนนี้"

ป้าย kanban ในโรงงาน Toyota เป็นสัญญาณ "ดึง" วัสดุเมื่อถึงเวลาใช้ — บอร์ดซอฟต์แวร์ใช้การ์ดเป็นสัญญาณดึงงานแบบเดียวกัน
6 practices
  • Visualize — ทำให้ขั้นตอนงานและงานค้างมองเห็นได้
  • Limit WIP — จำกัดจำนวนงานต่อคอลัมน์ ระบบดึง (pull) แทนดัน (push)
  • Manage flow — วัด lead time / throughput แล้วขจัดจุดคอขวด
  • Explicit policies — เขียนกติกาว่างานผ่านคอลัมน์ได้เมื่อไร
  • Feedback loops — cadence ประจำ เช่น replenishment, delivery review
  • Improve collaboratively — ปรับทีละน้อยจากข้อมูล ไม่รื้อทั้งระบบ
ต่างจาก Scrum — Kanban ไม่กำหนดบทบาทหรืออีเวนต์ใหม่ เริ่มจากกระบวนการเดิม แล้วปรับปรุงแบบวิวัฒนาการ

ตอนที่ 3 · Kanban · Flow Metrics

WIP limit และ Little's Law — อยากให้งานออกเร็วขึ้น ให้ลดงานที่ค้าง

  • Lead time — ตั้งแต่ลูกค้าขอ (สร้าง) จน Done; สิ่งที่ลูกค้ารับรู้
  • Cycle time — ตั้งแต่เริ่มลงมือ (In Progress) จน Done; สิ่งที่ทีมควบคุมได้
  • Throughput — จำนวนงานที่ Done ต่อหน่วยเวลา เช่น 3 ใบ/วัน
  • WIP — งานที่เริ่มแล้วแต่ยังไม่ Done ในขณะหนึ่ง
  • Flow efficiency — เวลาที่ถูกทำจริง ÷ lead time; ทำจริง 6 ชม. จาก 32 ชม.ทำงาน ≈ 19% (ที่เหลือคือรอ)
Little's Law — Lead time เฉลี่ย ≈ WIP ÷ Throughput (ระบบต้องนิ่ง) · WIP 12 ÷ 3 ใบ/วัน = รอ 4 วัน; ลด WIP เหลือ 6 → รอ 2 วัน โดยไม่ต้องเพิ่มคน

Cycle คือ Sprint ของ Plane — วันที่ · progress · burndown ที่คำนวณจาก completed_at

แผง Progress ของ cycle: เส้นทึบ = งานที่เหลือจริง, เส้นประ = ideal; สลับ Work items / Estimates ได้ (ต้องเปิด Cycles ที่ Settings › Projects › Features ก่อน)
  • Cycle มีแค่ start_date / end_date ไม่มีคอลัมน์สถานะ — In progress / Yet to start / Completed / Draft คำนวณจากวันที่ตอน query (timezone ของโปรเจกต์)
  • Active cycle = cycle ที่วันนี้อยู่ในช่วง — แผง Progress, Work item burndown, สถิติตาม priority / assignee / label อยู่ในหน้า Cycles ของโปรเจกต์; เมนู Active cycles ระดับ workspace ใน CE เป็นหน้า upsell
  • Progress นับ work items ต่อ state group (backlog / unstarted / started / completed / cancelled) และผลรวม points
  • Burndown: remaining(วัน) = total − Σ งานที่ completed_at ≤ วันนั้น; วันในอนาคตเป็น null · ideal = total × (1 − i/(n−1))
  • CE มีเฉพาะ burndown — ตัวเลือก Burn-up มีในโค้ดแต่ไม่ได้ต่อกับ UI; อยากได้ burn-up ต้องคำนวณเองจาก completed_at ของแต่ละใบ (cycle_report.py ใน LAB 4 คำนวณ burndown ด้วยสูตรเดียวกับ Plane)
  • จบ cycle แล้วงานที่ค้างใช้ Transfer ไป cycle ถัดไป (เก็บ snapshot ของสถิติเดิม) — ปุ่มนี้แสดงเฉพาะ cycle ที่ Completed (end_date ผ่านแล้ว)
  • ปฏิทินใน UI ไม่ให้เลือกวันในอดีต — cycle ที่ต้องเริ่มย้อนหลัง (เช่นใน LAB 4) สร้าง/แก้ผ่าน REST API

รัน Scrum ทั้งวงจรบน Plane — Page · Board · Cycle progress · Retro

Sprint Planning → Cycle

สร้าง Cycle 2 สัปดาห์ เขียน Sprint Goal ใน description ลาก work items เข้า ใส่ estimate ให้ครบก่อนวันแรก

Definition of Done → Page ของโปรเจกต์

เขียนเป็นเช็กลิสต์ ล็อก (lock) เมื่อทีมตกลงแล้ว ปรับได้เฉพาะใน Retrospective; ลิงก์ Page นี้ไว้ใน description ของทุก Cycle

Daily Scrum → Board ของ active cycle

เปิด Board layout กรอง Cycle = ปัจจุบัน Group by State; เดินจากคอลัมน์ขวาไปซ้าย ถามว่า "อะไรขวางไม่ให้ใบนี้ Done" ไม่ใช่ "เมื่อวานทำอะไร"

Sprint Review → Cycle progress + รายการ Done

เปิดแผง Progress ให้ stakeholder เห็นสัดส่วน completed / started / unstarted แล้วสาธิตงานที่ Done ทีละใบ; feedback บันทึกเป็น comment หรือ work item ใหม่ใน backlog

ตอนที่ 3 · Anti-patterns

สิ่งที่มักพัง — บอร์ดสวยแต่ทีมไม่ได้ทำ Agile

1Mini-waterfall

ใน sprint 2 สัปดาห์: สัปดาห์แรกทุกคนเขียนโค้ด สัปดาห์สอง test ทั้งหมด — burndown ราบแล้วดิ่งตอนท้าย แก้: แตกงานให้แต่ละใบ Done ได้ใน 1–2 วัน

2Zombie Scrum

มีอีเวนต์ครบแต่ไม่มีผล: Daily เป็นการรายงานหัวหน้า Review ไม่มี stakeholder Retro ไม่มี action item แก้: ทุกอีเวนต์ต้องจบด้วยการตัดสินใจอย่างน้อยหนึ่งข้อ

3WIP ระเบิด

คนละ 4–5 ใบใน In Progress ทุกอย่าง "เกือบเสร็จ" แต่ไม่มีอะไร Done แก้: ตกลง WIP limit ต่อคน ต่อคอลัมน์ และให้สคริปต์แจ้งเตือนเมื่อเกิน

4Velocity เป็น KPI

ผู้บริหารตั้งเป้า "sprint หน้าต้อง 25" → ทีมประเมินเฟ้อ ตัด test ออกจาก DoD ตัวเลขขึ้นแต่ผลิตภัณฑ์แย่ลง แก้: วัดผลลัพธ์ต่อผู้ใช้ (outcome) ไม่ใช่ output

5บอร์ดไม่อัปเดต

คุยกันใน chat แล้วค่อยมาย้ายการ์ดตอนสิ้นสัปดาห์ — burndown, activity log, lead time ทั้งหมดผิด แก้: "ถ้าไม่อยู่บนบอร์ด ถือว่ายังไม่เกิด" และย้ายการ์ดตอน Daily Scrum

6ทุก work item เป็น Urgent

priority ถูกตั้งเป็น urgent เกือบทั้ง backlog จนไม่มีความหมาย ทีมเลือกงานตามความคุ้นเคยแทน แก้: PO จัดลำดับเดียว (sort order) และจำกัด urgent ให้ตรงกับ class of service Expedite

ตรวจจับได้จากข้อมูลใน Plane — burndown ที่ราบ (1), activity log ที่ว่างหลายวันแล้วมีการย้ายการ์ดเป็นชุด (5), จำนวน work items ใน started ต่อ assignee (3), สัดส่วน urgent ใน Analytics (6)

ตอนที่ 3 · สรุป

สรุปตอนที่ 3 — จากทฤษฎี Scrum & Kanban สู่ LAB 4–5

  • Agile คือการย่นระยะระหว่างตัดสินใจกับเห็นผลจริง4 คุณค่า 12 หลักการ — เครื่องมือต้องรับใช้หลักการ ไม่ใช่กลับกัน
  • Scrum = 3 บทบาท · 5 อีเวนต์ · 3 อาร์ติแฟกต์ + commitmentวัดด้วย velocity และ burndown; DoD คือหัวใจของคำว่า Done
  • Kanban = visualize, limit WIP, manage flowLittle's Law: ลด WIP แล้ว lead time สั้นลงโดยไม่ต้องเพิ่มคน
  • Plane: Cycle = sprint, states 5 กลุ่ม, Board + swimlanes, Estimates, PageCE ไม่มี WIP limit / workflow rule — ทีมต้องมี policy และสคริปต์
  • metrics ของ Plane คำนวณจาก completed_at และ state groupข้อมูลดีได้เท่ากับวินัยในการย้ายการ์ดบนบอร์ด
คำถามทบทวน — (1) ทำไม burndown ของ Plane ถึงต้องพึ่ง completed_at ไม่ใช่ประวัติ state (2) ถ้า throughput 5 ใบ/วัน และ WIP 20 ใบ lead time เฉลี่ยเท่าไร (3) Sprint Goal ต่างจากรายการงานใน Cycle อย่างไร

LAB 4Scrum บน Plane

เปิด Estimates แบบ Fibonacci · สร้าง Cycle 2 สัปดาห์ผ่าน API · points จาก backlog.csv (seed_backlog.py) · time machine SQL กระจาย completed_at คนละวัน · อ่าน burndown ทั้งโหมด Work items และ Estimates · คำนวณ burndown/velocity เองด้วย cycle_report.py / velocity.py

LAB 5Kanban บน Plane

เพิ่ม state In Review · ตั้ง Board ให้มี swimlanes ตาม assignee · เขียน explicit policies และ WIP limit เป็น Page · เขียนสคริปต์ผ่าน API นับงานใน started แล้วเตือนเมื่อเกิน · บันทึกเป็น View และตั้ง Intake

ก่อนเริ่ม LAB — เปิด Cycles / Views / Intake ที่ Settings › Projects › Features (โปรเจกต์ที่สร้างจาก UI ปิดไว้ทั้งหมด) และตั้ง Estimates; ทบทวนตารางแปลศัพท์ Scrum ↔ Plane; เตรียม backlog อย่างน้อย 10 user stories ที่ผ่าน INVEST
