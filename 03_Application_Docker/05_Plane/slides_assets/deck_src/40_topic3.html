4 คุณค่าของ Agile — "ให้คุณค่าฝั่งซ้ายมากกว่า" ไม่ใช่ "ไม่เอาฝั่งขวา"

1คนและการสื่อสาร

เครื่องมือเป็นสื่อกลางของบทสนทนา ไม่ใช่ตัวแทนบทสนทนา — comment บน work item แทนอีเมลยาว

2ซอฟต์แวร์ที่ใช้ได้จริง

ความก้าวหน้าวัดจากงานที่ Done ตาม Definition of Done ไม่ใช่จำนวนเอกสาร

3ร่วมมือกับลูกค้า

ลูกค้าเห็นบอร์ดและ increment ทุกรอบ ไม่รอส่งมอบตอนจบสัญญา

4ตอบสนองการเปลี่ยนแปลง

backlog จัดลำดับใหม่ได้เสมอ แผนคือสมมติฐานที่ปรับได้ทุก sprint

12 หลักการของ Agile และผลที่มีต่อการออกแบบเครื่องมือ

#หลักการ (ย่อ)ผลต่อเครื่องมือ
1ส่งมอบซอฟต์แวร์ที่มีคุณค่า เร็วและต่อเนื่องรอบสั้น (Cycle) มี increment ทุกรอบ
2ยินดีรับ ความต้องการที่เปลี่ยน แม้ช่วงท้ายbacklog ลากจัดลำดับใหม่ได้ตลอด
3ส่งมอบซอฟต์แวร์ที่ใช้ได้ บ่อย ๆ (สัปดาห์–เดือน)Cycle 1–4 สัปดาห์ มีวันเริ่ม–จบชัด
4ฝ่ายธุรกิจและนักพัฒนา ทำงานร่วมกันทุกวันcomment / mention / activity บน work item
5สร้างงานรอบ คนที่มีแรงจูงใจ และไว้ใจเขาself-assign; เครื่องมือไม่ใช่ตัวจับผิด
6คุยต่อหน้า คือการสื่อสารที่ดีที่สุดบอร์ดเป็นฉากหลังของ Daily Scrum
#หลักการ (ย่อ)ผลต่อเครื่องมือ
7ซอฟต์แวร์ที่ใช้ได้ คือมาตรวัดความก้าวหน้าหลักนับเฉพาะ state group completed
8รักษา จังหวะที่ยั่งยืน ไปได้เรื่อย ๆvelocity คงที่, จำกัด WIP
9ใส่ใจ ความเป็นเลิศทางเทคนิค และการออกแบบDefinition of Done มี review/test
10ความเรียบง่าย — ทำเฉพาะสิ่งจำเป็นตัด/cancel งานที่ไม่คุ้มออกจาก backlog
11สถาปัตยกรรมที่ดีมาจาก ทีมที่จัดการตนเองทีมกำหนด states และ policy ของบอร์ดเอง
12ทีม ทบทวนและปรับ วิธีทำงานเป็นระยะRetrospective + activity log + analytics
สังเกต — ไม่มีหลักการข้อใดพูดถึง "เครื่องมือ" โดยตรง เครื่องมือที่ดีคือเครื่องมือที่ทำให้ 12 ข้อนี้เกิดขึ้นได้ง่าย ไม่ใช่เครื่องมือที่บังคับให้ทีมทำงานตามซอฟต์แวร์
คำถามชวนคิด — ถ้าทีมใช้ Plane ครบทุกฟีเจอร์ แต่ลูกค้าเห็นของจริงครั้งแรกในเดือนที่ 6 ทีมนั้นละเมิดหลักการข้อใดบ้าง (อย่างน้อยข้อ 1, 3, 4, 7)
