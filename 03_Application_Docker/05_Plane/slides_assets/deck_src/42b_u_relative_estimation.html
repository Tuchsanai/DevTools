Relative estimation — เทียบขนาดกับเรื่องอ้างอิง ไม่เทียบกับนาฬิกา

เลือก story ที่ทีมเข้าใจตรงกันเป็นฐาน แล้วถามว่าเรื่องใหม่เล็กกว่า พอ ๆ กัน หรือใหญ่กว่าฐานเพียงใด

ปัญหาที่แก้ · ทำไมต้องเทียบ

ชั่วโมงของงานเดียวกันเปลี่ยนตามคน เครื่องมือ และงานแทรก จึงถูกตีความเป็นกำหนดส่งได้ง่าย การเทียบ “ใหญ่กว่าเรื่องฐานแค่ไหน” ใช้ข้อมูลน้อยกว่าและทำให้ทีมคุยบนมาตราเดียวกัน

กลไก 3 ขั้น

1) เลือก reference story ที่เล็กและเข้าใจดี เช่น 2 pt · 2) เทียบ effort + complexity + uncertainty · 3) เลือกค่าที่ใกล้ที่สุดจากสเกลของทีม แล้วบันทึกเหตุผล

CampusEats · ตัวอย่าง

ใช้ PBI-02 ดูเมนูและราคา = 2 pt เป็นฐาน: ย้าย config = 1 pt · สั่งอาหารและออกเลขออเดอร์ = 5 pt · ติดตาม realtime = 8 pt เพราะมีการเชื่อมต่อและความไม่แน่นอนมากกว่า

❌ เข้าใจผิด — “5 points = 5 ชั่วโมง” และ “ทีม A ทำ 20 points จึงเก่งกว่าทีม B”
✅ ใช้ให้ถูก — point บอกขนาดเทียบกับฐานของ ทีมเดียวกัน; ห้ามแปลงเป็นเวลาแบบสูตรตายตัวหรือเทียบข้ามทีม

ตอนที่ 3 · Relative estimation · ใน Plane

บันทึกผลเทียบใน Plane — Estimate ของ work item · ตรวจความสม่ำเสมอใน List

Plane เก็บ “ค่าที่ทีมตกลงแล้ว” ส่วนการเปรียบเทียบและเหตุผลเกิดขึ้นในบทสนทนาของทีมก่อนเลือกค่า
รายละเอียด CampusEats story — Estimate อยู่ในชุด properties เดียวกับ assignee · cycle · module · labels

1เปิดระบบของโปรเจกต์

Project settings › Estimates → เลือกและเปิด Estimate แบบ Points หนึ่งระบบ; ช่อง Estimate ในแผงรายละเอียด work item จึงปรากฏให้เลือก

2บันทึกค่าที่ทีมตกลง

เลือกค่าใน Estimate dropdown ของแต่ละ work item; Plane ผูกใบงานกับ EstimatePoint ของโปรเจกต์ ไม่ได้เก็บจำนวนชั่วโมง

3ตรวจ consistency

เปิด List และแสดง property Estimate แล้วเทียบใบที่คล้ายกันกับ reference เดิม; CE ไม่มีตัวเลือก Order by Estimate จึงต้องตรวจค่าที่มองเห็นร่วมกัน

LAB 4Mini exercise — ให้ PBI-02 ดูเมนูและราคา = 2 pt เป็นฐาน จัดอันดับจากเล็กไปใหญ่: PBI-10 ย้าย config · PBI-01 ค้นหาร้าน · PBI-04 สั่งอาหารและออกเลขออเดอร์ · PBI-07 ติดตาม realtime · PBI-08 PromptPay QR แล้วเลือก point ให้แต่ละใบพร้อมเหตุผลด้าน effort / complexity / uncertainty อย่างละ 1 ประโยค—ห้ามเริ่มจากการเดาชั่วโมง
