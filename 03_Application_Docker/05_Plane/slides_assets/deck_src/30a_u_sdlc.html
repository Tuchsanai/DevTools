ตอนที่ 2 · SDLC · นิยาม

SDLC คือ แผนที่ร่วมตั้งแต่ “ต้องการอะไร” จนถึง “ดูแลต่ออย่างไร”

Software Development Life Cycle ไม่ใช่ชื่อเครื่องมือ แต่คือวงจรของกิจกรรมที่ทำให้ซอฟต์แวร์หนึ่งระบบเกิดขึ้น ใช้งานได้ และพัฒนาต่อได้
“SDLC คือวงจรของกิจกรรมตั้งแต่ทำความเข้าใจความต้องการ ออกแบบ พัฒนา ทดสอบ ส่งมอบ ไปจนถึงบำรุงรักษา”หนึ่งวงจรจบเมื่อสิ่งที่เรียนรู้ย้อนกลับไปเป็นความต้องการรอบถัดไป

ก่อนมีแผนที่ร่วม

เริ่มเขียนโค้ดทั้งที่โจทย์ยังคลุมเครือ · ลืมงบทดสอบ · ส่งงานแล้วไม่มีคนเฝ้าระบบหรือแก้ปัญหา

เมื่อใช้ SDLC

ทีมเห็นว่างานอยู่ช่วงใด ใครต้องส่งต่ออะไร และหลักฐานใดบอกว่าพร้อมไปขั้นถัดไป

ทำไมสำคัญ — SDLC ให้ภาษากลางแก่ผู้ใช้ นักวิเคราะห์ นักออกแบบ นักพัฒนา ผู้ทดสอบ และผู้ดูแลระบบ; เครื่องมือแต่ละชนิดจึงมีหน้าที่ช่วยคนละช่วงของวงจร
ช่วง Requirements เริ่มจากการทำความเข้าใจปัญหาร่วมกัน ก่อนเปลี่ยนความต้องการให้เป็นงานที่ตรวจสอบได้

หกขั้นเชื่อมกันด้วย ผลส่งมอบและ feedback

แต่ละขั้นเปลี่ยนคำถามให้เป็นหลักฐานที่ทีมใช้ทำขั้นถัดไป—และย้อนกลับได้เมื่อพบสิ่งที่เข้าใจผิด
ขั้นกิจกรรม → artifact
1 Requirementsคุยกับผู้ใช้ → user story · backlog
2 Designออกแบบข้อมูล/หน้าจอ → wireframe · API spec
3 Implementationเขียนและ review → code · commit
4 Testingตรวจเงื่อนไขยอมรับ → test result
5 Deploymentbuild และปล่อย → image · release
6 Maintenanceเฝ้าดู แก้ ปรับปรุง → bug · request ใหม่

Waterfall · รอบยาว

ผ่านแต่ละขั้นครั้งใหญ่ตามลำดับ จึงได้ feedback จริงค่อนข้างช้า

Iterative · แก้เป็นรอบ

ทดลอง ทบทวน และแก้แบบเดิมซ้ำจนเหมาะขึ้น

Agile · รอบสั้น + increment

ทำทั้งหกกิจกรรมกับชิ้นเล็ก ส่งมอบได้ แล้วนำ feedback ไปจัดรอบถัดไป

เชื่อมกับภาพ d04 — ความต่างสำคัญไม่ใช่ “มีหรือไม่มีขั้น” แต่คือขนาดของรอบและเวลาที่ทีมได้รับ feedback

ตอนที่ 2 · SDLC · ตัวอย่าง

CampusEats หนึ่งภาคการศึกษา — เดินครบวงจร ไม่ใช่เขียนโค้ดอย่างเดียว

โจทย์: ให้นักศึกษาสั่งอาหารล่วงหน้า ลดคิวหน้าร้าน และรับอาหารตามช่วงเวลาที่เลือก
ช่วงสิ่งที่ทีม CampusEats ทำให้เห็นจริง
Requirementsสัมภาษณ์นักศึกษาและร้านค้า → backlog: เลือกร้าน · เมนู · ช่วงรับอาหาร · ชำระเงิน
Designวาด flow การสั่งอาหาร ออกแบบหน้าจอและข้อมูล Order/Menu/Pickup slot
Implementationพัฒนาเป็นชิ้นเล็ก เช่น “เลือกช่วงรับอาหาร” พร้อม review code
Testingตรวจเส้นทางปกติและกรณีเมนูหมด ช่วงเต็ม ยกเลิก และสั่งซ้ำ
Deploymentbuild รุ่นทดลอง ปล่อยให้กลุ่มนำร่องใช้ และบันทึกสิ่งที่เปลี่ยน
Maintenanceติดตามปัญหา แก้ bug และเปลี่ยน feedback เช่น “แจ้งเตือนเมื่ออาหารพร้อม” เป็น backlog รอบใหม่

❌ “SDLC = Waterfall”

✅ จริง: SDLC บอกว่าต้องคิดกิจกรรมใดบ้าง ส่วน Waterfall เป็นเพียงวิธีจัดกิจกรรมเหล่านั้นเป็นรอบยาวแบบหนึ่ง

❌ “Agile ไม่ออกแบบและไม่ทดสอบ”

✅ จริง: Agile ยังออกแบบ พัฒนา ทดสอบ และส่งมอบ แต่ทำกับชิ้นเล็กในแต่ละ iteration เพื่อรับ feedback เร็ว

ลองชี้จุดย้อนกลับ — ถ้าทดสอบแล้วพบว่าร้านไม่สามารถรับออเดอร์เกิน 20 รายการต่อช่วง ทีมต้องย้อนกลับไปทบทวน Requirements และ Design ก่อนแก้ code

Plane เป็น ศูนย์กลางติดตามงานตลอดวงจร—ไม่ใช่เครื่องมือเขียนหรือ deploy code

ทีมเชื่อมความต้องการ แผน สถานะ กลุ่มงาน และ feedback ไว้ในโปรเจกต์เดียว แล้วใช้เครื่องมือเฉพาะทางทำ Design · Code · Test · Deploy ต่อ
PLAB › Work items — List layout จัดกลุ่มตาม State และแสดง backlog ของ CampusEats
  • Requirements → Work itemsเก็บ backlog ของความต้องการเป็นหน่วยงานที่ติดตามได้
  • Planning → Cyclesเลือก work items เข้าเวลาทำงานที่มีวันเริ่มและวันจบ
  • Tracking → Statesบอกว่างานอยู่ขั้นใดด้วย state ใน 5 กลุ่มหลัก
  • Release grouping → Modulesรวมงานตาม feature/release; ไม่ได้ deploy ซอฟต์แวร์ให้เอง
  • Feedback → Intake + commentsรับคำขอเข้าคิว triage และสนทนาบน work item
