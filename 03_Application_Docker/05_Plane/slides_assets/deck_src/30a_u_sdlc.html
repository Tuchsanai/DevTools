ตอนที่ 2 · SDLC · นิยาม

SDLC คือ วงจรร่วมของงาน ตั้งแต่ “ต้องการอะไร” จนถึง “ดูแลต่ออย่างไร”

Software Development Life Cycle ไม่ใช่ชื่อเครื่องมือหรือชื่อวิธีทำงาน แต่คือชุดกิจกรรมที่ทำให้ซอฟต์แวร์หนึ่งระบบเกิดขึ้น ใช้งานได้ และพัฒนาต่อได้
“SDLC คือวงจรของกิจกรรมที่ทีมทำซ้ำ ตั้งแต่ทำความเข้าใจความต้องการ ออกแบบ พัฒนา ทดสอบ ส่งมอบ ไปจนถึงบำรุงรักษา”หนึ่งรอบจบเมื่อสิ่งที่เรียนรู้จากการใช้งานจริง ย้อนกลับไปเป็นความต้องการของรอบถัดไป

ปัญหาเมื่อไม่มีวงจรร่วมกัน

เริ่มเขียนโค้ดทั้งที่โจทย์ยังคลุมเครือ · ไม่มีใครกันเวลาไว้ให้การทดสอบ · ส่งมอบแล้วไม่มีเจ้าของเมื่อระบบล่มหรือผู้ใช้ขอเพิ่ม

สิ่งที่ได้เมื่อใช้ SDLC

ทุกคนตอบตรงกันว่างานชิ้นนี้อยู่ขั้นใด ใครส่งต่อให้ใคร ต้องมีหลักฐานอะไรจึงข้ามไปขั้นถัดไป และ feedback จะกลับเข้ามาทางไหน

ทำไมสำคัญ — SDLC ทำให้ “งานที่ไม่ใช่การเขียนโค้ด” (สัมภาษณ์ผู้ใช้ · ออกแบบ · ทดสอบ · ดูแลหลังส่งมอบ) มีที่อยู่ในแผน มีเจ้าของ และถูกกันเวลาไว้ แทนที่จะโผล่เป็นงานแทรกตอนใกล้ส่ง; ทั้งยังเป็นภาษากลางของผู้ใช้ นักพัฒนา ผู้ทดสอบ และผู้ดูแลระบบ
ขั้น Requirements เริ่มจากการทำความเข้าใจปัญหาร่วมกัน ก่อนเปลี่ยนความต้องการให้เป็นงานที่ตรวจสอบได้

ตอนที่ 2 · SDLC · กลไก

หกขั้นเชื่อมกันด้วย ผลส่งมอบและ feedback

องค์ประกอบของวงจร = ขั้น (กิจกรรม) + artifact ที่ส่งต่อ + เส้นทาง feedback ที่ย้อนกลับได้เมื่อพบว่าเข้าใจผิด
ขั้นคำถามที่ต้องตอบก่อนไปต่อ
1 Requirementsใครใช้ ได้ประโยชน์อะไร และวัด “ใช่แล้ว” อย่างไร
2 Designข้อมูลและหน้าจอเป็นอย่างไร ส่วนใดคุยกับส่วนใด
3 Implementationโค้ดตรงกับที่ออกแบบไหม ผ่าน review จากใคร
4 Testingเกณฑ์ยอมรับข้อใดผ่าน/ไม่ผ่าน หลักฐานอยู่ที่ไหน
5 Deploymentผู้ใช้จริงได้รุ่นใด ตั้งค่าอย่างไร ย้อนกลับได้ไหม
6 Maintenanceระบบยังทำงานดีอยู่ไหม เรื่องใหม่เข้าคิวที่ใด

Waterfall · ผ่านครั้งเดียว

ผ่านหกขั้นตามลำดับเป็นรอบยาวรอบเดียว; feedback จากผู้ใช้จริงมาช่วงท้าย จึงแก้สิ่งที่เข้าใจผิดได้ช้า

Iterative · ทำซ้ำเพื่อปรับ

วนกลับมาแก้ของชิ้นเดิมหลายรอบจนดีขึ้น แต่ละรอบไม่จำเป็นต้องส่งมอบให้ผู้ใช้

Agile · รอบสั้น + increment

ทำครบหกกิจกรรมกับชิ้นเล็กทุกรอบ จบรอบได้ของที่ใช้งานได้จริง แล้วนำ feedback ไปจัดรอบถัดไป

อ่านภาพอย่างไร — ลูกศรทึบ = ลำดับงานและ artifact ที่ส่งต่อ (user story → wireframe/API spec → code → ผลทดสอบ → release) · ลูกศรประแดง = feedback ที่บังคับให้ย้อนไปทบทวนความต้องการ · ลูกศรจากขั้น 6 กลับขั้น 1 = รอบถัดไป  ·  ตำราแต่ละเล่มแบ่งจำนวนขั้นไม่เท่ากัน (บางเล่มรวม Deployment กับ Maintenance) ประเด็นคือกิจกรรมต้องครบและขนาดของรอบ ไม่ใช่จำนวนกล่อง

ตอนที่ 2 · SDLC · ตัวอย่าง

CampusEats หนึ่งภาคการศึกษา — เดินครบวงจร ไม่ใช่เขียนโค้ดอย่างเดียว

โจทย์เดียวกับ LAB 3–4: ให้นักศึกษาค้นหาร้าน ดูเมนู ใส่ตะกร้า และสั่งอาหารได้ครบวงจร
ขั้นสิ่งที่ทีม CampusEats ทำให้เห็นจริง
Requirementsสัมภาษณ์นักศึกษาและร้านค้า → Product Backlog 10 ใบ (PBI-01…10): ค้นหาร้าน · ดูเมนู · ตะกร้า · สั่งและติดตามออเดอร์ · ชำระเงิน
Designวาด flow ค้นหาร้าน → ดูเมนู → ตะกร้า → ยืนยันออเดอร์ และออกแบบข้อมูล Restaurant / Menu / Order ก่อนลงมือเขียน
Implementationทำทีละชิ้นเล็ก: PBI-01 “ค้นหาร้านตามชื่อ” (3 pt) และ PBI-02 “ดูเมนูและราคา” (2 pt) พร้อม review code และอ้างเลขใบใน commit
Testingตรวจตาม acceptance criteria ของแต่ละใบ: พิมพ์ 2 ตัวอักษรแล้วเห็นผลใน 1 วินาที (PBI-01) · เมนูหมดต้องกดไม่ได้ (PBI-02) · เลขออเดอร์ไม่ซ้ำ (PBI-04)
Deploymentbuild รุ่นทดลองให้กลุ่มนำร่องใช้; ก่อนขึ้น staging ต้องปิด PBI-10 — ย้าย URL ฐานข้อมูลและ key ออกจากโค้ดไปเป็น environment variable
Maintenanceรับ bug และคำขอจากผู้ใช้จริง เช่น “แอปเด้งออกตอนกดจ่ายเงินด้วย QR” เข้าคิว; PBI-07 ติดตามสถานะออเดอร์แบบ realtime (8 pt) รอเข้ารอบถัดไป

❌ “SDLC = Waterfall”

✅ จริง: SDLC บอกว่ามีกิจกรรมใดบ้างที่ต้องทำ ส่วน Waterfall เป็นเพียงวิธีจัดกิจกรรมเหล่านั้นเป็นรอบยาวรอบเดียว — Agile ก็ใช้ SDLC ชุดเดียวกัน

❌ “Agile ไม่ออกแบบและไม่ทดสอบ”

✅ จริง: Agile ยังออกแบบ พัฒนา ทดสอบ และส่งมอบครบ แต่ทำกับงานชิ้นเล็กทุก iteration เพื่อรับ feedback เร็ว

ลองชี้จุดย้อนกลับ — ทดสอบ PBI-01 แล้วพิมพ์ชื่อบางส่วนไม่พบร้าน: เกณฑ์ยอมรับไม่เคยระบุว่าต้องค้นบางส่วนได้ ทีมจึงต้องย้อนไปแก้ที่ Requirements และ Design ก่อนแก้โค้ด
สังเกต — งานที่ไม่ใช่ฟีเจอร์ใหม่ก็เป็นใบงานของวงจร: PBI-10 ย้าย config (tech-debt) มาจากขั้น Deployment · PBI-09 เอกสาร API (docs) มาจากผู้ใช้อีกกลุ่มคือทีมร้านค้า · bug หลังส่งมอบ = ความต้องการของรอบถัดไป

ตอนที่ 2 · SDLC · ใน Plane

Plane เป็น ศูนย์กลางติดตามงานตลอดวงจร — ไม่ใช่เครื่องมือเขียนหรือ deploy code

ทีมเก็บความต้องการ แผน สถานะ กลุ่มงาน และ feedback ไว้ในโปรเจกต์เดียว แล้วใช้เครื่องมือเฉพาะทางทำ Design · Code · Test · Deploy ต่อ
DevTools Lab › Plane Lab › Work items — List layout จัดกลุ่มตาม State เรียงตาม Priority; 20 ใบใน 7 สถานะ: Backlog 6 · Todo 2 · Ready 2 · In Progress 2 · In Review 1 · Done 7 · Cancelled 0 (เช่น PLAB-16 “ชำระเงินด้วย PromptPay QR”)
  • Requirements → Work itemsเก็บความต้องการเป็นใบงานที่มีเจ้าของ สถานะ และประวัติ
  • Planning → Cyclesเลือก work items เข้า Cycle; ใส่วันเริ่ม–วันจบเมื่อใช้เป็น timebox หรือเว้นทั้งคู่ให้เป็น Draft
  • Tracking → Statesตั้งชื่อ state เองได้ แต่ทุกอันสังกัด 1 ใน 5 กลุ่ม: backlog · unstarted · started · completed · cancelled (+ triage ที่ซ่อนไว้ให้ Intake)
  • Release grouping → Modulesรวมงานตาม feature หรือ release เพื่อดูความคืบหน้าเป็นก้อน — ไม่ได้ deploy ซอฟต์แวร์ให้
  • Feedback → Intake + commentsคำขอใหม่เข้าคิว triage ก่อนรับเข้าบอร์ด ส่วนการถกกันอยู่บน work item
ขอบเขตของ Plane CE v1.4.2 — Plane ติดตามงาน แต่ไม่ build/test/deploy ให้ และไม่มีหน้า Integrations สำเร็จรูปกับ Git/CI (ต้องเชื่อมเองผ่าน REST API + webhook) · โปรเจกต์ที่สร้างใหม่ปิด Cycles · Modules · Views · Intake ไว้ (เปิดเฉพาะ Pages) เปิดทีละฟีเจอร์ที่ Settings › Projects › Plane Lab › Features › Cycles
