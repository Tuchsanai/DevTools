ตอนที่ 3 · Agile · นิยาม

Agile คือการเรียนรู้เป็นรอบสั้น — ส่งมอบทีละส่วน ทดลอง แล้วปรับ

เป้าหมายไม่ใช่ “ทำให้คนทำงานเร็วขึ้น” แต่คือย่นเวลาระหว่าง “ตัดสินใจ” กับ “รู้ว่าตัดสินใจถูกหรือผิด”
นิยาม Agile คือแนวทางพัฒนาผลิตภัณฑ์ที่ทำงานเป็น รอบสั้นซ้ำ ๆ ที่กำหนดกรอบเวลาไว้ล่วงหน้า (iterative) และส่งมอบ ของที่ใช้งานได้เพิ่มขึ้นทีละส่วน (incremental) โดยให้ผู้ใช้ตรวจของจริงทุกรอบ แล้วใช้สิ่งที่เรียนรู้ปรับทั้งลำดับงานและวิธีทำงานของรอบถัดไป
iterative
วนทำซ้ำเป็นรอบ — ของที่ทำไปแล้วถูกนำกลับมาแก้ให้ดีขึ้นได้ ไม่ใช่ทำครั้งเดียวแล้วห้ามแตะ
incremental
ทุกรอบเพิ่ม “ชิ้นที่ใช้งานได้จริง” เข้ากับของเดิม ไม่ใช่สะสมงานที่ยังต่อกันไม่ติด

ปัญหาที่แก้ · ก่อน

ทีมวางแผนและสร้างนานหลายเดือน ผู้ใช้เห็นของจริงตอนท้าย ถ้าเข้าใจปัญหาผิดตั้งแต่ต้น งานเกือบทั้งหมดต้องรื้อ

ปัญหาที่แก้ · หลัง

เลือกส่วนเล็กที่มีคุณค่า → สร้างและทดสอบให้จบ → ให้ผู้ใช้ลองของจริง → ปรับลำดับ backlog ก่อนลงทุนกับส่วนถัดไป

ทำไมสำคัญ — ความต้องการเปลี่ยนได้ และทีมเข้าใจผู้ใช้ผิดได้เสมอ รอบที่สั้นจำกัด “เวลาที่เดินไปผิดทาง” ให้เหลือแค่หนึ่งรอบ และเปลี่ยนการถกเถียงเรื่องความคืบหน้าให้เป็นการดูของที่ใช้ได้จริง
เมื่อทุกคนดูของชิ้นเดียวกัน feedback จะอ้างอิงสิ่งเดียวกัน ไม่ใช่ภาพในใจที่คนละแบบ

หนึ่ง iteration ทำงานครบวงจร — แล้วใช้ feedback เปลี่ยนลำดับงาน

Workflow ของหนึ่งรอบ 6 ขั้นต่อกันเป็นวง: จัดลำดับ backlog → วางแผนรอบ → สร้าง → ทดสอบ → ทบทวนกับผู้ใช้ → ปรับ backlog แล้วเริ่มรอบใหม่ทันที
ทำงานอย่างไร — ซ้าย = วงรอบ 6 ขั้นของหนึ่ง iteration · ขวา = increment สะสมขึ้นทุกรอบ และ feedback จากผู้ใช้วิ่งกลับเข้าขั้นทบทวน · ล่าง = แถบเทียบ Waterfall (feedback ครั้งเดียวตอนจบ) กับ Agile (feedback ทุกรอบ)
องค์ประกอบ 4 อย่างที่ทำให้วงจรปิดได้ — ขาดข้อใดข้อหนึ่ง รอบนั้นจะไม่เกิดการเรียนรู้

รายการสิ่งที่อาจทำทั้งหมด เรียงเป็นลำดับเดียวตามคุณค่า แต่ละรอบหยิบจากบนสุด กรอบเวลาคงที่ที่ทีมวางแผน สร้าง ทดสอบ และทบทวนงานชุดหนึ่งให้จบครบวงจร ส่วนของผลิตภัณฑ์ที่รวมกับของเดิมแล้วใช้ได้จริง ไม่ใช่โค้ดที่ยังทดสอบไม่ได้ ข้อมูลจากผู้ใช้ ทีม และผลทดสอบ ใช้ยืนยันหรือหักล้างสมมติฐาน แล้วปรับ backlog
รอบต้องสั้นแค่ไหน — Agile Manifesto ข้อ 3 ให้ส่งมอบซอฟต์แวร์ที่ใช้ได้ “ทุกไม่กี่สัปดาห์ถึงไม่กี่เดือน โดยเลือกช่วงที่สั้นกว่า” ส่วน Scrum Guide 2020 กำหนด Sprint ไม่เกิน 1 เดือน — ทีมส่วนใหญ่จึงลงตัวที่ 1–4 สัปดาห์ ตามที่ไดอะแกรมนี้ใช้

CampusEats บน Plane — Cycle ทำให้รอบเรียนรู้มองเห็นและติดตามได้

Plane ไม่ได้ “ทำให้ทีมเป็น Agile” แต่ทำให้ลำดับงาน ขอบเขตของรอบ และสิ่งที่เสร็จจริง อยู่ในแหล่งข้อมูลเดียวที่ทุกคนเห็นตรงกัน
ภาพจริงใน Plane · Plane Lab › Cycles — Active cycle: Sprint 2 (60% · Aug 30 – Sep 12, 2026) แผง Progress 3/5 Work items closed ข้างกราฟ Work item burndown · Upcoming 0 · Completed 1 = Sprint 1 (38% · Aug 28–31)

1ตัวอย่างจริง · ตั้งเป้าของรอบ

LAB 4 เขียน Sprint Goal ของ Sprint 1: “นักศึกษาค้นหาร้าน ดูเมนู ใส่ตะกร้า และสั่งอาหารได้ครบวงจร” — เป้าของรอบ ไม่ใช่ Product Goal ของทั้งเทอม

2ส่งมอบเฉพาะที่ Done จริง

รอบนี้รับ 7 ใบ = 19 points แต่จบรอบมีเพียง PBI-01, 02, 10 ที่ผ่าน Definition of Done = 6 points — Review สาธิตเฉพาะสามใบนี้ ไม่ใช่ใบที่ “เกือบเสร็จ”

3ปรับก่อนเริ่มรอบใหม่

feedback บวกผลจริงของรอบแรก (Done 6 จาก 19 points) ใช้เรียง Product Backlog ใหม่ และตั้งขนาดรอบถัดไปจากหลักฐาน

การทำงานใน Plane — หนึ่งรอบ = Cycle เปิดที่ Project settings › Cycles › Enable cycles (หน้านี้อยู่ใต้กลุ่ม Features ในแถบซ้าย — CE ไม่มีหน้า Features หน้าเดียวที่รวมสวิตช์ · ตั้งต้นปิด = cycle_view) · งานในรอบผูกผ่าน cycle_issues · ฟีเจอร์ที่เกี่ยวข้อง: Progress + burndown ของรอบ และ Page สำหรับ Review/Retro · ข้อจำกัด: Plane นับ “เสร็จ” จาก state group completed ไม่ได้ตรวจ Definition of Done แทนทีม

ความเข้าใจผิด ❌ Agile = ไม่ต้องวางแผน

✅ วางแผนถี่ขึ้น: ละเอียดเฉพาะรอบที่กำลังจะทำ ส่วนที่ไกลออกไปเก็บเป็น backlog ที่จัดลำดับใหม่ได้เมื่อมีข้อมูลใหม่

ความเข้าใจผิด ❌ Agile = ไม่ต้องมีเอกสาร

✅ Manifesto ให้คุณค่ากับซอฟต์แวร์ที่ใช้ได้ มากกว่า เอกสารครบถ้วน ไม่ใช่ แทนที่ — ทำเท่าที่ช่วยให้สร้าง ทดสอบ ส่งมอบ และดูแลต่อได้
