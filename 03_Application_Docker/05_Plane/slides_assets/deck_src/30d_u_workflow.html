ตอนที่ 2 · Workflow · นิยาม

Workflow คือ ข้อตกลงว่า “งานอยู่ขั้นไหน และย้ายต่อได้เมื่อใด”

จาก “เสร็จ” ที่แต่ละคนตีความเอง → เป็นเส้นทางเดียวที่ทุกคนมองเห็น ตรวจสอบได้ และส่งต่องานกันได้
Workflow = states ขั้นที่งานอยู่ได้ + transitions การย้ายที่อนุญาต + policies เงื่อนไขที่ต้องผ่านก่อนย้ายครบทั้งสามส่วนเมื่อใด คำว่า “เสร็จ” จึงมีความหมายเดียวกันทั้งทีม

ปัญหาก่อนมี workflow

โปรแกรมเมอร์บอก “เสร็จ” ตอนเขียนโค้ดจบ · ผู้ทดสอบหมายถึงทดสอบผ่าน · เจ้าของผลิตภัณฑ์หมายถึงผู้ใช้ได้ใช้จริง — งานจึงค้างอยู่ระหว่างนิยามที่ไม่ตรงกันโดยไม่มีใครเห็น

ทำไมจึงสำคัญ

เมื่อทุกขั้นมีชื่อและมีเกณฑ์ ทีมตอบได้ทันทีว่างานอยู่ตรงไหน ใครถือต่อ และต้องมีหลักฐานอะไรจึงขยับได้ — โดยไม่ต้องเดินไล่ถามทีละคน

ตัวอย่าง · CampusEats

PBI-04 “สั่งอาหารและรับหมายเลขออเดอร์” เดิน Backlog → Todo → Ready → In Progress → In Review → Done และเข้า Done ได้ก็ต่อเมื่อ acceptance criteria ครบและผ่าน DoD ของทีม

โค้ดกับบอร์ดต้องเล่าเรื่องเดียวกัน มิฉะนั้นสถานะบนบอร์ดจะไม่สะท้อนงานจริง
ความเข้าใจผิด — ❌ “workflow ก็คือชื่อคอลัมน์บนบอร์ด” → ✅ คอลัมน์เป็นเพียงครึ่งเดียว ต้องมีเกณฑ์เข้า–ออกกำกับทุกขั้น · ❌ “ลากการ์ดไป Done แล้วงานเสร็จ” → ✅ การลากคือการบันทึกว่าผ่าน Definition of Done แล้ว ไม่ใช่ตัวทำให้เสร็จ

ตอนที่ 2 · Workflow · กลไก

กลไกของ workflow — state บอกตำแหน่ง · transition บอกทาง · policy บอกเงื่อนไข

1State · ตำแหน่งของงาน

ชื่อ state ตั้งเองได้ไม่จำกัด (Ready · In Review · Testing) แต่ทุก state ต้องสังกัด 1 ใน 5 group: backlog · unstarted · started · completed · cancelled — รายงานและสูตรทุกตัวอ่านที่ group ไม่ใช่ชื่อคอลัมน์

2Transition · ทางที่อนุญาต

เส้นทางหลักเดินหน้า รอทำ → กำลังทำ → ตรวจ → เสร็จ แต่ต้องออกแบบทางถอยด้วย: ตรวจไม่ผ่านให้ย้อนกลับไปแก้ และงานที่ไม่ควรทำต่อให้จบที่ cancelled แทนการปล่อยค้าง

3Policy · เงื่อนไขก่อนย้าย

เขียนเป็นข้อ ๆ ว่าอะไรต้องจริงก่อนเข้าแต่ละขั้น เช่น เข้า Ready ต้องผ่าน Definition of Ready · เข้า Done ต้องผ่าน Definition of Done · แต่ละคอลัมน์รับงานพร้อมกันได้ไม่เกินเพดานที่ทีมตั้ง

เครื่องมือบังคับ vs ทีมบังคับ — Jira นิยาม transition พร้อม condition/validator ได้ในตัว ส่วน Plane CE มีเพียง state + group จึงย้ายจากขั้นใดไปขั้นใดก็ได้ นโยบายจึงต้องอยู่ในเอกสารที่ทีมเห็นร่วมกันและสคริปต์ที่คอยตรวจ
ออกแบบให้พอดี — ขั้นที่ควรมีคือขั้นที่งาน “เปลี่ยนมือหรือรอคนอื่น” จริง ๆ ถ้าตั้ง state ตามทุกกิจกรรมย่อย จะได้คอลัมน์ที่ไม่มีใครดูแล เริ่มจากเส้นทางที่ทีมทำอยู่จริง แล้วค่อยปรับเมื่อเห็นคอขวด

ตอนที่ 2 · Workflow · ใน Plane

Plane ใช้ States + state groups — ตั้งโครงเองได้ แต่ CE ไม่บังคับเส้นทางให้

ภาพจริง · Project settings › States ของ Plane Lab (PLAB) — 5 กลุ่มเรียงจาก Backlog ถึง Cancelled และมี state ที่ทีมเพิ่มเองคือ Ready (Unstarted) กับ In Review (Started)

เส้นทางใน UI และสิ่งที่เก็บจริง

Settings → Projects → Plane Lab → States · แต่ละแถวคือหนึ่งแถวในตาราง states: name ตั้งอิสระ · group มี 5 ค่าตายตัว (+ triage ที่ซ่อนไว้ให้ Intake) · sequence คือลำดับคอลัมน์ · default คือ state ที่งานใหม่ตกลงมา

ย้าย state แล้วระบบทำอะไรให้

เข้ากลุ่ม completed → ตั้ง completed_at เป็นเวลานั้น และล้างเป็นค่าว่างทันทีที่ย้ายออก · กลุ่ม cancelled ก็จบงานเหมือนกันแต่ไม่มี completed_at · ทุกครั้งระบบบันทึก Activity field="state" พร้อมชื่อ state เดิมและใหม่

สิทธิ์และขอบเขตของ CE v1.4.2

เพิ่ม/ลบ/ตั้ง default ได้เฉพาะ project Admin และลบ state ที่เป็น default หรือยังมีงานค้างไม่ได้ · ไม่มี transition rule จึงลากข้ามขั้นได้ทั้งหมด และบอร์ดไม่มี WIP limit — workflow แบบมีเงื่อนไขเป็นฟีเจอร์ของรุ่นเสียเงิน

LAB 5ลงมือทำ + Mini exercise — ในแล็บ: เพิ่ม Ready (unstarted) และ In Review (started) ให้บอร์ดเป็น 7 คอลัมน์ แล้วประกาศ policy ไว้ใน Page · แบบฝึก: ออกแบบ workflow ของทีม support CampusEats 5 ขั้น — ตั้งชื่อ · จับคู่ group · เขียนเกณฑ์เข้า 1 ข้อ แล้วตอบว่า “ใบไหนควรจบที่ completed ใบไหนควรจบที่ cancelled และ Plane บันทึกต่างกันอย่างไร?”
