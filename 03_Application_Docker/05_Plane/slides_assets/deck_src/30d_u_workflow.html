ตอนที่ 2 · Workflow · นิยาม

Workflow คือ ภาษากลางว่า “งานอยู่ขั้นไหน และพร้อมขยับเมื่อใด”

จากงานที่ทุกคนตีความเอง → เป็นกระบวนการที่มองเห็น ตรวจสอบ และส่งต่องานได้
Workflow = states ที่บอกตำแหน่งของงาน + transitions ที่บอกทางย้ายที่อนุญาต + policies ที่บอกเงื่อนไขก่อนย้ายเป้าหมายคือทำให้คำว่า “เสร็จ” มีความหมายเดียวกันทั้งทีม

ปัญหาก่อนมี workflow

นักพัฒนาบอกว่า “เสร็จ” เมื่อเขียนโค้ดจบ แต่ผู้ทดสอบหมายถึงผ่าน test แล้ว งานจึงค้างแบบมองไม่เห็น

ทำไมสำคัญ

ทุกคนเห็นจุดเดียวกันว่าใครต้องทำอะไรต่อ งานค้างอยู่ที่ขั้นใด และต้องตรวจหลักฐานอะไร

CampusEats

เรื่อง “สั่งอาหารล่วงหน้า” เดินจาก Todo → In Progress → In Review → Done เมื่อผ่าน acceptance criteria

โค้ดกับบอร์ดต้องเล่าเรื่องเดียวกัน มิฉะนั้นสถานะบนบอร์ดจะไม่สะท้อนงานจริง
ความเข้าใจผิด — ❌ “Workflow คือชื่อคอลัมน์สวย ๆ” → ✅ ต้องระบุเกณฑ์การเข้า–ออกแต่ละ state ด้วย · ❌ “Done = โค้ดเสร็จ” → ✅ Done ต้องผ่าน Definition of Done ที่ทีมตกลง

กลไกของ workflow — state บอกตำแหน่ง · transition บอกทาง · policy บอกเงื่อนไข

1State กับ group คนละชั้น

ทีมเพิ่ม In Review หรือ Testing ได้ แต่แต่ละ state ต้องอยู่ในกลุ่ม backlog · unstarted · started · completed · cancelled

2เส้นทางทำงาน

งานไหลจากรอทำ → กำลังทำ → ตรวจ → เสร็จ; ถ้าตรวจไม่ผ่านให้ย้อนกลับ และยกเลิกเมื่อไม่ควรทำต่อ

3Policy ทำให้ state มีความหมาย

เข้า In Review ต้องมี PR link; เข้า Done ต้องผ่าน acceptance criteria ครบ ไม่ใช่เพียงลากการ์ดให้จบ

Jira-style vs Plane — ระบบที่มี transition rules บังคับเส้นทางและเงื่อนไขได้ในเครื่องมือ; Plane CE เลือก state + group แบบเรียบง่าย จึงต้องอาศัยวินัยและ policy ของทีม

Plane ใช้ States + state groups — ตั้งโครงได้ แต่ CE ไม่บังคับ transition หรือ WIP

Project settings › States ของ PLAB แสดง 5 state groups และ state In Review ที่เพิ่มเอง

Plane บันทึกอย่างไร

Work item มี state หนึ่งค่า และ state นั้นสังกัดหนึ่ง group; เมื่อย้ายเข้ากลุ่ม completed ระบบตั้ง completed_at และล้างค่านี้เมื่อย้ายออก
