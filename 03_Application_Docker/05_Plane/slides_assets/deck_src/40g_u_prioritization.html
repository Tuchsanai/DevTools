ตอนที่ 3 · Prioritization · นิยาม

Prioritization คือ การตัดสินใจว่า “ทำอะไรก่อน”

ผลลัพธ์ที่ต้องได้คือ backlog ที่เรียงเป็นลำดับเดียว ไม่ใช่กองงานที่ทุกใบติดป้ายว่า “ด่วน”
นิยาม — การจัดลำดับความสำคัญ คือการเปรียบเทียบงานทุกใบในกองเดียวกัน แล้วตัดสินใจ “ลำดับที่จะลงมือทำ” จากคุณค่า · ต้นทุน · ความเสี่ยงที่ลดลง และความเสียหายที่เกิดขึ้นถ้ายังไม่ทำ— ผลลัพธ์คือรายการเรียง 1, 2, 3… ที่ไม่มีอันดับเสมอกัน

ปัญหาที่แก้ · ก่อนจัดลำดับ

ทุกคำขอถูกเรียกว่า “ด่วน” ทีมจึงสลับไปทำงานของคนที่เร่งเสียงดังที่สุด งานที่มีคุณค่าจริงถูกดองไว้ และไม่มีใครตอบได้ว่าใบถัดไปคือใบไหน

ผลลัพธ์ · หลังจัดลำดับ

เหลือรายการเดียวที่เรียงแล้ว ทุกคนจึงเห็น trade-off เดียวกัน: ถ้างานใหม่ขึ้นอันดับ 1 ต้องบอกได้ว่าใบใดถูกเลื่อนลง

ทำไมสำคัญ

กำลังคนและเวลาในหนึ่งรอบมีจำกัด ลำดับที่ชัดทำให้ส่งคุณค่าสูงก่อน และทำให้คำว่า “ยังไม่ทำตอนนี้” มีเหตุผลรองรับ

ตัวอย่าง · CampusEats จาก LAB 3–4

ทีมวางบั๊ก PLAB-5 “ตะกร้าคำนวณราคาผิดเมื่อมีโปรโมชันซ้อนกัน” (Urgent · label bug) ไว้เหนือ PBI-09 “เขียนเอกสาร API สำหรับทีมร้านค้า” (Low · label docs) เพราะบั๊กกระทบยอดเงินจริงทุกวันที่ยังไม่แก้ ส่วนเอกสารเลื่อนได้โดยยังไม่มีใครเสียหาย

ความเข้าใจผิด · ❌ → ✅

❌ ตั้ง priority ครบทุกใบแล้ว = จัดลำดับเสร็จ
✅ priority เป็นเพียงป้ายระดับที่ใช้ซ้ำได้ไม่จำกัด — งานที่เป็น Urgent พร้อมกันหลายใบยังไม่บอกว่าใบไหนก่อน; การจัดลำดับจบเมื่อได้ลำดับที่ไม่มีอันดับเสมอกัน

ลำดับเปลี่ยนได้ ไม่ใช่การกลับคำ — Scrum Guide 2020 เรียก Product Backlog ว่า emergent, ordered list และให้ Product Owner รับผิดชอบการจัดลำดับ การเรียงใหม่จึงคือการใช้ข้อมูลล่าสุด

หลายวิธีคิด — แต่ต้องรวมเป็น backlog ที่เรียงลำดับเดียว

แต่ละกรอบตอบคำถามคนละข้อ จึงใช้เป็นเครื่องมือเปรียบเทียบเพื่อให้เหตุผลตรวจสอบได้ ไม่ใช่สูตรที่ตัดสินแทนทีม
แผนภาพ d40 — สามกรอบป้อนเข้าสู่ backlog ที่เรียงลำดับเดียว · สังเกตใบอันดับ 3 กับ 4 ที่เป็น medium ทั้งคู่ แต่ยังต้องเรียงก่อนหลัง — เลขลำดับคือ sort_order ไม่ใช่ป้าย priority

1ทำงานอย่างไร

ใช้เกณฑ์เดียวกันกับงานทั้งกอง แล้วเทียบทีละคู่จนเหลือลำดับเดียว

2องค์ประกอบ

Value × Effort หา quick win · MoSCoW ตกลงขอบเขต Must / Should / Could / Won't · WSJF = Cost of Delay ÷ Duration ค่ามากทำก่อน · Class of Service กติกาการไหล เช่น Expedite เฉพาะเหตุฉุกเฉิน

3Workflow

PO เสนอลำดับ → ทีมค้านด้วยต้นทุน ความเสี่ยง และ dependency → บันทึกลำดับลง backlog → ทบทวนเมื่อข้อมูลเปลี่ยน

ลองคิดด้วย WSJF · CampusEats — ทีมให้คะแนน Cost of Delay 1–10 และ Duration เป็นวัน: บั๊ก “ตะกร้าคำนวณราคาผิดเมื่อมีโปรโมชันซ้อนกัน” CoD 9 (ลูกค้าจ่ายเงินผิดทุกวัน) ÷ 1 วัน = 9.0 · PBI-09 “เขียนเอกสาร API” CoD 3 ÷ 2 วัน = 1.5 — บั๊กจึงขึ้นอันดับ 1; คะแนนเป็นของทีมเอง ใช้เทียบกันเท่านั้น ไม่ใช่ค่ามาตรฐาน

ตอนที่ 3 · Prioritization · ใน Plane

Plane แยก ป้าย priority ออกจาก ลำดับของ backlog

เส้นทางใน UI — ป้าย: Plane Lab › Work Items › เปิดใบงาน › แผง Properties › Priority · ลำดับ: Work Items › ปุ่ม Display › Order by แล้วลากใบงาน
ภาพจริง · PLAB-12 — แผง Properties เปิดเมนู Priority: Urgent (ติ๊กอยู่) · High · Medium · Low · None — ค่าคงที่ 5 ค่า เพิ่มเองไม่ได้
ภาพจริง · Board › Display — Group by = States · Order by = Priority; ตัวเลือกแรกของ Order by คือ Manual = โหมดเดียวที่ลากจัดลำดับได้

Plane นำไปใช้อย่างไร · priority

คอลัมน์ priority ของตาราง issues เป็น enum 5 ค่า ค่าเริ่มต้น none; Order by › Priority เรียง urgent → high → medium → low → none และใบที่ระดับเท่ากันเรียงต่อด้วย ใบที่สร้างล่าสุดก่อน

ลำดับจริง · sort_order

ตั้ง Order by › Manual แล้วลาก — Plane เขียน sort_order เป็นค่ากึ่งกลางของใบบนกับใบล่าง (วางบนสุด = ใบแรก − 65535) · แก้ priority ไม่ขยับลำดับ

ฟีเจอร์ที่เกี่ยวข้อง · Views

บันทึกฟิลเตอร์ Priority = Urgent, High เป็น View (LAB 5 ตั้งชื่อ “Expedite lane”) และใช้ Group by › Priority ดูว่างานด่วนไปกองอยู่คอลัมน์ใด

ข้อจำกัด CE · Plane v1.4.2 — priority เป็น enum แก้ไขไม่ได้ · ไม่มีช่องกรอกคะแนน WSJF · ไม่มี WIP limit; ถ้า Order by ไม่ใช่ Manual การลากจะย้ายกลุ่มเท่านั้น Plane ขึ้นแถบทับคอลัมน์ว่า “This layout is ordered by Priority” และไม่บันทึกตำแหน่งใหม่
LAB 5 แบบฝึกหัด / ทบทวน — PBI-04 “สั่งอาหารและรับหมายเลขออเดอร์” (Urgent) ทำไม่ได้ถ้ายังไม่มี PBI-03 “เพิ่มเมนูลงตะกร้าและแก้จำนวน” (High): ควรวางใบใดไว้อันดับ 1 · ต้องตั้ง Order by เป็นอะไรจึงลากได้ · และบันทึกการพึ่งพานี้ใน Plane ด้วยอะไร
