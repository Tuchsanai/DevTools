ตอนที่ 3 · Prioritization · นิยาม

Prioritization คือ การตัดสินใจว่า “ทำอะไรก่อน”

ผลลัพธ์ที่ต้องได้คือ backlog ที่เรียงเป็นลำดับเดียว ไม่ใช่กองงานที่ทุกใบติดป้ายว่า “ด่วน”
นิยาม — การจัดลำดับความสำคัญ คือการเปรียบเทียบงานทุกใบในกองเดียวกัน แล้วตัดสินใจ “ลำดับที่จะลงมือทำ” จากคุณค่า · ต้นทุน · ความเสี่ยงที่ลดลง และความเสียหายที่เกิดขึ้นถ้ายังไม่ทำ— ผลลัพธ์คือรายการเรียง 1, 2, 3… ที่ไม่มีอันดับเสมอกัน

ปัญหา · ก่อนจัดลำดับ

ทุกคำขอถูกเรียกว่า “ด่วน” ทีมจึงสลับไปทำงานของคนที่เร่งเสียงดังที่สุด งานที่มีคุณค่าจริงถูกดองไว้ และไม่มีใครตอบได้ว่าใบถัดไปคือใบไหน

ผลลัพธ์ · หลังจัดลำดับ

เหลือรายการเดียวที่เรียงแล้ว ทุกคนจึงเห็น trade-off เดียวกัน: ถ้างานใหม่ขึ้นอันดับ 1 ต้องบอกได้ว่าใบใดถูกเลื่อนลง

ทำไมสำคัญ

กำลังคนและเวลาในหนึ่งรอบมีจำกัด ลำดับที่ชัดทำให้ส่งคุณค่าสูงก่อน และทำให้คำว่า “ยังไม่ทำตอนนี้” มีเหตุผลรองรับ

ตัวอย่าง · CampusEats จาก LAB 3–4

ทีมวางบั๊ก PLAB-5 “ตะกร้าคำนวณราคาผิดเมื่อมีโปรโมชันซ้อนกัน” (Urgent · label bug) ไว้เหนือ “เขียนเอกสาร API สำหรับทีมร้านค้า” (Low · label docs) เพราะบั๊กกระทบยอดเงินจริงทุกวันที่ยังไม่แก้ ส่วนเอกสารเลื่อนได้โดยยังไม่มีใครเสียหาย

ความเข้าใจผิด · ❌ → ✅

❌ ตั้ง priority ครบทุกใบแล้ว = จัดลำดับเสร็จ
✅ priority เป็นเพียงป้ายระดับที่ใช้ซ้ำได้ไม่จำกัด — งานที่เป็น Urgent พร้อมกันหลายใบยังไม่บอกว่าใบไหนก่อน; การจัดลำดับจบเมื่อได้ลำดับที่ไม่มีอันดับเสมอกัน

ลำดับเปลี่ยนได้ ไม่ใช่การกลับคำ — Scrum Guide 2020 เรียก Product Backlog ว่า emergent, ordered list และให้ Product Owner รับผิดชอบการจัดลำดับ การเรียงใหม่จึงคือการใช้ข้อมูลล่าสุด

หลายวิธีคิด — แต่ต้องรวมเป็น backlog ที่เรียงลำดับเดียว

แต่ละกรอบตอบคำถามคนละข้อ จึงใช้เป็นเครื่องมือเปรียบเทียบเพื่อให้เหตุผลตรวจสอบได้ ไม่ใช่สูตรที่ตัดสินแทนทีม
แผนภาพ d40 — สามกรอบป้อนเข้าสู่ backlog ที่เรียงลำดับเดียว แถวล่างคือการแมปกลับไปยัง Plane

1ทำงานอย่างไร

ใช้เกณฑ์เดียวกันกับงานทั้งกอง แล้วเทียบทีละคู่จนเหลือลำดับเดียว

2องค์ประกอบ

Value × Effort หา quick win · MoSCoW ตกลงขอบเขต Must / Should / Could / Won't · WSJF = Cost of Delay ÷ Duration ค่ามากทำก่อน · Class of Service กติกาการไหล เช่น Expedite เฉพาะเหตุฉุกเฉิน

3Workflow

PO เสนอลำดับ → ทีมค้านด้วยต้นทุน ความเสี่ยง และ dependency → บันทึกลำดับลง backlog → ทบทวนเมื่อข้อมูลเปลี่ยน

ตัวอย่างการใช้ WSJF · CampusEats — บั๊ก “ตะกร้าคำนวณราคาผิดเมื่อมีโปรโมชันซ้อนกัน” มี Cost of Delay สูง เพราะผู้ใช้จ่ายเงินผิดทุกวันที่ยังไม่แก้ และใช้เวลาแก้สั้น จึงได้คะแนนสูงกว่า “เขียนเอกสาร API สำหรับทีมร้านค้า” ที่เลื่อนได้โดยยังไม่มีความเสียหาย — ผลคือบั๊กขึ้นเป็นอันดับ 1

ฟิลด์ · priority

enum ตายตัว 5 ค่า ค่าเริ่มต้น none; Order by › Priority เรียง urgent → high → medium → low → none และใบที่ระดับเท่ากันเรียงต่อด้วย ใบที่สร้างล่าสุดก่อน

ลำดับ · sort_order

ลำดับจริงอยู่คนละฟิลด์: ตั้ง Order by › Manual แล้วลากใบงาน — Plane เขียน sort_order ใหม่เป็นค่ากึ่งกลางของใบบนกับใบล่าง; การแก้ priority ไม่ขยับลำดับ

ฟีเจอร์ที่เกี่ยวข้อง · Views

บันทึกฟิลเตอร์ Priority = Urgent, High เป็น View (LAB 5 ตั้งชื่อ “Expedite lane”) และใช้ Group by › Priority ดูว่างานด่วนไปกองอยู่คอลัมน์ใด

ข้อจำกัด CE · Plane v1.4.2 — priority เป็น enum แก้ไขไม่ได้ · ไม่มีฟิลด์คะแนน WSJF · ไม่มี WIP limit ทีมต้องเขียนกติกาจำกัดใบ Expedite ไว้ใน Page เอง
LAB 5 แบบฝึกหัด — PBI-04 “สั่งอาหารและรับหมายเลขออเดอร์” (Urgent) ต้องรอ PBI-03 “เพิ่มเมนูลงตะกร้า” (High) ควรวางใบใดไว้อันดับ 1 และบันทึกความสัมพันธ์นี้ใน Plane อย่างไร
