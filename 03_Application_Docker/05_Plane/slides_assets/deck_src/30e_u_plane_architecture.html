หนึ่งคลิกวิ่งผ่านหลายบริการ — proxy เลือกทาง · api ตอบ · worker ตามเก็บ

มีเพียง proxy ที่เปิดพอร์ตออกสู่ host (LAB 1 map 8080 → :80 ของ Caddy) ที่เหลือคุยกันบนเครือข่ายภายในของ Compose · api, worker, beat-worker และ migrator ใช้ image plane-backend ตัวเดียวกัน ต่างกันที่ entrypoint

1องค์ประกอบ · สามชั้น

หน้าบ้าน web · admin · space · live (:3000) · ตรรกะ api Django :8000 · งานหลังบ้าน worker + beat-worker (Celery) · migrator รันครั้งเดียวแล้วออก

2องค์ประกอบ · ที่เก็บสถานะ

PostgreSQL = ข้อมูลทั้งหมดรวม session · Valkey = cache/lock ไม่ใช่คิว · RabbitMQ = broker คิวเดียวชื่อ celery · MinIO = ไฟล์แนบใน bucket uploads

3ทำงานอย่างไร · ประตูเดียว

ทุกอย่างอยู่ใต้ origin เดียว proxy จึงเลือกปลายทางจาก prefix ของ URL — SPA เรียก API เป็น path สัมพัทธ์ ไม่ข้าม origin

Workflow · CampusEats

กด Save ที่ PLAB-12 → api เขียนแถวใน issues แล้วตอบกลับทันที → โยน task เข้าคิว celery → worker ค่อยเขียน activity และยิง webhook

ความเข้าใจผิด — ❌ 13 container = 13 ผลิตภัณฑ์ → ✅ ระบบเดียวที่แยก process ตามหน้าที่ · ❌ web คือตัวที่คุยกับฐานข้อมูล → ✅ web เสิร์ฟไฟล์ของ SPA เท่านั้น ทุก query วิ่งผ่าน api

Compose เปลี่ยนแบบให้รันได้ — 13 services · 10 volumes · ประตูเดียวสู่ host

docker-compose.yml บอกว่ารันอะไรและพึ่งใคร ส่วน plane.env ใส่ค่าที่เปลี่ยนไปตามเครื่อง
ค่า ${VAR} ถูกแทนด้วยค่าจาก plane.env ตอน up · มี proxy service เดียวที่ publish พอร์ตออก host คือ LISTEN_HTTP_PORT→80 และ LISTEN_HTTPS_PORT→443 (LAB 1 ใช้ 8080 กับ 8443)

Compose ทำงานอย่างไร

หนึ่ง service = หนึ่งหน้าที่ · depends_on จัดลำดับเริ่ม · named volume เก็บสถานะไว้นอกตัว container

LAB 1 ตัวอย่างจริง · ทีม CampusEats

ตั้ง APP_DOMAIN · WEB_URL · CORS_ALLOWED_ORIGINS = localhost:8080 · ต้องได้ 12 Up + migrator Exited (0)

ค่าที่พลาดแล้วเจ็บ

WEB_URL ผิดพอร์ต → หลัง login เด้งไปพอร์ตที่ไม่มีใครฟัง · SECRET_KEY ว่าง → api ออกตั้งแต่ configure_instance · บางบรรทัด ไม่มีผลเลย: GUNICORN_WORKERS ถูกฮาร์ดโค้ด 1 ในไฟล์ compose ส่วน TRUSTED_PROXIES ไม่ถูกส่งเข้า container

ความเข้าใจผิด — ❌ แก้ plane.env แล้ว restart ก็พอ → ✅ ต้อง up -d ให้สร้าง container ใหม่ · ❌ down = ข้อมูลหาย → ✅ มีแต่ down -v ที่ลบ volume · ❌ เปลี่ยน POSTGRES_PASSWORD แล้วปลอดภัยขึ้น → ✅ ถ้าไม่แก้ DATABASE_URL ด้วย Django ยังต่อด้วยรหัสเดิม

ความเข้าใจผิด — ❌ depends_on แปลว่าบริการนั้นพร้อมแล้ว → ✅ compose จัดแค่ลำดับ เริ่ม และไฟล์นี้ไม่มีบล็อก healthcheck เลย (docker compose ps ขึ้น (healthy) เฉพาะ web · admin · space เพราะ image สามตัวนี้ประกาศ HEALTHCHECK มาเอง) · ความพร้อมจริงของ api มาจาก entrypoint ที่วน wait_for_migrations ทุก 10 วินาที แล้วค่อยเปิด gunicorn
หยุดบริการอาการที่เกิด — ทดลองหยุดทีละตัวได้ใน LAB 2
plane-dbหน้าเว็บและ /api/instances/ ยังตอบ 200 เพราะคำตอบถูก cache ไว้ แต่ /api/v1/…/projects/ ที่ต้องอ่าน DB ตอบ 500 — readiness ที่ผ่าน cache จึงโกหกได้
plane-redis/api/instances/ ตอบ 500 ทันที ทุกหน้าจึงโหลดไม่ขึ้น และ live วน reconnect · ข้อมูลไม่หาย เปิดกลับมา cache สร้างใหม่เอง
workerUI ยังลื่นและ CRUD ปกติ แต่ activity, notification, webhook, export กองในคิว celery · เปิดกลับมาแล้วระบายหมดในไม่กี่วินาที
plane-mqงานเบื้องหลังไม่มีที่ส่ง · ถ้าบูต api ใหม่จะไม่ผ่านขั้น register_instance ที่ต้อง publish task เข้า broker
plane-minioแนบไฟล์/ดาวน์โหลด/export ล้ม เพราะเบราว์เซอร์ POST ไฟล์ตรงไปที่ /uploads · แต่ api ยังบูตได้ เพราะไม่มี service ใด depends_on MinIO
