สถาปัตยกรรมของ Plane — แผนที่ว่าอะไรอยู่ที่ไหน และสัมพันธ์กันอย่างไร

อ่านสองมุมพร้อมกัน: ลำดับชั้นของงานที่ผู้ใช้จัดการ และบริการเบื้องหลังที่ทำให้ข้อมูลชุดนั้นใช้งานได้
ลำดับชั้นเชิงตรรกะ: Instance → Workspace → Project → Work item; Cycles, Modules, Views, Pages และ Intake เป็นความสามารถระดับโปรเจกต์
“สถาปัตยกรรม” คือการแบ่งระบบเป็นส่วนที่มีหน้าที่ชัด พร้อมกติกาว่าส่วนเหล่านั้นสื่อสารและพึ่งพากันอย่างไร

หลัง: ระบุตำแหน่งข้อมูล ผู้รับ request และ dependency ได้ตรงจุด

หนึ่งการกระทำไหลผ่านหลายบริการ — proxy เลือกทาง · api จัดการข้อมูล · worker ทำงานเบื้องหลัง

มีเพียง proxy ที่รับ traffic จากภายนอก; บริการอื่นคุยกันบนเครือข่ายภายในของ Compose

1หน้าเว็บ

Browser → proxy (Caddy) → web; /god-mode, /spaces และ /live ไป admin, space และ live

2ข้อมูลธุรกรรม

/api/* และ /auth/* ไป api ซึ่งอ่านเขียน PostgreSQL และใช้ Valkey เป็น cache/lock

3งานเบื้องหลัง

api ส่ง Celery task เข้า RabbitMQ; worker ทำ activity, notification, webhook และ export; beat-worker ส่งงานตามเวลา

CampusEats หนึ่งเรื่อง

เปิด PLAB → web; สร้างเรื่อง “สั่งอาหารล่วงหน้า” → api/PostgreSQL; แนบภาพ → MinIO; activity ผ่าน RabbitMQ → worker

Compose เปลี่ยนแบบสถาปัตยกรรมให้รันได้ — 13 services · 10 volumes · 1 published entry point

docker-compose.yml บอกว่าให้รันอะไรและพึ่งใคร ส่วน plane.env ใส่ค่าที่เปลี่ยนตามเครื่อง
Compose สร้าง 13 containers; ปกติมี 12 ตัวทำงานและ migrator จบด้วย Exited (0) หลัง migrate สำเร็จ

Public origin

APP_DOMAIN เป็นค่าต้นแบบใน plane.env ที่ขยายไปเป็น WEB_URL และ CORS_ALLOWED_ORIGINS; origin/พอร์ตต้องตรงกับ Browser

Secrets

SECRET_KEY ต้องไม่ว่างและควรเปลี่ยนจาก placeholder; LIVE_SERVER_SECRET_KEY ต้องมีค่าเพื่อให้ live ผ่านการตรวจ env ตอนเริ่ม

Data stores

DATABASE_URL, REDIS_URL, AMQP_URL ชี้ไปบริการข้อมูล; storage ใช้ USE_MINIO, S3 credentials, bucket และ FILE_SIZE_LIMIT

อย่าสับสน — volumes อยู่ต่อเมื่อ restart หรือ down; แต่ down -v ลบข้อมูลด้วย
