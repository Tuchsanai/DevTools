Burndown คือกราฟ “งานคงเหลือเทียบกับเวลา”

แกนนอน = วันใน Sprint · แกนตั้ง = งานที่ยังไม่ Done · เส้น ideal เป็นเพียงแนวอ้างอิง ไม่ใช่คำสั่งว่าทีมต้องเดินตามทุกวัน
นิยาม — Burndown คือกราฟอนุกรมเวลาที่พล็อตปริมาณงานคงเหลือใน Sprint เทียบกับวัน เพื่อช่วยคาดการณ์และเปิดบทสนทนาเรื่องความเสี่ยงก่อนถึงวันสุดท้าย

ทำไมสำคัญ

ทำให้ทีมเห็นแนวโน้มร่วมกันและตรวจความคืบหน้าสู่ Sprint Goal ได้เร็วขึ้น แล้วคุยเรื่อง blocker การแตกงาน หรือการเจรจา scope กับ Product Owner โดยไม่ทำลาย Sprint Goal

ปัญหาที่แก้ · ก่อน → หลัง

ก่อน: “เสร็จ 80%” ตรวจสอบยากและค้างหลายวัน
หลัง: เห็นจำนวนใบหรือ points ที่ยังไม่ผ่าน Definition of Done เป็นตัวเลขเดียวกันทั้งทีม

ตัวอย่างจริง · CampusEats — LAB 4 วาง 7 work items รวม 19 points ไว้ใน Sprint 1 ตอนต้นรอบ; PBI-01 ขนาด 3 points แม้เขียนโค้ดไป 80% ก็ยังไม่ลด จนผ่าน DoD จึงทำให้ remaining ลด 19 → 16 points
ความเข้าใจผิด — ❌ actual สูงกว่า ideal = ทีมล้มเหลว  →  ✅ เป็นเพียงสัญญาณให้ตรวจสาเหตุ; burndown ไม่พิสูจน์คุณค่า คุณภาพ หรือการบรรลุ Sprint Goal ด้วยตัวมันเอง
ขอบเขตของแนวคิด — Scrum Guide 2020 ไม่ได้บังคับใช้ burndown และไม่นับเป็นอาร์ติแฟกต์หรืออีเวนต์ของ Scrum; ทีมเลือกใช้เป็นเทคนิคพยากรณ์ได้

อ่าน burndown ให้เป็น — ideal · actual · รูปแบบที่บอกปัญหา

แผนภาพแนวคิด: อ่านฝั่งซ้ายเป็นหลัก; ฝั่งขวาเกริ่น Burn-up ซึ่งแยก Done สะสมออกจาก scope รวม
  • องค์ประกอบแกนเวลา · หน่วยงาน (ใบหรือ points) · ideal · actual
  • วิธีทำงานเริ่มที่ total → หักเฉพาะงาน Done ตามวัน → actual จึงมักลดเป็นขั้น
  • ideal ไม่ใช่พันธะเป็นเส้นตรงที่สมมติว่างาน Done กระจายเท่ากันทุกวัน ซึ่งไม่เกิดจริง
  • ราบนานแล้วดิ่งงานใหญ่ หรือ review/test กองปลาย Sprint
  • กระโดดขึ้นscope เพิ่ม; ต้องตรวจเหตุการณ์จริงและสมาชิกของ Sprint ก่อนตีความ
  • เหนือ / ต่ำกว่า idealเหนือ = ลดช้ากว่าแนวอ้างอิง ตรวจ blocker และขนาดงาน · ต่ำกว่า = เร็วกว่าแนว แต่ยังต้องตรวจคุณภาพตาม DoD
Workflow การอ่าน — ดู “รูปทรง” → หาเหตุการณ์จริงบนบอร์ด → คุยเหตุและทางเลือกกับทีม; อย่าสรุปจากเส้นเดียว เพราะกราฟไม่บอกเองว่างานติดที่ใครหรือขั้นใด

สูตรที่ Plane ใช้

remaining(d) = total − Σ ใบที่ completed_at ≤ d ทุกวันในช่วง Cycle · Work items นับใบละ 1 · Estimates รวม EstimatePoint.value · เส้น ideal = total × (1 − i/(n−1)) วาดโดยฝั่งเว็บ ไม่ได้มาจาก API · completed_at เขียนตอนใบเข้ากลุ่ม completed

อ่านให้ถูก · หางกราฟที่ดิ่งถึง 0

API ส่งวันในอนาคตเป็น null แต่หน้าเว็บแปลงเป็น 0 ก่อนวาด เส้นจึงดูเหมือนลงถึงศูนย์ — จุดจริงจุดสุดท้ายคือ “วันนี้” และต้องเท่ากับ total ลบงานที่ Done ในแถบ Progress

ฟีเจอร์ที่เกี่ยวข้อง · Estimates

โหมด Estimates ใช้ได้เมื่อโปรเจกต์เปิดระบบ Points ที่ Project settings › Work structure › Estimates · ถ้าใช้ Categories ปลายทางตอบ 200 พร้อมกราฟว่าง ไม่ใช่ error

ข้อจำกัด CE และกรณีขอบ — CE ไม่ตรวจ DoD ให้ · ใบที่ cancelled ไม่ถูกหักออก จึงค้างบนเส้น remaining · เปิดงานที่ Done กลับ = ล้าง completed_at ใบนั้นหายจากประวัติทุกวัน · เพิ่มใบกลาง Cycle ยก total ของทุกวันย้อนหลัง · หลังกด Transfer กราฟถูกแช่แข็งใน progress_snapshot ถาวร
