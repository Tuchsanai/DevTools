ตอนที่ 3 · WIP limit · นิยาม

WIP limit — จำกัดงานที่เริ่ม เพื่อให้งานเสร็จ

“WIP คือ งานที่เริ่มแล้วแต่ยังไม่ Done · WIP limit คือจำนวนสูงสุดที่ยอมให้ค้างในคอลัมน์หรือกับคนหนึ่งคน ณ ขณะเดียวกัน”
งานที่เสร็จ 1 ใบสร้างคุณค่าได้มากกว่า งาน 5 ใบที่ “เกือบเสร็จ”เป้าหมายคือ flow ของชิ้นงาน ไม่ใช่ทำให้ทุกคนเริ่มงานตลอดเวลา

ก่อนจำกัด · ทุกอย่าง 80%

ทุกคนรับงานใหม่ทันที งานกองในพัฒนาและ review ต้องสลับบริบทบ่อย แต่ลูกค้ายังไม่ได้รับงานที่ Done สักใบ

หลังจำกัด · จบก่อนเริ่ม

ดึงงานใหม่ได้เมื่อมีช่องว่าง คอลัมน์ที่เต็มทำให้คอขวดมองเห็น ทีมจึงช่วยกันปิดงานค้างก่อน

1อะไรนับเป็น WIP

งานที่เข้าสู่ขั้นลงมือแล้วและยังไม่ Done รวมเวลาที่รอ test, review หรือ deploy; งานใน To Do ที่ยังไม่เริ่มไม่นับ

2ปัญหาที่แก้

ลดการเริ่มพร้อมกัน ลดคิวที่ซ่อนอยู่ และบังคับให้ทีมเห็นจุดที่งานติด แทนการเพิ่มงานเข้าไปเรื่อย ๆ

3ทำไมสำคัญ

เมื่อ throughput ใกล้เดิม Little’s Law อธิบายว่า WIP ลดลง → cycle time เฉลี่ยสั้นลง โดยไม่ต้องเพิ่มคน

ขอบเขตของ limit — ตั้งต่อขั้นตอน เช่น In Progress ≤ 3, Review ≤ 2 เพื่อป้องกันคอขวดทั้งระบบ และอาจเสริม limit ต่อคนเพื่อไม่ให้คนหนึ่งถือหลายใบเกินไป

คอลัมน์เต็ม = หยุดดึงงานใหม่ แล้วช่วยงานที่ค้าง

ลด WIP จาก 12 เหลือ 6 ขณะที่ throughput เท่าเดิม 3 ใบ/วัน → cycle time โดยประมาณลดจาก 4 เหลือ 2 วัน
แผง Little’s Law จากภาพ flow metrics

1ตั้ง limit เริ่มต้น

นับ WIP ปัจจุบัน แล้วเลือกเพดานที่เล็กพอให้คอขวดปรากฏแต่ทีมยังทำงานได้ เช่น In Progress ≤ 3 · Review ≤ 2

2เมื่อเต็ม

ห้าม pull ใบใหม่ · ช่วย review/test · ปลด blocker · แตกงานที่ใหญ่ เป้าหมายคือทำให้ช่องว่างเกิดทางขวา

3วัดแล้วปรับ

ติดตาม cycle time กับ throughput 1–2 รอบ ปรับ limit ทีละค่า และบันทึกเหตุผล; limit เป็นเพดาน ไม่ใช่เป้าหมายที่ต้องเติมให้เต็ม

ตอนที่ 3 · WIP limit · ตัวอย่าง

CampusEats — ปิดคิว review ก่อนรับบั๊กเพิ่ม

สถานการณ์: ทีม 3 คนมีงานเริ่มแล้ว 12 ใบ throughput เฉลี่ย 3 ใบ/วัน และมีบั๊ก “ชำระเงินแล้วคำสั่งซื้อไม่เข้าโรงอาหาร” เข้ามา

1ไม่มี limit

ทีมรีบดึงบั๊กเข้า In Progress ทั้งที่งานเดิมค้าง ทุกคนสลับไปมา; WIP 12 ÷ 3 ใบ/วัน ≈ cycle time 4 วัน

2Review เต็ม 2/2

นโยบายห้ามดึงงานใหม่ นักพัฒนาจึงช่วย test และ review ใบที่ใกล้ Done จนส่งมอบได้ 1 ใบและเกิดช่องว่าง

3ดึงตามความจุจริง

จึงเริ่มแก้บั๊ก CampusEats; ถ้าลด WIP ทั้งระบบเหลือ 6 และ throughput ยัง 3 ใบ/วัน cycle time ≈ 2 วัน

❌ “limit ทำให้คนว่างหรือลดผลงาน”

การไม่เริ่มใบใหม่ไม่ได้แปลว่าหยุดทำงาน ทีมใช้ความจุช่วย review, test, แก้ blocker และทำใบที่ค้างให้ Done — วัดผลที่งานส่งมอบ ไม่ใช่จำนวนงานที่เริ่ม

✅ “limit ปกป้อง flow ของทั้งระบบ”

จำกัดตามขั้นตอนที่เป็นคิวร่วมก่อน เช่น In Progress และ Review; limit ต่อคนเป็นเพียงตัวเสริม เพราะคนว่างแต่คอลัมน์ Review เต็มก็ยังไม่ควรเริ่มเพิ่ม

อย่าใช้สูตรแบบกลไก — Little’s Law ใช้กับค่าเฉลี่ยของระบบที่ค่อนข้างนิ่ง: WIP, throughput และช่วงเวลาต้องนับด้วยขอบเขตเดียวกัน; งานเร่งด่วนยังต้องผ่าน policy ที่ทีมตกลง ไม่ใช่ข้าม limit โดยไม่มีเหตุผล
