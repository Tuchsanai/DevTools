ตอนที่ 3 · Backlog Refinement · นิยาม

Backlog Refinement คือการทำงานใกล้มือให้พร้อม — เล็ก · ชัด · ประเมินได้

ทีมกลั่นรายการบนสุดอย่างต่อเนื่อง เพื่อให้ Sprint Planning เลือกงานได้โดยไม่ต้องเริ่มทำความเข้าใจทุกอย่างจากศูนย์
Backlog Refinement คือกิจกรรมต่อเนื่องที่ทีม แตกงานใหญ่ · เติมรายละเอียดและ acceptance criteria · หา dependency · ประเมินขนาด ให้รายการลำดับต้น ๆ “พร้อมพอ” สำหรับการวางแผนรอบถัดไป

ก่อน refine

เรื่องใหญ่และกำกวม เช่น “ทำระบบสั่งอาหาร” ไม่มีเงื่อนไขทดสอบ ทีมพบคำถามใหม่กลาง Sprint และ Planning ยืดเป็นชั่วโมง

หลัง refine

งานบนสุดเล็กพอทำใน Sprint มีคุณค่าชัด มีเกณฑ์รับงาน และมี estimate ทีมจึงเลือกได้โดยเห็นขนาดและความเสี่ยง

ทำไมสำคัญ — คำถามที่ถูกตอบก่อนเริ่มงานมีต้นทุนต่ำกว่าการหยุดทีมกลาง Sprint; refinement จึงลดงานค้าง ลดความประหลาดใจ และทำให้การคาดการณ์มีฐานร่วม
ทีมเปรียบเทียบขนาดของงานร่วมกัน เพื่อเปิดเผยความเข้าใจและความเสี่ยงที่แต่ละคนเห็นต่างกัน

❌ Refinement = ประชุมใหญ่ก่อน Sprint

✅ เป็นกิจกรรมต่อเนื่อง ทำทีละน้อยกับงานใกล้มือ; ไม่ต้องแจกแจงทั้ง backlog และไม่ใช่ Scrum event ที่ Scrum Guide กำหนด

CampusEats — จากไอเดียกว้าง “ระบบสั่งอาหารในมหาวิทยาลัย” ทีมเลือกเฉพาะส่วนใกล้ทำ แล้วแตกเป็นเรื่องเล็ก เช่น เลือกร้าน · เลือกเมนู · เห็นเวลารับอาหาร ก่อนค่อยประเมินและเรียงลำดับ

ตอนที่ 3 · Backlog Refinement · กลไก

กลั่นผ่าน funnel — จากไอเดียดิบสู่รายการ Ready

รายละเอียดเพิ่มขึ้นเมื่อรายการเข้าใกล้การทำจริง ส่วนรายการไกล ๆ ยังเปลี่ยนหรือหายไปได้ จึงไม่ควรลงทุนเขียนละเอียดเท่ากันทั้งหมด
หยิบจากรายการที่จัดลำดับแล้ว → refine ทีละน้อย → เข้า Sprint Planning เฉพาะใบที่ผ่านเกณฑ์ Ready ของทีม

1DEEP · ดูสุขภาพทั้ง backlog

Detailed appropriately · Estimated · Emergent · Prioritized — ใบใกล้ทำละเอียดกว่า ใบไกลเปลี่ยนได้ และทั้งหมดมีลำดับเดียว

2Refine · ทำกับใบลำดับต้น

ยืนยันคุณค่าและขอบเขต → เขียน acceptance criteria ที่ตรวจได้ → แตกใบใหญ่ → เปิดเผย blocker/dependency → ประเมินขนาดร่วมกัน

3Definition of Ready · เช็กก่อนเลือก

ตัวอย่างข้อตกลงทีม: ผ่าน INVEST · criteria ชัด · มี estimate · เล็กกว่าเพดานที่ทีมกำหนด · ไม่มี blocker ที่ทำให้เริ่มไม่ได้

อย่าสับสนกับ Definition of Done — Ready = พร้อมเริ่มและวางแผนได้; Done = ผลงานผ่านเกณฑ์คุณภาพแล้ว DoR เป็นข้อตกลงเสริมของทีม ไม่ใช่อาร์ติแฟกต์บังคับของ Scrum

ตอนที่ 3 · Backlog Refinement · ใน Plane

Refine ใน Plane — เปิดใบงานบน List แล้วทำข้อมูลให้พร้อม

ในหน่วยนี้ ทีมใช้ work item detail และ properties เป็นแหล่งข้อมูลเดียวสำหรับเตรียมรายการ ก่อนเลือกงานเข้า Cycle
Work item detail ของเรื่อง CampusEats: description และ properties เช่น state · priority · assignee · estimate · labels · cycle · module · dates
พื้นที่ทำงาน — ใช้ List layout มองรายการตามลำดับ แล้วเปิดใบลำดับต้นเพื่อเติมรายละเอียด; List เป็นเพียง layout หนึ่ง เกณฑ์ “Ready” ยังเป็นข้อตกลงของทีม

1ทำความหมายให้ตรวจได้

ชื่อสรุปคุณค่า · description เก็บบริบทและ acceptance criteria · labels ช่วยจัดหมวด; จากนั้นใช้ comment คุยข้อสงสัยโดยผูกกับใบเดียวกัน

2ทำขนาดและโครงสร้างให้เหมาะ

แตกงานด้วย Sub-work items (parent) และใส่ Estimate เมื่อโปรเจกต์เปิดระบบ Points หรือ Categories; โปรเจกต์เลือก estimate system ที่ใช้งานอยู่หนึ่งระบบ

3CE ไม่บังคับ Definition of Ready

Plane CE ไม่มี transition rules ที่ตรวจ DoR ก่อนย้าย state ทีมจึงใช้ checklist ที่ตกลงกัน และตรวจให้ผ่านก่อนเลือกใบงานเข้า Cycle

LAB 3–4 ลองทำ — เลือก CampusEats 1 ใบที่กว้างเกินไป แล้ว (1) แตกเป็น 2–3 เรื่องเล็ก (2) เขียน acceptance criteria อย่างน้อย 2 ข้อ (3) ใส่ label และ estimate จากนั้นถามเพื่อนว่า “ข้อมูลใดขาดจนยังไม่ควรเลือกเข้า Cycle?”
