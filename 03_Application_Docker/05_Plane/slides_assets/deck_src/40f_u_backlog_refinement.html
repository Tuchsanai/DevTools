Backlog Refinement — ทำใบงานที่ใกล้ถึงคิวให้ เล็ก · ชัด · ประเมินได้

ทีมกลั่นรายการบนสุดอย่างต่อเนื่อง เพื่อให้ Sprint Planning ใช้เวลาไปกับการวางแผน ไม่ใช่การเพิ่งเริ่มทำความเข้าใจงาน
นิยาม — Backlog Refinement คือ การแตกและนิยาม Product Backlog item ให้เล็กลงและแม่นยำขึ้น เป็นกิจกรรมต่อเนื่องที่เติม คำอธิบาย · ลำดับ · ขนาด ให้ใบงาน; ใบที่ Scrum Team ทำให้ Done ได้ภายในหนึ่ง Sprint ถือว่า “ready” พอจะถูกเลือกใน Sprint Planning— เรียบเรียงจาก Scrum Guide 2020 · หัวข้อ Product Backlog

ปัญหา · ก่อน refine

มีใบเดียวเขียนว่า “ทำระบบสั่งอาหาร” ไม่มีเกณฑ์ว่าอะไรคือเสร็จ ประเมินไม่ได้ · Planning หมดเวลาไปกับคำถามว่าใบนี้แปลว่าอะไร แล้วยังเจอคำถามใหม่กลาง Sprint จนงานค้างข้ามรอบ

ผลลัพธ์ · หลัง refine

ใบบนสุดเล็กพอทำให้ Done ได้ในหนึ่ง Sprint · คุณค่าต่อผู้ใช้ชัด · มี acceptance criteria ที่ตรวจว่าผ่าน/ไม่ผ่านได้ · มีขนาดที่ทีมเห็นตรงกัน Planning จึงเหลือแค่ “เลือกและวางแผน”

ทำไมสำคัญ — คำถามที่ตอบก่อนเริ่มงาน ถูกกว่าการหยุดทีมกลาง Sprint มาก; refine จึงลดงานค้าง ลดความประหลาดใจ และทำให้ทุกคนคาดการณ์บนฐานเดียวกัน
ทีมเทียบขนาดของงานร่วมกัน — บทสนทนาตรงนี้เผยความเข้าใจและความเสี่ยงที่แต่ละคนเห็นต่างกัน

❌ ความเข้าใจผิดที่พบบ่อย

❌ “refinement = ประชุมใหญ่ก่อน Sprint” → ✅ เป็นกิจกรรมต่อเนื่อง ทำทีละน้อยกับงานใกล้คิว ไม่ใช่ 1 ใน 5 Scrum event และไม่ต้องแจกแจงทั้ง backlog

❌ “ใบใหญ่ให้แตกเป็นงานย่อยเสมอ” → ✅ ใบที่ใหญ่เกินหนึ่ง Sprint ต้องแตกเป็นใบพี่น้องที่ส่งคุณค่าได้เอง ส่วนงานย่อยไว้บันทึกขั้นตอนของใบที่เล็กพอแล้ว

ตัวอย่าง · CampusEats — ไอเดีย “ระบบสั่งอาหารในมหาวิทยาลัย” ถูกกลั่นเป็นใบที่ส่งคุณค่าได้ทีละใบ: ค้นหาร้าน (3 pt) · ดูเมนูและราคา (2) · เพิ่มลงตะกร้า (3) · สั่งอาหารและรับหมายเลขออเดอร์ (5) ส่วน “ติดตามสถานะออเดอร์แบบ realtime” (8) และ “ชำระเงินด้วย PromptPay QR” (8) ยังใหญ่และมีคำถามค้าง จึงรอ refine ต่อ ไม่ถูกดึงเข้า Sprint 1 ของ LAB 4

กลั่นผ่าน funnel — จากไอเดียดิบสู่รายการ Ready

รายละเอียดเพิ่มขึ้นเมื่อรายการเข้าใกล้การทำจริง ส่วนรายการไกล ๆ ยังเปลี่ยนหรือหายไปได้ จึงไม่ควรลงทุนเขียนละเอียดเท่ากันทั้งหมด
ซ้าย อ่านจากล่างขึ้นบน: ไอเดียดิบ → refine ทีละน้อย → Ready → หยิบเข้า Sprint Planning · ขวาบน DEEP = คุณสมบัติของ backlog ที่ดี · ขวาล่าง ตัวอย่าง Definition of Ready 4 ข้อ (INVEST · AC ตรวจได้ · ประเมินแล้ว ≤ 8 pt · ไม่มี blocker) ที่ทีมตกลงกันเอง

1หลักการ · ละเอียดตามระยะ

ใบบนสุดต้องละเอียดพอเริ่มทำได้ ใบล่างหยาบไว้ก่อนได้ เพราะอาจถูกแก้หรือถูกตัดก่อนถึงคิว — ลงแรงเขียนเมื่อใกล้ทำ

2องค์ประกอบ · ใบที่ refine แล้ว

ชื่อที่บอกคุณค่าต่อผู้ใช้ · บริบท · acceptance criteria ที่ตรวจได้ · ขนาด (story point) · dependency ที่รู้แล้ว

3Workflow · ใครทำอะไร

PO เรียงลำดับและอธิบายคุณค่า → ทีมถามจนเข้าใจ เขียน criteria แตกใบที่ใหญ่เกินหนึ่ง Sprint → Developers กำหนดขนาด → ใบที่ผ่านเกณฑ์รอ Sprint Planning

DoR ≠ DoD — Scrum Guide เรียกใบที่ Done ได้ในหนึ่ง Sprint ว่า “ready” แต่ไม่มีอาร์ติแฟกต์ชื่อ DoR: checklist คือข้อตกลงทีม ส่วน DoD เป็น commitment ของ Increment
จังหวะ — ทำทีละน้อยต่อเนื่อง ไม่มีรูปแบบบังคับ; Scrum Guide 2017 เคยแนะ ≤10% ของ capacity ทีม · ฉบับ 2020 ตัดออก

Refine ใน Plane — เปิดใบจาก List แล้วทำข้อมูลให้ครบก่อนเข้า Cycle

เส้นทางใน UI — Plane Lab › Work Items › layout List › เปิดใบบนสุด → แก้ Description · ตั้งค่าใน Properties · ปุ่ม Add sub-work item / Add relation อยู่ในใบเดียวกัน
ภาพจริง — PLAB-12 “สั่งอาหารและรับหมายเลขออเดอร์”: description เป็น user story + acceptance criteria 2 ข้อ · properties ที่ตั้งไว้แล้ว: In Review · dev1 · Urgent · Estimate 5 · Ordering · Sprint 2 · label feature · Start/Due Sep 02–05 (ช่อง Parent ยังว่าง) · ปุ่ม Add sub-work item / Add relation คือเครื่องมือ refine ในหน้าเดียวกัน

1การใช้ใน Plane · ทำความหมายให้ตรวจได้

ชื่อใบสรุปคุณค่า · Description เก็บบริบทและ acceptance criteria (ใช้ to-do list ติ๊กได้) · Labels จัดหมวด · ข้อสงสัยที่ค้างให้ถามใน Comment ของใบนั้น ไม่ใช่ในแชตทีม

2ฟีเจอร์ที่เกี่ยวข้อง · แตกและเชื่อมงาน

Sub-work items (ฟิลด์ parent) บันทึกขั้นตอนย่อย · Relations › Blocked by เปิดเผย dependency · Estimate ใส่ได้เมื่อเปิด Estimates ของโปรเจกต์ (CE มี Points หรือ Categories และใช้ได้ทีละหนึ่งระบบ)

3ข้อจำกัด CE · บังคับ DoR ไม่ได้

v1.4.2 ไม่มี transition rule และไม่บังคับฟิลด์ใดนอกจากชื่อ จึงเพิ่มใบที่ยังไม่พร้อมเข้า Cycle ได้ — ทีมต้องตกลง DoR เอง แล้วตรวจด้วยสายตาหรือสคริปต์ (lint_work_items.py ของ LAB 3 ให้คะแนน AC · assignee · priority · due · label)

LAB 3–4 แบบฝึกหัด — “ติดตามสถานะออเดอร์แบบ realtime” (8 pt) ถูกกันไว้นอก Sprint 1 เพราะใหญ่เกิน จง refine ใบนี้: (1) แตกเป็นใบพี่น้องที่ส่งคุณค่าได้เองอย่างน้อย 2 ใบ (2) เขียน acceptance criteria ใบละ ≥ 2 ข้อ (3) ใส่ Label และ Estimate ใหม่ แล้วตอบว่า ยังขาดข้อมูลใดจนทีมไม่ควรเลือกใบนี้เข้า Cycle และงานย่อยแบบใดควรเป็น sub-work item แทนที่จะเป็นใบแยก
