CampusEats · ตัวเลขบอกอะไร

ปัญหาไม่ได้อยู่ที่ “คนไม่ขยัน” แต่อยู่ที่ขั้นที่รับงานเข้าเร็วกว่าส่งต่อได้ — WIP (In Progress + In Review) โต 4→6 ใบ ขณะ throughput เท่าเดิม เวลารอเฉลี่ยจึงยาวขึ้น

ความเข้าใจผิดที่พบบ่อย — ❌ “CFD คือภาพสถานะของบอร์ดวันนี้” → ✅ หนึ่งคอลัมน์ของ CFD คือหนึ่งวัน ต้องมีข้อมูลหลายวันจึงเป็น CFD · ❌ “เส้นบนสุดสูงขึ้น = แย่” → ✅ เส้นบนคืองานที่เข้าระบบสะสม ซึ่งขึ้นเสมอ; สิ่งที่ต้องอ่านคือ ความหนาและความชันของแต่ละแถบ ร่วมกัน

อ่าน CFD จาก เส้นขอบ · ความหนา · ช่องว่าง · ความชัน

นับงานคงค้างของแต่ละสถานะตอนสิ้นวันแล้วซ้อนขึ้นเป็นแถบ · เส้นสะสมทุกเส้น “ไม่ลดลง” (ถ้าลด แปลว่ามีการลบหรือยกเลิกงาน) · ช่องว่างแนวนอนเป็นค่า lead time โดยเฉลี่ยและโดยประมาณ ไม่ใช่เวลาจริงของงานใบใดใบหนึ่ง

กลไก · สร้างกราฟ 3 ขั้น

1) นับงานในแต่ละสถานะ ณ สิ้นวัน 2) บวกสะสมจากปลายน้ำขึ้นมาตามลำดับ workflow 3) ระบายพื้นที่ระหว่างเส้น แล้วเปรียบเทียบรูปทรงข้ามวัน

องค์ประกอบ · เส้นขอบและแถบ

เส้นบนสุด = งานที่เข้าระบบสะสม · ขอบบนของแถบ Done = งานที่เสร็จสะสม · พื้นที่ระหว่างเส้นที่ติดกัน = จำนวนงานในสถานะนั้น; WIP คือความหนารวมของแถบที่ “เริ่มแล้วแต่ยังไม่เสร็จ”

Workflow การอ่าน · ตามรูปทรง

อ่านแนวตั้งหา WIP → แนวนอนหา lead time โดยประมาณ → ดูความชันเส้น Done หา throughput → หาแถบที่กว้างขึ้นเรื่อย ๆ เพื่อระบุคอขวด

CFD ใช้ “ยืนยันผล” ไม่ใช่สั่งการ — แถบที่กว้างขึ้นบอกว่าขั้นนั้นรับงานเข้าเร็วกว่าที่ส่งออกได้ หน้าที่ของทีมคือไปหาสาเหตุที่ขั้นนั้น (รอรีวิว · รอ deploy · รอคนนอกทีม) แล้วดู CFD ของรอบถัดไปว่านโยบายที่ตั้งไว้ — เช่น WIP limit ในหน่วยก่อนหน้า — ทำให้แถบแคบลงจริงหรือไม่

ข้อจำกัดของ Plane CE

v1.4.2 ไม่มี CFD (และไม่มี velocity, burn-up, lead/cycle time สำเร็จรูป) · ที่ใกล้ที่สุดคือ Workspace › Analytics › Work items ซึ่งวาด Created vs Resolved ราย “เดือนที่สร้าง” และนับ resolved จากกลุ่ม completed ปัจจุบัน จึงไม่ใช่การเล่นย้อนประวัติ state; Guest เปิดหน้านี้ไม่ได้ (403)

ข้อมูลที่ Plane เก็บให้ · Activity

ทุกครั้งที่ state เปลี่ยน Plane เขียน IssueActivity field="state": ชื่อ state อยู่ใน old/new_value และ UUID อยู่ใน old/new_identifier — ชื่อถูกแก้ภายหลังได้ งานจริงจึง join ด้วย UUID กับ states.group

Workflow · ดึง → ย้อนสถานะ → วาด

LAB 9 ดึง work items, states และ activity ราย work item (…/work-items/<id>/activities/) ผ่าน REST API v1 ที่จำกัด 60 ครั้ง/นาที จึงดึงเฉพาะใบที่ updated_at เปลี่ยน · แล้วเริ่มจากสถานะปัจจุบัน ย้อน transition ทุกอันที่เกิด หลัง สิ้นวันนั้น · มี pytest คุมสูตรก่อนวาดแถบซ้อน

Mini exercise — อ่านจากภาพ: 28 ส.ค. มี 8 ใบ (completed 2 · started 5 · unstarted 1) ส่วน 31 ส.ค. มี 13 ใบ (completed 8 · started 3 · unstarted 2) → (1) throughput เฉลี่ยของช่วงนี้กี่ใบ/วัน (2) แถบ started แคบลงเพราะ “ปิดงานได้” หรือเพราะ “เลิกเริ่มงาน” — ดูจากอะไร (3) เส้นบนสุดกระโดดจาก 8 เป็น 13 หมายถึงอะไร และกระทบ lead time อย่างไร
