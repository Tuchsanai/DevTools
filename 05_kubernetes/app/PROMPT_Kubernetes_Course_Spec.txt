ส่วนที่ 0 — สรุปต้นแบบที่ต้องยึดตาม (DESIGN DNA)
--------------------------------------------------------------------------------
ลักษณะเด่นที่ต้องคงไว้ในชุด Kubernetes ทุกข้อ :

  1. สอนจาก "ปัญหา" ก่อนเสมอ ไม่ได้สอนจาก "เครื่องมือ"
     ต้นแบบเปิดด้วยการให้ผู้เรียนเห็น pain point ของการเปิด backend ตรง ๆ
     (2 service = 2 port, 20 service = 20 port) แล้วจึงค่อยเสนอ proxy เป็นคำตอบ

  2. วงจรการเรียนรู้ประจำทุกแล็บ
        ทายผล -> รัน -> สังเกตหลักฐาน -> อธิบายเหตุผล -> ทดลองให้พัง -> แก้กลับ
     ทุกแล็บต้องมีหัวข้อ "การทดลองจำลองความล้มเหลว" อย่างน้อย 1 หัวข้อ ที่จงใจทำให้ระบบเสีย
     เพื่อให้ผู้เรียนเห็นอาการจริง แล้วแก้กลับให้ถูก

  3. ทุกคำสั่งมีสามส่วนเสมอ (กฎเหล็ก ห้ามข้าม)
        (ก) code block ของคำสั่ง
        (ข) บล็อกอ้างอิง "> 📝 **คำอธิบาย:**" อธิบายทีละ flag/ทีละส่วน คั่นด้วย ·
        (ค) "✅ **Expected output**" พร้อม code block ของผลรัน "จริง" ที่ copy มา
     ห้ามแต่งผลลัพธ์ขึ้นเอง ถ้าค่าบางส่วนไม่คงที่ (hash, IP, เวลา, ชื่อ pod)
     ให้เขียนกำกับไว้ว่า "ค่าเหล่านี้ต่างกันได้"

  4. ผู้เรียนต้องพิสูจน์ได้ด้วยหลักฐาน 3 มุมเสมอ
        ผลใน terminal · หน้า UI/Dashboard · log ของระบบ
     (ในชุด Kubernetes = ผล kubectl · Kubernetes Dashboard หรือหน้าเว็บของแอป ·
      kubectl logs / kubectl get events)

  5. เอกสารมีวินัยเรื่อง "เริ่มสะอาด จบสะอาด"
     ทุกแล็บปิดท้ายด้วย Cleanup และพิสูจน์ Clean Re-run ว่าลบแล้วสร้างใหม่ได้ผลเดิม

  6. ภาษา : ไทยเป็นหลัก ศัพท์เทคนิคคงภาษาอังกฤษ (Pod, Deployment, Service,
     rolling update) น้ำเสียงเป็นครูที่ชวนคิด ใช้ "ประโยคคำถามนำ" ก่อนเริ่มแล็บ
     และปิดท้ายด้วยประโยค "จำภาพเดียวให้ได้ : ..."

  7. เป้าหมายคือความเข้าใจ ไม่ใช่ความครบถ้วน
     ถ้าต้องเลือกระหว่าง "อธิบายหนึ่งเรื่องให้เข้าใจจริง" กับ "พูดถึงห้าเรื่อง
     แบบผิวเผิน" ให้เลือกอย่างแรกเสมอ ตัดเนื้อหาที่ไม่ช่วยให้เข้าใจแนวคิดออก


ส่วนที่ 1 — เป้าหมายรายวิชา
--------------------------------------------------------------------------------
กลุ่มผู้เรียน :
  นักศึกษาปริญญาตรีชั้นปีที่ 4 ที่ "ไม่เคยใช้ Kubernetes มาก่อน"
  พื้นฐานที่มีมาแล้ว : Linux command line, Docker (image · container · compose ·
  network · port mapping), Git และแนวคิด reverse proxy / load balancer
  จากชุด Traefik ที่เรียนไปก่อนหน้า

เป้าหมายรายวิชา :
  ให้นักศึกษา **เข้าใจแนวคิด (concept)** ของ Kubernetes เป็นหลัก
  ว่าแต่ละองค์ประกอบคืออะไร มีไว้แก้ปัญหาอะไร และทำงานร่วมกันอย่างไร
  ส่วนการลงมือปฏิบัติมีไว้เพื่อ "พิสูจน์แนวคิดให้เห็นกับตา" ไม่ใช่เพื่อฝึกให้เป็น
  ผู้ดูแลระบบระดับ production

  นักศึกษาไม่จำเป็นต้องจำคำสั่งหรือ YAML ได้ขึ้นใจ แต่ต้อง "อธิบายได้"
  ว่าเกิดอะไรขึ้น ทำไมถึงเป็นแบบนั้น และถ้าเปลี่ยนค่าหนึ่งผลจะเปลี่ยนอย่างไร

ผลลัพธ์การเรียนรู้ (เมื่อจบทั้ง 3 ครั้ง นักศึกษาต้อง "อธิบายได้" ว่า...) :
  LO1  Kubernetes คืออะไร มีไว้แก้ปัญหาอะไรที่ Docker Compose แก้ไม่ได้
       และ control plane กับ worker node ทำหน้าที่ต่างกันอย่างไร
  LO2  Pod คืออะไร ทำไมหน่วยเล็กที่สุดถึงไม่ใช่ container
  LO3  แนวคิด desired state กับ self-healing ทำงานอย่างไร และทำไมลบ Pod
       ที่อยู่ใต้ Deployment แล้วถึงมีตัวใหม่ขึ้นมาแทน
  LO4  Service มีไว้ทำไม ทำไมเรียก Pod ด้วย IP ตรง ๆ ไม่ได้ และ ClusterIP
       กับ NodePort ต่างกันตรงไหน
  LO5  ทำไมต้องแยก config และรหัสผ่านออกจาก image (ConfigMap · Secret)
       และทำไมข้อมูลใน container ถึงหายเมื่อ Pod เกิดใหม่ (Volume · PVC)
  LO6  แอปหลายชั้นบน Kubernetes ประกอบกันอย่างไร และ rolling update
       ทำให้อัปเดตได้โดยผู้ใช้ไม่สะดุดได้อย่างไร
  LO7  เมื่อระบบมีปัญหา ควรไล่ดูอะไรตามลำดับ และอาการ Pending ·
       ImagePullBackOff · CrashLoopBackOff บอกอะไรกับเรา

หลักการสำคัญของชุดนี้ — CONCEPT FIRST :
  1. ทุกแล็บมี "แนวคิดหลัก" เพียงหนึ่งข้อ เขียนเป็นประโยคเดียวไว้ต้นแล็บ
     และทุกอย่างในแล็บต้องรับใช้ประโยคนั้น
  2. คำสั่งในแล็บให้สั้นและน้อยที่สุดเท่าที่พิสูจน์แนวคิดได้ — ไม่ต้องครบทุก flag
     ไม่ต้องครอบคลุมทุกกรณีใช้งาน
  3. YAML ที่ให้เขียนต้องสั้น อ่านจบในหน้าเดียว ตัด field ที่ไม่จำเป็นออกให้หมด
  4. ทุกแล็บปิดด้วย "คำถามที่ต้องตอบได้" 2-3 ข้อ ซึ่งเป็นคำถามเชิงแนวคิด
     ไม่ใช่คำถามว่าคำสั่งไหนพิมพ์อย่างไร
  5. หัวข้อระดับสูง (HPA · Job/CronJob · RBAC · StatefulSet · Helm ·
     blue-green/canary · ResourceQuota) ไม่ต้องทำเป็นแล็บ ให้กล่าวถึงสั้น ๆ
     ในสไลด์ว่า "มีอยู่ ใช้ตอนไหน" แล้วชี้แหล่งอ่านต่อเท่านั้น

ส่วนที่ 2.5 — แอปตัวอย่างจริงที่ใช้ตลอดทั้งชุด (สำคัญมาก)
--------------------------------------------------------------------------------
ทั้งชุดใช้ "แอปจริงตัวเดียว" เป็นตัวเดินเรื่อง ไม่ใช้ nginx หรือ whoami เปล่า ๆ
เพราะนักศึกษาต้องเห็นหน้าเว็บสวย ๆ ที่ใช้งานได้จริง แล้วค่อย ๆ เข้าใจว่า
Kubernetes ดูแลระบบแบบนี้อย่างไร

  Stack ที่ใช้
    web  : Next.js (App Router) + TypeScript + Tailwind CSS — UI ต้องสวยและใช้งานได้จริง
    api  : REST API (FastAPI หรือ Next.js Route Handler ก็ได้ ให้เลือกแบบเดียว
           แล้วใช้ให้เหมือนกันทั้งชุด)
    db   : PostgreSQL พร้อม schema และ seed data

  ต้นแบบที่ให้ยึด — มีของจริงอยู่แล้ว ให้ศึกษาและนำมาปรับใช้
    /root/workspace/DevTools/02_Docker/03_Fullstack_App_Example/002_LAB_Fullstack_Compose
      web/   Next.js + Tailwind (App Router, standalone build)
      api/   FastAPI + healthcheck ที่ยิง SELECT 1 เข้า db จริง
      db/    PostgreSQL + initdb (schema + seed)
      compose.yaml  ระบบ 3 service ที่รันได้จริงด้วยคำสั่งเดียว
    ให้ยกโครงนี้มาเป็นจุดตั้งต้น แล้ว "แปลงจาก Compose เป็น Kubernetes manifest"
    ซึ่งเป็นเส้นเรื่องหลักของชุดนี้พอดี — นักศึกษาเคยเห็นระบบนี้บน Docker Compose
    มาแล้ว จึงเทียบได้ทันทีว่าบน Kubernetes ของแต่ละชิ้นกลายเป็นอะไร

  ตารางเทียบที่ต้องมีในสไลด์ครั้งที่ 1 (เป็นสะพานเชื่อมความรู้เดิม)
      docker compose up          ->  kubectl apply -f
      service ใน compose.yaml    ->  Deployment + Service
      depends_on / healthcheck   ->  readiness / liveness probe
      environment:               ->  ConfigMap / Secret
      named volume               ->  PersistentVolumeClaim
      ports: "3000:3000"         ->  Service (NodePort) หรือ Ingress
      compose network + ชื่อ service ->  Service DNS ภายใน cluster

  วิธีใช้แอปตัวอย่างในแต่ละครั้ง
    ครั้งที่ 1 : ใช้เฉพาะ "web" ตัวเดียว (Next.js) เป็นตัวอย่างในทุกแล็บ
                 เพราะยังไม่ได้เรียน Service/Config — ให้หน้าเว็บแสดงชื่อ Pod
                 ที่ตอบกลับมา เพื่อให้เห็นผลของ scale / self-healing ด้วยตา
    ครั้งที่ 2 : เพิ่ม api และ db ทีละชิ้นตามหัวข้อที่เรียน
                 (Service -> ConfigMap -> Secret -> PVC -> probes)
    ครั้งที่ 3 : ประกอบครบ 3 ชั้นและเปิดผ่าน Ingress เป็นระบบที่ใช้งานได้จริง

  ข้อกำหนดของหน้าเว็บ (UI ต้อง "Wow" ไม่ใช่หน้าเปล่า)
    - ใช้ Tailwind จัดหน้าให้ดูเป็นมืออาชีพ : การ์ด · ตาราง · badge สถานะ · สีสื่อความหมาย
    - ต้องมีแถบ/การ์ดที่แสดง **ชื่อ Pod ที่ตอบ request นี้** และ **เวลาที่ตอบ**
      เพื่อให้เห็น load balancing และ rolling update ด้วยตาเปล่าแบบเรียลไทม์
    - มีหน้าที่ดึงข้อมูลจาก PostgreSQL จริง เพื่อพิสูจน์เรื่อง PVC และ Secret
    - มี endpoint /health และ /ready แยกกัน เพื่อใช้สอนเรื่อง probe ให้เห็นผลต่าง
    - รองรับการเปลี่ยนข้อความ/สีบางอย่างผ่าน environment variable
      เพื่อใช้สาธิต ConfigMap ให้เห็นการเปลี่ยนแปลงทันที
    - image ต้อง build ได้เองในเครื่องเรียนและ pin tag เวอร์ชันชัดเจน
      (เช่น :v1 และ :v2 สำหรับสอน rolling update / rollback)

  ภาพประกอบของหน้าเว็บ
    ต้อง capture จากหน้าเว็บที่รันจริงในเครื่องเรียนเท่านั้น ห้ามใช้ภาพที่ generate
    หรือจำลองขึ้น และภาพแต่ละ step ต้องตรงกับสิ่งที่นักศึกษาเห็นจริงในขั้นตอนนั้น


ส่วนที่ 3 — แผนการสอน 3 ครั้ง x 7 แล็บ (รวม 21 แล็บ)
--------------------------------------------------------------------------------
ทุกแล็บเขียนตามโครงเดียวกัน 3 บรรทัด : แนวคิดหลัก · พิสูจน์ด้วย · ต้องตอบได้ว่า
แล็บหนึ่งใช้เวลาประมาณ 20-30 นาที และมีแนวคิดหลักเพียงเรื่องเดียว

ทุกแล็บใช้ **แอปจริงตัวเดียวกันตลอดทั้งชุด** ตามส่วนที่ 2.5
(Next.js + Tailwind + API + PostgreSQL) โดยค่อย ๆ เพิ่มชิ้นส่วนเข้าไปทีละครั้ง
ห้ามใช้ nginx/whoami/busybox เปล่า ๆ เป็นตัวอย่างหลัก — ใช้ได้เฉพาะกรณีที่ต้อง
สาธิตอาการพังบางอย่างที่ทำกับแอปจริงไม่สะดวกเท่านั้น


########## ครั้งที่ 1 : Kubernetes คืออะไร และมันดูแลแอปให้เราอย่างไร ##########
ธีม : เข้าใจว่า Kubernetes คือระบบที่ "คอยทำให้สภาพจริงตรงกับสภาพที่เราสั่งไว้"

  001-kubernetes-introduction
      แนวคิดหลัก : Kubernetes คือผู้ดูแลที่คอยรันแอปให้ตรงกับที่เราสั่งไว้เสมอ
                   แม้เครื่องจะพังหรือแอปจะตาย
      พิสูจน์ด้วย : ดูภาพรวม cluster · kubectl get nodes · ดูว่ามีอะไรรันอยู่บ้าง
      ต้องตอบได้ว่า : Docker Compose ทำอะไรไม่ได้บ้างที่ Kubernetes ทำได้ ·
                     control plane กับ worker node ต่างกันอย่างไร

  002-kubectl-and-namespace
      แนวคิดหลัก : ทุกอย่างใน Kubernetes คือ "object" ที่เราสั่งผ่าน kubectl
                   และถูกจัดกลุ่มด้วย namespace
      พิสูจน์ด้วย : get · describe · -n · -o wide บน object ที่มีอยู่แล้ว
      ต้องตอบได้ว่า : namespace มีไว้ทำไม · ทำไมบางทีหา resource ไม่เจอ

  003-pod-the-smallest-unit
      แนวคิดหลัก : หน่วยเล็กที่สุดที่ Kubernetes ดูแลคือ Pod ไม่ใช่ container
      พิสูจน์ด้วย : รัน web (Next.js) เป็น Pod เดียว · ดู logs · exec เข้าไปดูข้างใน ·
                   port-forward แล้วเปิดหน้าเว็บสวย ๆ จากเบราว์เซอร์จริง
                   (จุดแรกที่นักศึกษาได้เห็นแอปของตัวเองรันบน Kubernetes)
      ต้องตอบได้ว่า : Pod ต่างจาก container อย่างไร · ทำไมถึงออกแบบมาแบบนั้น

  004-declarative-yaml
      แนวคิดหลัก : เราไม่ได้สั่งว่า "ทำอะไร" แต่บอกว่า "อยากได้สภาพแบบไหน"
                   แล้ว Kubernetes จัดการให้เอง (declarative)
      พิสูจน์ด้วย : เขียน Pod เดิมเป็น YAML สั้น ๆ · apply · แก้ไฟล์ · apply ซ้ำ
      ต้องตอบได้ว่า : imperative ต่างจาก declarative อย่างไร ·
                     apiVersion/kind/metadata/spec แต่ละส่วนบอกอะไร

  005-labels-the-glue
      แนวคิดหลัก : label คือกาวที่ทำให้ object ต่าง ๆ รู้จักกัน โดยไม่ต้องรู้จัก
                   ชื่อหรือ IP ของกันและกัน
      พิสูจน์ด้วย : ติด label · หยิบด้วย -l · เปลี่ยน label แล้วดูว่าหาไม่เจอ
      ต้องตอบได้ว่า : ทำไมระบบถึงใช้ label แทนการอ้างชื่อตรง ๆ

  006-desired-state-and-self-healing
      แนวคิดหลัก : Kubernetes เทียบ "จำนวนที่อยากได้" กับ "จำนวนที่มีจริง"
                   ตลอดเวลา แล้วแก้ส่วนต่างให้เอง
      พิสูจน์ด้วย : รัน web 3 ตัว · รีเฟรชหน้าเว็บดู "ชื่อ Pod ที่ตอบ" สลับไปมา ·
                   ลบ Pod ทิ้งแล้วดูตัวใหม่ขึ้นมาแทนทั้งบนหน้าเว็บและใน kubectl
                   (จุด "ว้าว" ของครั้งนี้ — เทียบกับแล็บ 003 ที่ลบแล้วหายเลย)
      ต้องตอบได้ว่า : self-healing เกิดขึ้นได้อย่างไร · ทำไมลบ Pod ในแล็บ 003
                     แล้วไม่มีตัวใหม่ขึ้น

  007-deployment-manages-change
      แนวคิดหลัก : Deployment คือชั้นที่ดูแล "การเปลี่ยนแปลง" ให้เรา —
                   scale และเปลี่ยนเวอร์ชันโดยไม่ต้องลบของเดิมทิ้งเอง
      พิสูจน์ด้วย : ดูสามชั้น Deployment -> ReplicaSet -> Pod · scale ·
                   เปลี่ยน image ของ web จาก :v1 เป็น :v2 (หน้าเว็บเปลี่ยนสี/ข้อความ
                   ให้เห็นชัด) · undo กลับเป็น :v1
      ต้องตอบได้ว่า : ทำไมถึงมีสามชั้น · rollback ทำได้เพราะอะไร


########## ครั้งที่ 2 : แอปคุยกันอย่างไร และตั้งค่า/เก็บข้อมูลอย่างไร ##########
ธีม : เข้าใจว่าของที่ "เกิดใหม่ตลอดเวลา" จะเชื่อมต่อกันและเก็บของได้อย่างไร

  008-why-we-need-service
      แนวคิดหลัก : Pod เกิดใหม่แล้ว IP เปลี่ยน จึงต้องมี "ชื่อคงที่" ให้เรียกแทน
      พิสูจน์ด้วย : ดู IP ของ Pod · ลบแล้วดู IP ใหม่ · สร้าง Service ให้ api
                   แล้วให้ web เรียก api ด้วย "ชื่อ service" (เหมือนที่เคยเรียก
                   ข้ามชื่อ service ใน Docker Compose)
      ต้องตอบได้ว่า : ทำไมเรียกด้วย IP ตรง ๆ ไม่ได้ · Service ช่วยอะไร

  009-service-types-and-access
      แนวคิดหลัก : Service มีหลายแบบ ต่างกันที่ "ใครเข้าถึงได้" ไม่ใช่ที่การทำงาน
      พิสูจน์ด้วย : api เป็น ClusterIP (เรียกได้เฉพาะข้างใน) · web เป็น NodePort
                   แล้วเปิดหน้าเว็บจากเบราว์เซอร์จริง — สะท้อนกฎเดิมจาก Compose
                   ที่มีเพียง web เท่านั้นที่ publish port
      ต้องตอบได้ว่า : ClusterIP กับ NodePort ต่างกันตรงไหน · ใช้อันไหนเมื่อไร

  010-configmap-separate-config
      แนวคิดหลัก : config ไม่ควรอยู่ใน image — build ครั้งเดียวแต่เปลี่ยน
                   พฤติกรรมได้ตามที่ deploy
      พิสูจน์ด้วย : ย้ายค่าอย่างชื่อระบบ/ธีมสีของหน้าเว็บไปไว้ใน ConfigMap
                   แล้วแก้ค่า -> restart -> หน้าเว็บเปลี่ยนให้เห็นทันที
      ต้องตอบได้ว่า : ถ้าฝัง config ไว้ใน image จะเจอปัญหาอะไร

  011-secret-and-why-not-configmap
      แนวคิดหลัก : ข้อมูลลับต้องแยกออกมาต่างหาก และ base64 ไม่ใช่การเข้ารหัส
      พิสูจน์ด้วย : ย้ายรหัสผ่าน PostgreSQL ไปไว้ใน Secret · ส่งเข้า api ·
                   ถอด base64 กลับด้วยคำสั่งเดียวให้เห็นกับตาว่ามันไม่ลับจริง
      ต้องตอบได้ว่า : Secret ต่างจาก ConfigMap อย่างไร · ทำไมห้าม commit ลง git

  012-why-data-disappears
      แนวคิดหลัก : ข้อมูลที่เขียนไว้ใน container หายเมื่อ Pod เกิดใหม่
                   เพราะ container ถูกสร้างใหม่จาก image เสมอ
      พิสูจน์ด้วย : เขียนไฟล์ใน Pod · ลบ Pod · ดูว่าไฟล์หาย
      ต้องตอบได้ว่า : ทำไมข้อมูลถึงหาย · แอปแบบไหนที่ได้รับผลกระทบ

  013-persistent-storage-with-pvc
      แนวคิดหลัก : ถ้าอยากให้ข้อมูลอยู่รอด ต้องเก็บไว้ "นอก" container
                   โดยขอพื้นที่ผ่าน PVC
      พิสูจน์ด้วย : ต่อ PVC ให้ PostgreSQL · เพิ่มข้อมูลผ่านหน้าเว็บ · ลบ Pod
                   ของ db · ขึ้นใหม่แล้วข้อมูลบนหน้าเว็บยังอยู่ครบ
                   (เทียบกับ named volume ที่เคยใช้ใน Compose)
      ต้องตอบได้ว่า : PVC คือการขออะไร · ต่างจาก emptyDir อย่างไร

  014-running-is-not-ready
      แนวคิดหลัก : "Pod Running" ไม่ได้แปลว่า "แอปพร้อมรับงาน"
      พิสูจน์ด้วย : ใช้ /health และ /ready ของแอปจริง · ตั้ง readiness probe
                   แล้วดูว่า Pod ที่ยังต่อ db ไม่ได้จะไม่ถูก Service ส่งงานให้
                   (เทียบกับ healthcheck + depends_on ที่เคยใช้ใน Compose)
      ต้องตอบได้ว่า : readiness กับ liveness ตอบคนละคำถามอย่างไร


########## ครั้งที่ 3 : ประกอบเป็นระบบจริงและดูแลต่อ ##########
ธีม : เห็นภาพรวมว่าชิ้นส่วนทั้งหมดประกอบกันเป็นระบบที่ใช้งานได้อย่างไร

  015-assembling-a-real-application
      แนวคิดหลัก : แอปจริงคือหลาย object ที่ทำงานร่วมกัน ไม่ใช่ object เดียว
      พิสูจน์ด้วย : deploy web (Next.js + Tailwind) + api ที่เรียกกันผ่านชื่อ Service
                   จนหน้าเว็บแสดงข้อมูลได้ครบ
      ต้องตอบได้ว่า : แต่ละ object ในระบบนี้ทำหน้าที่อะไร ถ้าขาดตัวไหนจะเกิดอะไร

  016-adding-a-database
      แนวคิดหลัก : ส่วนที่มีข้อมูลต้องการการดูแลต่างจากส่วนที่ไม่มีข้อมูล
      พิสูจน์ด้วย : เพิ่ม PostgreSQL + PVC + Secret เข้าไปเป็นชั้นที่ 3 ·
                   บันทึกข้อมูลผ่านหน้าเว็บ · ลบ Pod ของ db · ข้อมูลยังอยู่
      ต้องตอบได้ว่า : stateless กับ stateful ต่างกันอย่างไรในทางปฏิบัติ

  017-ingress-the-front-door
      แนวคิดหลัก : Ingress คือประตูหน้าบ้านที่ทำหน้าที่เดียวกับ reverse proxy
                   ที่เคยเรียน แต่รับคำสั่งจาก Kubernetes
      พิสูจน์ด้วย : route ตาม path — / ไป web, /api ไป api
                   เข้าเว็บจาก URL เดียวแทนการจำหลาย port
      ต้องตอบได้ว่า : Ingress ต่างจาก NodePort อย่างไร · เกี่ยวข้องกับ
                     reverse proxy ที่เรียนมาก่อนหน้าอย่างไร

  018-updating-without-downtime
      แนวคิดหลัก : เปลี่ยนเวอร์ชันทีละส่วนทำให้ผู้ใช้ไม่สะดุด
      พิสูจน์ด้วย : เปิดหน้าเว็บค้างไว้แล้วรีเฟรชรัว ๆ ระหว่าง update จาก :v1
                   เป็น :v2 · เห็นชื่อ Pod และหน้าตาเว็บค่อย ๆ เปลี่ยนทีละตัว
                   โดยเว็บไม่เคยล่ม · undo กลับ
      ต้องตอบได้ว่า : ทำไม rolling update ถึงไม่ทำให้เว็บล่ม ·
                     rollback ทำได้เพราะระบบเก็บอะไรไว้

  019-telling-kubernetes-what-you-need
      แนวคิดหลัก : Kubernetes ต้องรู้ว่าแอปใช้ทรัพยากรเท่าไร จึงจะเลือก node
                   ให้ถูกและกันไม่ให้ตัวหนึ่งกินหมด
      พิสูจน์ด้วย : ตั้ง requests/limits · ขอเกินที่มี แล้วดู Pod ค้าง Pending
      ต้องตอบได้ว่า : requests กับ limits มีผลคนละจังหวะอย่างไร

  020-reading-the-symptoms
      แนวคิดหลัก : อาการที่ Kubernetes แสดง บอกได้ว่าปัญหาอยู่ชั้นไหน
      พิสูจน์ด้วย : ดู 4 อาการยอดฮิตจากระบบที่พังจริง — Pending ·
                   ImagePullBackOff · CrashLoopBackOff · Service ไม่มีปลายทาง
      ต้องตอบได้ว่า : แต่ละอาการชี้ไปที่สาเหตุกลุ่มไหน ·
                     ควรไล่ดูอะไรตามลำดับ (get -> describe -> logs -> events)

  021-the-big-picture
      แนวคิดหลัก : ทุกอย่างที่เรียนมาต่อกันเป็นภาพเดียวได้
      พิสูจน์ด้วย : ประกอบระบบ Next.js + API + PostgreSQL ให้ครบและใช้งานได้จริง
                   ผ่าน Ingress แล้ววาดแผนภาพเส้นทางของ request ตั้งแต่เบราว์เซอร์
                   จนถึง PostgreSQL พร้อมบอกชื่อ object ที่ผ่านทุกตัว
      ต้องตอบได้ว่า : request หนึ่งเดินผ่าน object อะไรบ้างตามลำดับ ·
                     ถ้าตัดชิ้นใดออกระบบจะพังตรงไหน

    - <html lang="th"> · เวทีขนาดคงที่ 1280x720 px · scale อัตโนมัติด้วย

    - ทุก <img> ต้องมี alt ภาษาไทยที่บรรยายภาพจริง (เพื่อการเข้าถึงและการค้นหา)

    image     : tuchsanai/devtools-k8s:2569_1  (Ubuntu 26.04 + Docker-in-Docker)

        docker pull tuchsanai/devtools-k8s:2569_1

  สร้าง cluster — มีสคริปต์สำเร็จอยู่แล้วใน image ให้ใช้ตัวนี้ อย่าเขียนใหม่
        k8s-bootstrap                 # kind cluster ชื่อ "devtools"
                                      # 1 control-plane + 2 worker
                                      # + metrics-server + ingress-nginx
        k8s-bootstrap --single-node   # เครื่องแรมน้อย
        k8s-teardown                  # ลบ cluster ทิ้ง
    context ที่ได้คือ kind-devtools

    helm v4.2.4 · k9s v0.51.0 · stern v1.34.0 · kustomize v5.8.1 · yq v4.53.6
    Node.js 24 · Python venv ที่ /opt/venv (มี uv)

  การเข้าถึงหน้าเว็บจากเบราว์เซอร์ (สำคัญมาก ต้องเขียนให้ตรงนี้ในทุกแล็บ)
    - Ingress : kind map 80/443 ของ control-plane ออกมาที่ container
                แล้ว container map ต่อออก host เป็น 8080 และ 8443
                => เปิดเว็บผ่าน Ingress ที่  http://localhost:8080
    - NodePort / port-forward : ใช้ port 3000 หรือ 9090 ที่เปิดไว้ให้แล้ว
                เช่น kubectl port-forward svc/web 3000:3000 --address 0.0.0.0
                => http://localhost:3000
    - ให้ใช้วิธีเดียวกันนี้ทั้งชุด อย่าสลับไปมาจนนักศึกษาสับสน

    alias : k · kgp · kgn · kaf · kdes  (มี bash completion ให้ครบ)

    stern : ตาม log หลาย Pod พร้อมกัน — เหมาะกับแล็บ rolling update และ debug

  วินัยการใช้ cluster
    - ทุกแล็บใช้ namespace ของตัวเอง (เช่น lab003) และลบ namespace ทิ้งเมื่อจบ
    - ห้ามให้แล็บหนึ่งทิ้ง resource ไว้ชนแล็บถัดไป
    - แล็บที่ใช้ Ingress ให้ตรวจก่อนว่า ingress-nginx พร้อม
      (kubectl -n ingress-nginx get pods)
    - image ของแอปตัวอย่างต้อง load เข้า kind ก่อนใช้ :
        kind load docker-image k8s-lab-web:v1 --name devtools

# แนวทางภาษาวิชาการของชุดวิชา Kubernetes (ผู้สอนกำหนด 2026-09-03: "ต้องการให้การใช้ภาษาทั้งหมดเป็นภาษาวิชาการ")

## A. หลักการ (บังคับทุกไฟล์: README ทุกระดับ · YAML_Guide.md · สไลด์ · photos.md · ข้อความในไดอะแกรม)
1. ใช้ภาษาไทยระดับทางการ/วิชาการ แบบเอกสารประกอบการสอนระดับอุดมศึกษา: ประโยคสมบูรณ์ มีประธาน-กริยา ชัดเจน ไม่ใช้ภาษาพูด ไม่ใช้คำลงท้าย ไม่ใช้คำอุทาน ไม่ใช้สแลง
2. ไม่ใช้สรรพนามบุรุษที่ 1-2 (ผม เรา คุณ) → ใช้ "ผู้เรียน" "ผู้สอน" หรือเรียบเรียงเป็นประโยคไม่ระบุบุคคล (เช่น "เมื่อลบ Pod ระบบจะสร้าง Pod ใหม่")
3. คำถามเชิงโวหาร (rhetorical) → เปลี่ยนเป็นประโยคบอกเล่า หรือคำถามทางการที่ลงท้ายด้วย "หรือไม่ / อย่างไร / เหตุใด"
4. ศัพท์เทคนิคของ Kubernetes/Docker/Linux คงเป็นภาษาอังกฤษตามเดิม (Pod, Deployment, kubectl, container, cluster, manifest, rollout ...) ไม่ถอดเสียง · คำทั่วไปใช้ภาษาไทย · ศัพท์บัญญัติที่ใช้: สภาพที่ต้องการ (desired state) · สภาพจริง (actual state) · การปรับให้สอดคล้อง (reconcile) · ป้ายกำกับ (label) · ตัวเลือก (selector) · เนมสเปซ (namespace) ใช้คำอังกฤษได้เมื่ออ้างชื่อ object
5. หน่วยเวลา/ตัวเลขเขียนแบบทางการ: "เวลา 03.00 น." ไม่ใช่ "ตีสาม" · "จำนวน 3 รายการ" ไม่ใช่ "3 ตัว"
6. ความยาวใกล้เคียงเดิม (±10% ของจำนวนบรรทัดต่อไฟล์) ไม่เพิ่มเนื้อหาใหม่ ไม่ตัดเนื้อหาเดิม — เปลี่ยน "ภาษา" เท่านั้น
7. ตัวอักษรเชิงโครงสร้างที่ linter ใช้ (📝 ✅ 💡 ❓ 🧭 และ "—" ในหัวข้อ) คงไว้ · เครื่องหมาย "?" ท้ายหัวข้อให้เลี่ยง
